A Gradle plugin that scans your OpenAPI documentation for operations, compares them against a set of implemented endpoints, and reports every operation that has no match - a "mirage API". By default, "implemented" means exposed by a scanned Spring Boot `@RestController` class; set `scanMocks = true` to instead treat WireMock stub mapping files as the implementation evidence - see "Scanning WireMock stubs instead of controllers" below.

Mirage APIs are endpoints that exist on paper but not in code: documented, reviewed, and visible to API consumers, yet unreachable at runtime. This is the mirror image of the companion link:../shadow-api-detector/README.adoc[Shadow API Detector] plugin, which catches the opposite drift - implemented but undocumented endpoints.

== OpenAPI compatibility

The plugin supports OpenAPI v3 documents that are compatible with the parser stack bundled by the plugin.
In practice, this means OpenAPI 3.0.x, 3.1.x, and 3.2.x are supported.
OpenAPI v2 (Swagger 2.0) is not supported.
OpenAPI versions newer than 3.2 are not supported at this time.
If `rootDocument` declares an unsupported version, the `detectMirageApis` task fails with a parse error.
The root document and every transitively referenced `$ref` document must also be parseable and resolvable as OpenAPI v3 content.

=== OpenAPI 3.2 support details (current implementation)

OpenAPI 3.2 support is currently implemented as a compatibility workaround.
The plugin first tries to parse the configured root document as-is.
If that parse fails and the root document declares `openapi: 3.2.x`, the plugin creates a temporary compatibility copy of the root document in the same directory.
In that temporary copy, only the root `openapi` version string is rewritten from `3.2.x` to `3.1.0`.
The plugin then parses that temporary compatibility file and continues normal endpoint extraction.
The original source OpenAPI document is not modified.
The temporary compatibility file is deleted after parsing.

[CAUTION]
====
This is an explicit, temporary compatibility mechanism.
It is not native end-to-end OpenAPI 3.2 parser support.
It exists so OpenAPI 3.2 root documents can be processed with the parser stack available in the plugin today.
====

== How it works

1. The configured root OpenAPI document is parsed, following every `$ref` link - including links to other documents, resolved relative to the root document - to build the full set of described endpoints, each with its HTTP verb, path template, `operationId`, and tags.
2. Steps 2-4 below describe the default mode. Every Java source file under the configured controller directories is parsed and scanned for classes annotated with `@RestController`. This is an MVP restriction - only Spring MVC's annotation-based REST controllers are recognised.
3. For each `@RestController` class, the class-level `@RequestMapping` base path (if any) is combined with every method-level `@RequestMapping`, `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`, and `@PatchMapping` to build the full set of implemented endpoints.
4. Endpoints are matched by HTTP verb and by path template; path variables are matched positionally, so an OpenAPI `{userId}` matches a controller's `{id}`. A described endpoint is considered implemented as soon as a matching controller endpoint is found, whether that endpoint's verb matches exactly or the controller method carries `HttpVerb.ANY` (a Spring `@RequestMapping` that does not restrict its HTTP method).
5. Every described endpoint with no matching implementation is a mirage API. An AsciiDoc report listing them, grouped by their OpenAPI tag (or `(untagged)` when none is set), is written to the configured report directory - the report is always written, whether or not the build is configured to fail.

[NOTE]
====
This is a scope restriction of the current MVP, not a design limit: only `@RestController`-based endpoints (or, in `scanMocks` mode, WireMock stubs) are recognised as implementation evidence, and only "documented but unimplemented" is reported (the reverse case - implemented but undocumented - is the companion link:../shadow-api-detector/README.adoc[Shadow API Detector] plugin's job). Both may be lifted in a future release.
====

== Scanning WireMock stubs instead of controllers

By default, an OpenAPI operation is considered implemented as soon as a matching `@RestController` endpoint is found. Set `scanMocks = true` to use a different notion of "implemented" entirely: an operation is implemented when a WireMock stub mocks it, regardless of whether any controller exists for it. This suits teams building against a contract before the real implementation exists - or testing purely at the API-mock boundary - where "is this endpoint stubbed for consumer testing?" matters more than "does a controller method exist?".

[IMPORTANT]
====
`scanMocks` and controller scanning are mutually exclusive, not additive. When `scanMocks = true`, `controllerDirs` is not scanned at all - a real, working `@RestController` implementation with no matching stub still reports as a mirage API.
====

The plugin looks for `*.json` files, recursively, under `stubDirs` (default `src/test/resources/mappings`, WireMock's own conventional mapping directory). One file is expected to describe one stub - the common convention for files stored under a `mappings` directory. Each file is read structurally for its first `method` field and its first `url`, `urlPath`, `urlPattern`, or `urlPathPattern` field - deliberately without a JSON parser or the WireMock library itself on this plugin's classpath, the same "read the file as data, not code" approach the companion link:../doppelganger-api-detector/README.adoc[Doppelganger API Detector] plugin uses for Spring Cloud Contract files.

.Example stub mapping file (`src/test/resources/mappings/getItem.json`)
[source,json]
----
{
  "request": {
    "method": "GET",
    "urlPath": "/items/1"
  },
  "response": {
    "status": 200
  }
}
----

[source,groovy]
----
mirageApiDetector {
    scanMocks = true
    stubDirs.from('src/test/resources/mappings')
}
----

== Configuration

The plugin registers a `mirageApiDetector` extension.

.Groovy DSL
[source,groovy]
----
mirageApiDetector {
    // One or more directories to search recursively for @RestController classes, used to
    // determine which OpenAPI operations are implemented. Not scanned when scanMocks is true.
    // Default: src/main/java
    controllerDirs.from('src/main/java')

    // Whether to determine implemented endpoints from WireMock stub mapping files instead of
    // scanning @RestController classes. See "Scanning WireMock stubs instead of controllers".
    // Default: false
    scanMocks = false

    // One or more directories to search recursively for WireMock stub mapping files, used only
    // when scanMocks is true.
    // Default: src/test/resources/mappings
    // stubDirs.from('src/test/resources/mappings')

    // The root OpenAPI document. Required - every other document is expected to be
    // reachable from this one via $ref links relative to it.
    rootDocument = file('src/main/resources/openapi/openapi.yaml')

    // Directory where the OpenAPI documentation is stored, tracked so that a change to
    // any linked document invalidates the task's cached result.
    // Default: rootDocument's own parent directory
    openApiDir = file('src/main/resources/openapi')

    // Whether the build should fail when mirage APIs are found. The report is written
    // either way.
    // Default: false
    failOnMirage = false

    // Directory the AsciiDoc report is written to.
    // Default: layout.buildDirectory.dir('reports/mirage-api-detector')
    reportDir = layout.buildDirectory.dir('reports/mirage-api-detector')

    // Name of the generated AsciiDoc report file.
    // Default: 'mirage-apis.adoc'
    reportFileName = 'mirage-apis.adoc'

    // Version of the system under test whose @RestController classes are scanned, printed near
    // the top of the generated report (see "System Under Test Version" below).
    // Default: the project's own `version`
    // systemUnderTestVersion = 'v1.0.0'

    // Persists a per-endpoint history of when each endpoint first reached declared/implemented/
    // verified status (see "Tracking Contract History" below).
    // Default: false
    trackContractHistory = false

    // NDJSON file the history is read from/written to. Defaults into the project directory
    // (not build/), since it's meant to be committed.
    // Default: file('mirage-api-detector-contract-history.ndjson')
    // contractHistoryFile = file('mirage-api-detector-contract-history.ndjson')

    // When true, contractHistoryFile is written back to disk. Only consulted when
    // trackContractHistory is true; the file is always read either way.
    // Default: same as trackContractHistory
    // updateContractHistory = true
}
----

.Kotlin DSL
[source,kotlin]
----
mirageApiDetector {
    controllerDirs.from("src/main/java")
    scanMocks.set(false)
    // stubDirs.from("src/test/resources/mappings")
    rootDocument.set(file("src/main/resources/openapi/openapi.yaml"))
    failOnMirage.set(false)
    reportDir.set(layout.buildDirectory.dir("reports/mirage-api-detector"))
    reportFileName.set("mirage-apis.adoc")
    // systemUnderTestVersion.set("v1.0.0")
    trackContractHistory.set(false)
    // contractHistoryFile.set(file("mirage-api-detector-contract-history.ndjson"))
    // updateContractHistory.set(true)
}
----

`rootDocument` is the only property that must be set - in all but very rare cases (an OpenAPI description split across many top-level documents with no single entry point) the root document is all the plugin needs, since it is expected to link to every other document itself.

== Task

[cols="2,1,3",options="header"]
|===
| Task name           | Group        | Description
| `detectMirageApis`  | verification | Scans the OpenAPI documentation and reports operations with no matching implementation (a `@RestController` class by default, or a WireMock stub when `scanMocks` is true).
|===

The task is **not** wired into `check` or `build` automatically. Teams that write their OpenAPI documentation ahead of the implementation - a common "spec-first" workflow - would otherwise see every build fail on endpoints that simply have not been built yet.

Running the report explicitly:

[source,shell]
----
./gradlew detectMirageApis
----

To make the task part of every build, wire it into `check` (or `build`) yourself once you're ready to enforce it:

.Groovy DSL
[source,groovy]
----
tasks.named('check') {
    dependsOn 'detectMirageApis'
}
----

.Kotlin DSL
[source,kotlin]
----
tasks.named("check") {
    dependsOn("detectMirageApis")
}
----

== Progress reporting

Resolving OpenAPI documents and scanning `@RestController` classes can take a while on a large codebase.
The task periodically logs progress at `LIFECYCLE` level so a long-running scan doesn't sit silently until it finishes.

[source,shell]
----
> Task :detectMirageApis
Resolving OpenAPI documents: 12 processed so far
Resolving OpenAPI documents: done, 14 item(s)
Scanning @RestController classes: 150/438 (34%)
Scanning @RestController classes: done, 438 file(s)
Mirage API Detector: scanned 512 described endpoint(s), found 2 mirage API(s). Report → build/reports/mirage-api-detector/mirage-apis.adoc
----

This is plain log output, not an animated progress indicator.
The plugin deliberately avoids Gradle's internal, unsupported console/progress APIs, since their shape can change between Gradle versions and this plugin is published on the Gradle Plugin Portal for consumers on Gradle versions this project doesn't control.
Each line is printed once and never overwritten in place, so it plays back cleanly in CI logs as well as an interactive terminal.

The `@RestController` progress line only appears when `scanMocks` is `false`; scanning WireMock stubs does not currently report per-file progress.

== Tracking Contract History

Setting `trackContractHistory = true` persists, across builds, a history of when each endpoint first reached each stage of its contract lifecycle - declared, implemented, verified.
The history is keyed by a fingerprint of the endpoint's own HTTP verb and path, not by which plugin observed it, so Shadow, Mirage, and Doppelganger API Detector can all advance the *same* record when pointed at the same `contractHistoryFile` - useful if you run more than one of these plugins against the same API.
Mirage API Detector only ever has evidence for the `declared` and `implemented` stages (from the OpenAPI documentation, and from either the scanned `@RestController` classes or WireMock stubs depending on `scanMocks`); it never advances `verifiedAt`, since it has no visibility into contract verification evidence.
The plugin itself has no dependency on git or any other version control system - branch-based control over when to advance the history (e.g. "only on `main`") is entirely a CI concern, expressed through `updateContractHistory`.

[cols="1,1,1,3",options="header"]
|===
| Property                | Type    | Default                                                    | Description
| `trackContractHistory`  | Boolean | `false`                                                    | When `true`, loads, advances, and reports from a persisted contract progress history file.
| `contractHistoryFile`   | File    | `mirage-api-detector-contract-history.ndjson` (project directory) | The NDJSON file the history is read from and, when `updateContractHistory` is `true`, written back to.
Deliberately defaults into the project directory, not `build/`, since it's meant to be committed. Only consulted when `trackContractHistory` is `true`.
| `updateContractHistory` | Boolean | same as `trackContractHistory`                             | When `true`, `contractHistoryFile` is written back to disk after being updated with the current run's endpoints.
The file is always *read* when `trackContractHistory` is `true`, regardless of this property - so the generated report always reflects the up-to-date history, whether or not this run persists it. Overridable for the whole build via the `-PmirageApiDetector.updateContractHistory` project property.
|===

`contractHistoryFile` is newline-delimited JSON (NDJSON) - one line per endpoint - sorted by fingerprint so that git diffs stay minimal and stable:

[source,json]
----
{"fingerprint":"a1f3c9d0e21b7f44","verb":"GET","path":"/orders/{id}","declaringClass":"com.example.OrderController","declaredAt":"2026-01-14T09:02:11Z","implementedAt":"2026-02-20T11:15:44Z","verifiedAt":null,"lastSeenAt":"2026-08-12T07:00:00Z","removedAt":null}
----

A missing `contractHistoryFile` is treated as an empty history, not an error.
A line that fails to parse (e.g. hand-edited into something invalid) is skipped with a `WARNING`-level `java.util.logging` message identifying its line number; it never fails the build.
A previously persisted record whose fingerprint is no longer present in the current scan is *never deleted* - it's kept exactly as it was, except its `removedAt` is stamped the first time it goes missing.

The generated report reflects the loaded (and possibly just-advanced) history as a `== Progress Over Time` section, once `trackContractHistory` finds at least one record: a human-friendly `Tracked since` timestamp, how many endpoints were declared/implemented/verified in the last 7 and 30 days, and how many previously tracked endpoints are no longer seen in the current run.

Like any other Gradle task, `detectMirageApis` is skipped as `UP-TO-DATE` when none of its declared inputs have changed since the last run.
`contractHistoryFile`'s configured *path* (not its content, which the task itself manages) is one of those tracked inputs, so renaming or relocating it in the build script is, on its own, enough to make the task run again and write history to the newly configured location.
If a run is skipped for some other reason and you need to force it regardless (e.g. after manually editing `contractHistoryFile`), pass `--rerun`:

[source,shell]
----
./gradlew detectMirageApis --rerun
----

== System Under Test Version

Every generated report includes a line just below the title identifying the version of the system under test that was scanned:

[source,asciidoc]
----
System Under Test version: 1.0.0
----

By default, this is the project's own `version`, exactly as set in `build.gradle`/`build.gradle.kts` or a `gradle.properties` file. Set `systemUnderTestVersion` to override it - useful when the `@RestController` classes in `controllerDirs` belong to a different, independently versioned artifact than the one Gradle is building:

[source,groovy]
----
mirageApiDetector {
    systemUnderTestVersion = 'v1.0.0'
}
----

== Report output

After the task runs, an AsciiDoc report is written to the configured `reportDir` (default: `build/reports/mirage-api-detector/mirage-apis.adoc`), listing every mirage API grouped by its OpenAPI tag (or `(untagged)` when the operation declares none), with its HTTP verb, path, and `operationId`.

Every report opens with a preamble explaining what a mirage API is, how it differs from a shadow API and a zombie API, what the risks are, and a link to the https://owasp.org/API-Security/editions/2023/en/0x11-t10/[OWASP API Security Top 10] (specifically https://owasp.org/API-Security/editions/2023/en/0xa9-improper-inventory-management/[API9:2023 Improper Inventory Management]). The preamble text lives in its own bundled resource - `mirage-api-preamble.adoc` in the plugin's `src/main/resources` - so it can be revised independently of the report-writing code.

When `failOnMirage` is `true` and at least one mirage API was found, the task fails the build after writing the report, so the report is always available for inspection regardless of build outcome.

== Full example

[source,groovy]
----
plugins {
    id 'java'
    id 'org.springframework.boot' version '<version>'
    id 'com.arc-e-tect.mirage-api-detector' version '<version>'
}

mirageApiDetector {
    rootDocument = file('src/main/resources/openapi/openapi.yaml')
    failOnMirage = true
}

tasks.named('check') {
    dependsOn 'detectMirageApis'
}
----

With this setup, running `./gradlew check` will fail the build - after writing the report - as soon as any operation in `openapi.yaml` (or any document it links to) is found with no matching `@RestController` endpoint.

== Relationship to the Shadow API Detector

This plugin and link:../shadow-api-detector/README.adoc[Shadow API Detector] scan the same two sources of truth - your `@RestController` classes and your OpenAPI documentation - and compare them in opposite directions:

[cols="1,3",options="header"]
|===
| Plugin                | Finds
| Shadow API Detector   | `@RestController` endpoints with no matching OpenAPI operation (implemented, undocumented)
| Mirage API Detector   | OpenAPI operations with no matching `@RestController` endpoint (documented, unimplemented)
|===

Applying both plugins to the same project gives full-coverage drift detection between your code and your contract in either direction. The two plugins share the same DSL shape and configuration property names (mapped one-to-one, e.g. `failOnShadow` / `failOnMirage`) so switching between - or applying both alongside - them requires no relearning.
