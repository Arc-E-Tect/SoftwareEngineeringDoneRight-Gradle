A Gradle plugin that scans your OpenAPI documentation for operations, compares them against the endpoints exposed by scanned Spring Boot `@RestController` classes, and reports every operation that has no match - a "mirage API". Set `scanMocks = true` to additionally scan WireMock stub mapping files - and Java source that creates WireMock stubs at run time - for stub evidence, recorded into contract history and the report alongside the real implementation evidence above - see "Additionally scanning WireMock stubs" below.

Mirage APIs are endpoints that exist on paper but not in code: documented, reviewed, and visible to API consumers, yet unreachable at runtime. This is the mirror image of the companion link:../shadow-api-detector/README.adoc[Shadow API Detector] plugin, which catches the opposite drift - implemented but undocumented endpoints.

== OpenAPI compatibility

The plugin supports OpenAPI v3 documents that are compatible with the parser stack bundled by the plugin.
In practice, this means OpenAPI 3.0.x, 3.1.x, and 3.2.x are supported.
OpenAPI v2 (Swagger 2.0) is not supported.
OpenAPI 2 compatibility conversion is explicitly excluded from the runtime classpath.
The plugin uses `io.swagger.parser.v3:swagger-parser-v3` only.
OpenAPI versions newer than 3.2 are not supported at this time.
If `rootDocument` declares an unsupported version, the `detectMirageApis` task fails with a parse error.
The root document and every transitively referenced `$ref` document must also be parseable and resolvable as OpenAPI v3 content.

=== OpenAPI 3.2 support details (current implementation)

OpenAPI 3.2 support is currently implemented as a compatibility workaround.
The plugin first tries to parse the configured root document as-is.
If that parse fails and the root document declares `openapi: 3.2.x`, the plugin creates a temporary compatibility copy of the root document in the same directory.
In that temporary copy, only the root `openapi` version string is rewritten from `3.2.x` to `3.1.0`.
The plugin then parses that temporary compatibility file and continues normal endpoint extraction.
The original source OpenAPI document is not modified.
The temporary compatibility file is deleted after parsing.

[CAUTION]
====
This is an explicit, temporary compatibility mechanism.
It is not native end-to-end OpenAPI 3.2 parser support.
It exists so OpenAPI 3.2 root documents can be processed with the parser stack available in the plugin today.
====

== How it works

1. The configured root OpenAPI document is parsed, following every `$ref` link - including links to other documents, resolved relative to the root document - to build the full set of described endpoints, each with its HTTP verb, path template, `operationId`, and tags.
2. Steps 2-4 below describe the default mode. Every Java source file under the configured controller directories is parsed and scanned for classes annotated with `@RestController`. This is an MVP restriction - only Spring MVC's annotation-based REST controllers are recognised.
3. For each `@RestController` class, the class-level `@RequestMapping` base path (if any) is combined with every method-level `@RequestMapping`, `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`, and `@PatchMapping` to build the full set of implemented endpoints.
4. Endpoints are matched by HTTP verb and by path template; path variables are matched positionally, so an OpenAPI `{userId}` matches a controller's `{id}`. A described endpoint is considered implemented as soon as a matching controller endpoint is found, whether that endpoint's verb matches exactly or the controller method carries `HttpVerb.ANY` (a Spring `@RequestMapping` that does not restrict its HTTP method).
5. Every described endpoint with no matching implementation is a mirage API. An AsciiDoc report listing them, grouped by their OpenAPI tag (or `(untagged)` when none is set), is written to the configured report directory - the report is always written, whether or not the build is configured to fail.

[NOTE]
====
This is a scope restriction of the current MVP, not a design limit: only `@RestController`-based endpoints are recognised as implementation evidence, and only "documented but unimplemented" is reported (the reverse case - implemented but undocumented - is the companion link:../shadow-api-detector/README.adoc[Shadow API Detector] plugin's job). Both may be lifted in a future release.
====

== Additionally scanning WireMock stubs

An OpenAPI operation is considered implemented - and so never reported as a mirage API - as soon as a matching `@RestController` endpoint is found; that never changes. Set `scanMocks = true` to *additionally* scan `stubDirs` for WireMock stub mapping files: every match is recorded as stub evidence (`stubbedAt`) in contract history and the report's `== Progress Over Time` section, alongside whatever real implementation evidence `controllerDirs` found. This suits teams that want to track "is this endpoint stubbed for consumer testing?" as a separate signal from "does a controller method exist?", without losing sight of which endpoints are still genuinely unimplemented.

[IMPORTANT]
====
Stub evidence never counts as implementation evidence. An endpoint stubbed by WireMock but implemented by no `@RestController` still reports as a mirage API - `scanMocks` only ever adds `stubbedAt` information, it never removes an endpoint from the Mirage APIs list.
====

The plugin looks for `*.json` files, recursively, under `stubDirs` (default `src/test/resources/mappings`, WireMock's own conventional mapping directory). One file is expected to describe one stub - the common convention for files stored under a `mappings` directory. Each file is read structurally for its first `method` field and its first `url`, `urlPath`, `urlPattern`, or `urlPathPattern` field - deliberately without a JSON parser or the WireMock library itself on this plugin's classpath, the same "read the file as data, not code" approach the companion link:../doppelganger-api-detector/README.adoc[Doppelganger API Detector] plugin uses for Spring Cloud Contract files.

.Example stub mapping file (`src/test/resources/mappings/getItem.json`)
[source,json]
----
{
  "request": {
    "method": "GET",
    "urlPath": "/items/1"
  },
  "response": {
    "status": 200
  }
}
----

=== Matching a stub's id segment to its declared/implemented endpoint's path variable

A stub mapping file has no concept of a named path variable the way an OpenAPI document or a `@RequestMapping` does - it only ever records either a regular expression (`urlPattern`/`urlPathPattern`) or a literal example value (`url`/`urlPath`) for the request path it matches. Left as-is, neither would ever be recognised as evidence for the corresponding `{customerId}`-style declared/implemented endpoint - each would instead accumulate as its own, permanently unmatched, orphaned path, both in this run's `Stubbed: Yes`/`No` display and in `contractHistoryFile`. So every `"/"`-delimited path segment that *looks like* it stands in for a path variable is rewritten into a `{id}` placeholder before comparison - the same shape a declared/implemented endpoint's own path variable uses - by two separate heuristics, one per matcher kind:

[cols="1,2,2",options="header"]
|===
| Field | Segment rewritten when... | Example
| `urlPattern` / `urlPathPattern` | it contains a regular-expression metacharacter, *or* it's purely numeric even without one - a `urlPathPattern` value is free to be a plain literal instead of an actual regular expression, and gets the same numeric-id treatment `url`/`urlPath` does below | `"/customers/[0-9]+"` → `/customers/{id}` +
`"/customers/123"` → `/customers/{id}`
| `url` / `urlPath` | it consists of digits only | `"/customers/700336"` → `/customers/{id}`
|===

A segment that doesn't match either shape - e.g. `orders`, `post`, or a mixed alphanumeric identifier like `ord-2026-001` - is left exactly as written.

[IMPORTANT]
====
Both heuristics are deliberately imprecise, not a certainty, and this is a known, accepted trade-off rather than an oversight:

* A WireMock regular expression can express far more than "any numeric id here", and this scanner doesn't attempt to parse it as one - it only recognises the *shape* of a segment (does it contain a regex metacharacter at all), not what the expression actually matches.
* A **literal, purely numeric path segment that genuinely is not a path variable** - e.g. a year in a URL such as `/reports/2026` - is indistinguishable, by shape alone, from an example id standing in for one, and is rewritten into `/reports/{id}` all the same. If that endpoint's real declared/implemented path is truly the literal `/reports/2026`, this stub's evidence will now fail to match *that* - the same "orphaned, unmatched path" failure mode this rewriting exists to fix, just triggered in the opposite direction.

There is currently no way to opt a specific stub file or segment out of either rewrite - a genuinely literal numeric path segment has no way to signal that it means exactly what it says. In practice, a stub matching a truly fixed, non-variable numeric path is rare enough - and the alternative of leaving every numeric-id stub permanently unmatched is common enough - that this plugin accepts the trade-off by default.
====

[source,groovy]
----
mirageApiDetector {
    scanMocks = true
    stubDirs.from('src/test/resources/mappings')
}
----

=== Interpreting a stub whose evidence never merges with a declared/implemented endpoint

A stub's evidence staying permanently unmerged is visible directly in `contractHistoryFile`: its own record, with `stubbedAt` set but `declaringClass`, `declaredAt`, and `implementedAt` all `null`, never joining the record for the endpoint it was actually meant to exercise. The heuristics above are one reason this happens, but not the only one - and this plugin has no way to tell the difference on its own. Before assuming the scanner is wrong, check for these, in roughly the order they're worth ruling out:

[cols="1,3",options="header"]
|===
| Cause | What it looks like

| A regex/id-segment mismatch (see above)
| The stub's path, after canonicalisation, still doesn't structurally match its endpoint's declared/implemented path - a different segment count, a different literal segment, or the false-positive/false-negative case the heuristics above knowingly accept.

| The endpoint is a genuine Shadow API
| The `@RestController` method the stub is meant to exercise really exists, but was never added to the OpenAPI documentation. `scanMocks` only ever compares stub evidence against what *this* plugin (and any sibling detector sharing the same `contractHistoryFile`) has found declared or implemented - an undeclared endpoint has no `declaredAt` evidence to merge with, no matter how precisely the stub's path is written. Run the companion link:../shadow-api-detector/README.adoc[Shadow API Detector] against the same `controllerDirs` to check directly: if it reports the endpoint, the stub is correct and the gap is in your OpenAPI documentation, not your stub suite.

| The stub itself has a bug
| The stub file is simply describing a request that doesn't correspond to what you think it does - nothing heuristic about it. A doubled base path (`"/user-account-service/user-account-service/v1/..."`), a copy-pasted URL left over from a different endpoint, a typo in a `urlPathPattern` regex, or a `method` that doesn't match what the endpoint actually accepts, are all real examples found in the wild. The raw stub file is the place to look.

| The stub and the documentation have drifted apart
| A stub written against an earlier shape of the API - a path since renamed, restructured, or removed - describes a request nothing in the current codebase or documentation recognises any more. This isn't a bug in the stub or the scanner; it's a signal that the stub suite needs updating to track the current contract.
|===

[TIP]
====
To list every currently-orphaned stub record, look for a line in `contractHistoryFile` containing both `"stubbedAt":"` and `"declaredAt":null` - each one is a stub whose evidence has never merged with anything, and a candidate for one of the four causes above.
====

=== Scanning stubs created at run time by WireMock's Java DSL

A stub mapping file only exists on disk when a stub is created statically, ahead of time. A stub created programmatically at test run time - via WireMock's fluent Java DSL, e.g. `stubFor(get(urlEqualTo("/orders/1")).willReturn(aResponse().withStatus(200)))` - has no such file, and so is invisible to `stubDirs`. Set `scanMocks = true` to *additionally* scan `stubSourceDirs` for this shape of call: every match contributes the exact same `stubbedAt` stub evidence as a `stubDirs` match, merged into the same run.

[source,groovy]
----
mirageApiDetector {
    scanMocks = true
    stubSourceDirs.from('src/test/java')
}
----

Left unconfigured (the default) while `scanMocks` is `true`, `stubSourceDirs` defaults to the Java directories of *every* source set except `main` - not just the conventional `test` source set, but every additional test suite a project defines too, e.g. `testIntegration`/`testSystem`/`testSystemWireMock` registered via the `jvm-test-suite` plugin's `testing.suites` - since stub-creating code may live in any of them. Most projects need no configuration here at all. Since a project's full set of test suites can be large to re-parse on every run, set `stubSourceDirs` explicitly to restrict the scan to only the directories that actually create stubs, e.g. a dedicated `src/testStubs/java` source set.

The scanner recognises a call to a method named `stubFor(...)` - regardless of its scope, so both the statically-imported `stubFor(...)` and an instance call like `wireMockServer.stubFor(...)` are matched - whose single argument is a fluent chain built from one of WireMock's verb builders (`get`/`post`/`put`/`delete`/`patch`/`head`/`options`/`trace`) applied to one of its URL matchers (`urlEqualTo`/`urlPathEqualTo`/`urlMatching`/`urlPathMatching`/`urlPathTemplate`) with a literal string argument. Any other builder calls chained in between - `.willReturn(...)`, `.atPriority(...)`, `.inScenario(...)`, etc. - are walked through transparently. Matching is by simple method name only, the same "read the code structurally, without the library on the classpath" approach `controllerDirs` and `stubDirs` already use - this scanner needs neither WireMock nor Spring on this plugin's own classpath.

[IMPORTANT]
====
A `stubFor(...)` call whose argument isn't shaped this way - e.g. the mapping builder was assembled in a local variable first, the URL matcher argument is not a string literal, or the matcher is a dynamic one like `anyUrl()` - is silently skipped, the same way a stub mapping file missing a recognised `method`/`url` field is skipped under `stubDirs`.
====

=== Stripping a base path from stub-scanned paths

A WireMock stub mapping records the full request path a client actually sends - including whatever deployment-time context path the server runs under, e.g. `/user-account-service` - while an OpenAPI-declared path never includes one (a server's `paths` are always relative to its own `servers` entry). Left unaccounted for, this mismatch means a stub's path never matches its corresponding OpenAPI operation: the stub is still found, but ends up as an orphaned, unmatched entry instead of being recognised as evidence for the declared endpoint.

Set `basePath` to strip a fixed prefix from every scanned stub path before comparing it:

[source,groovy]
----
mirageApiDetector {
    scanMocks = true
    stubDirs.from('src/test/resources/mappings')
    basePath = '/user-account-service'
}
----

Left unset (the default), the base path is instead read automatically from `rootDocument`'s own first `servers` entry's `url` - e.g. `servers: [{ url: http://localhost:9011/user-account-service }]` yields `/user-account-service` with no configuration needed at all. Set `basePath` explicitly only when the document either declares no `servers` entry or declares the wrong one for this purpose.

== Excluding known-good gaps

Some documented endpoints are never going to be backed by a hand-written `@RestController` - Spring
Boot Actuator's management endpoints (`/actuator/health`, `/actuator/info`, ...) are the canonical
example: they're wired up by the framework's own auto-configuration, not a controller method, so
`detectMirageApis` reports them as mirage APIs even though they're documented on purpose and fully
functional at runtime. Exclusion rules let a project say "this gap is known and fine" without
disabling detection for everything else.

An exclusion rule is a string: a path pattern, optionally prefixed with an HTTP verb -
`"/actuator/health"` (any verb) or `"GET /actuator/**"` (verb-restricted). Path patterns support
Ant-style wildcards: `*` matches exactly one path segment, and a trailing `**` matches any number
of remaining segments. The same rule syntax is used in all three ways to supply rules below, and
rules from every source are combined:

[source,groovy]
----
mirageApiDetector {
    // Rule strings written directly in the build script.
    excludePaths.add('/actuator/health')

    // One or more YAML files of rules - see the format below. Lets a team check in its own
    // reusable exclusion sets (e.g. an org-wide file shared across projects).
    excludeFiles.from('mirage-exclusions.yaml')

    // Bundled, well-known exclusion sets, selected by name.
    excludeWellKnown.add('spring-boot-actuator')
}
----

An exclusion file (`mirage-exclusions.yaml` above) looks like:

[source,yaml]
----
exclusions:
  - "/actuator/health"
  - "GET /actuator/**"
----

Currently bundled well-known sets:

[cols="1,3",options="header"]
|===
| Name                    | Covers
| `spring-boot-actuator`  | `/actuator/**` (any verb) - Spring Boot Actuator's management endpoints
|===

[IMPORTANT]
====
An endpoint matching an exclusion rule is still, factually, a mirage API - declared in the OpenAPI
documentation with no matching `@RestController` implementation. Exclusion changes what happens
with that fact, not the fact itself:

* It is reported under `== Excluded Mirage APIs` instead of `== Mirage APIs`.
* It never fails `failOnMirage`.
* It is never written to `contractHistoryFile` - excluded endpoints are expected to permanently
  miss implementation evidence, so tracking their "progress over time" would just be noise.

When `scanMocks` is `true`, each excluded mirage's *current-run* WireMock stub status is still
shown in `== Excluded Mirage APIs` (`Stubbed: Yes`/`No`/`Not scanned`) even though it's never
persisted to history - consumers relying on a stub for an excluded endpoint still need to know,
this run, whether that stub actually exists.
====

An unrecognised `excludeWellKnown` name, or a malformed rule string (in `excludePaths` or an
exclusion file), fails the build - both are build-script/file mistakes, not a "not built yet"
bootstrapping gap. A configured `excludeFiles` entry that doesn't exist yet only warns, the same
way a missing `controllerDirs`/`stubDirs`/`stubSourceDirs` entry does.

== Configuration

The plugin registers a `mirageApiDetector` extension.

.Groovy DSL
[source,groovy]
----
mirageApiDetector {
    // One or more directories to search recursively for @RestController classes, used to
    // determine which OpenAPI operations are implemented - and thus which are reported as
    // mirage APIs. Always scanned, regardless of scanMocks.
    // Default: src/main/java
    controllerDirs.from('src/main/java')

    // Whether to additionally scan WireMock stub mapping files for stub evidence, alongside
    // controllerDirs' real implementation evidence. See "Additionally scanning WireMock stubs".
    // Default: false
    scanMocks = false

    // One or more directories to search recursively for WireMock stub mapping files, scanned
    // for stub evidence when scanMocks is true.
    // Default: src/test/resources/mappings
    // stubDirs.from('src/test/resources/mappings')

    // One or more directories to search recursively for Java source files that create WireMock
    // stubs programmatically at test run time, scanned for stub evidence when scanMocks is true.
    // See "Scanning stubs created at run time by WireMock's Java DSL".
    // Default: every source set's Java directories except main (every test suite, not just test)
    // stubSourceDirs.from('src/test/java')

    // The base path to strip from every stub-scanned path before comparing it against the
    // OpenAPI documentation, used only when scanMocks is true. Left unset, this is instead read
    // automatically from rootDocument's own first servers entry's url - see "Stripping a base
    // path from stub-scanned paths" above.
    // Default: unset
    // basePath = '/user-account-service'

    // The root OpenAPI document. Required - every other document is expected to be
    // reachable from this one via $ref links relative to it.
    rootDocument = file('src/main/resources/openapi/openapi.yaml')

    // Directory where the OpenAPI documentation is stored, tracked so that a change to
    // any linked document invalidates the task's cached result.
    // Default: rootDocument's own parent directory
    openApiDir = file('src/main/resources/openapi')

    // Whether the build should fail when mirage APIs are found. The report is written
    // either way.
    // Default: false
    failOnMirage = false

    // Directory the AsciiDoc report is written to.
    // Default: layout.buildDirectory.dir('reports/mirage-api-detector')
    reportDir = layout.buildDirectory.dir('reports/mirage-api-detector')

    // Name of the generated AsciiDoc report file.
    // Default: 'mirage-apis.adoc'
    reportFileName = 'mirage-apis.adoc'

    // Version of the system under test whose @RestController classes are scanned, printed near
    // the top of the generated report (see "System Under Test Version" below).
    // Default: the project's own `version`
    // systemUnderTestVersion = 'v1.0.0'

    // Persists a per-endpoint history of when each endpoint first reached declared/implemented/
    // verified status (see "Tracking Contract History" below).
    // Default: false
    trackContractHistory = false

    // NDJSON file the history is read from/written to. Defaults into the project directory
    // (not build/), since it's meant to be committed.
    // Default: file('mirage-api-detector-contract-history.ndjson')
    // contractHistoryFile = file('mirage-api-detector-contract-history.ndjson')

    // When true, contractHistoryFile is written back to disk. Only consulted when
    // trackContractHistory is true; the file is always read either way.
    // Default: same as trackContractHistory
    // updateContractHistory = true

    // Exclusion rule strings, files, and well-known set names - see "Excluding known-good gaps"
    // above. All three are combined; each defaults to empty.
    // excludePaths.add('/actuator/health')
    // excludeFiles.from('mirage-exclusions.yaml')
    // excludeWellKnown.add('spring-boot-actuator')
}
----

`rootDocument` is the only property that must be set - in all but very rare cases (an OpenAPI description split across many top-level documents with no single entry point) the root document is all the plugin needs, since it is expected to link to every other document itself.

== Tasks

[cols="2,1,3",options="header"]
|===
| Task name                    | Group               | Description
| `detectMirageApis`           | verification        | Scans the OpenAPI documentation and reports operations with no matching `@RestController` implementation. Additionally scans WireMock stubs for stub evidence when `scanMocks` is true.
| `migrateContractHistory`     | verification         | One-off, manually-invoked migration of `contractHistoryFile` from the old 9-field format to the current 10-field format. Not run automatically. See "Tracking Contract History" below.
| `updateMirageApiDetectorDSL` | mirage api detector | Adds any `mirageApiDetector { }` properties missing from the project's build file, set to their defaults.
|===

None of these tasks is wired into `check` or `build` automatically. `detectMirageApis` isn't because teams that write their OpenAPI documentation ahead of the implementation - a common "spec-first" workflow - would otherwise see every build fail on endpoints that simply have not been built yet; `migrateContractHistory` is a one-off migration; `updateMirageApiDetectorDSL` is a deliberate, occasional maintenance action.

Running the report explicitly:

[source,shell]
----
./gradlew detectMirageApis
----

To make the task part of every build, wire it into `check` (or `build`) yourself once you're ready to enforce it:

.Groovy DSL
[source,groovy]
----
tasks.named('check') {
    dependsOn 'detectMirageApis'
}
----

.Kotlin DSL
[source,kotlin]
----
tasks.named("check") {
    dependsOn("detectMirageApis")
}
----

== Updating the DSL to the latest properties

`updateMirageApiDetectorDSL` reads the project's own `build.gradle` and adds any `mirageApiDetector { }` properties missing from it, set to the same default value each one's `convention(...)` already resolves to - so setting an added property explicitly afterwards is a no-op.
This lets a project pick up new plugin properties introduced by a later version without going back to the docs and hand-copying them in.

[source,shell]
----
./gradlew updateMirageApiDetectorDSL
----

Only properties with a real default are ever added: `failOnMirage`, `scanMocks`, `reportDir`, `reportFileName`, `systemUnderTestVersion`, `openApiDir`, `trackContractHistory`, `contractHistoryFile`, `updateContractHistory`, `excludePaths`, and `excludeWellKnown`.
`rootDocument` is left out on purpose - it is required, with deliberately no default at all.
`controllerDirs`, `stubDirs`, and `stubSourceDirs` are left out too: their defaults are applied to the task, not the extension, conditionally when still empty (and for the latter two, only when `scanMocks` is true).
`basePath` has no convention at all - it falls back at task time to the root document's own `servers[].url` path.
`excludeFiles` has no default beyond "empty".
There's nothing a literal could usefully add for any of these.
An existing assignment is never touched, even when its value differs from the default - only a *missing* property is ever added.

If the project has no `mirageApiDetector { }` block at all, `updateMirageApiDetectorDSL` leaves it alone by default.
Pass `--generateMirageApiDetectorDSL` to generate a full new block instead, appended to the end of the build file:

[source,shell]
----
./gradlew updateMirageApiDetectorDSL --generateMirageApiDetectorDSL
----

A freshly generated block still needs `rootDocument` configured separately - there's no default it could guess.

Pass `--cleanupMirageApiDetectorDSL` to strip every comment from inside the managed block - both pre-existing ones and any doc comment `updateMirageApiDetectorDSL` itself would otherwise add - leaving only properties:

[source,shell]
----
./gradlew updateMirageApiDetectorDSL --cleanupMirageApiDetectorDSL
----

Run with Gradle's own `--info` flag to see exactly which properties were added and what value each was set to.

Before writing any change, `updateMirageApiDetectorDSL` copies the file exactly as it was to `build.gradle.bak`, alongside it - a plain-file fallback even for a project not using version control (or one that just hasn't committed the file yet).
Only written on a run that actually changes something; each subsequent changing run overwrites the previous backup.

Groovy DSL (`build.gradle`) only - Kotlin DSL (`build.gradle.kts`) isn't supported.

== Progress reporting

Resolving OpenAPI documents and scanning `@RestController` classes can take a while on a large codebase.
The task periodically logs progress at `LIFECYCLE` level so a long-running scan doesn't sit silently until it finishes.

[source,shell]
----
> Task :detectMirageApis
Resolving OpenAPI documents: 12 processed so far
Resolving OpenAPI documents: done, 14 item(s)
Scanning @RestController classes: 150/438 (34%)
Scanning @RestController classes: done, 438 file(s)
Mirage API Detector: scanned 512 described endpoint(s), found 2 mirage API(s). Report → build/reports/mirage-api-detector/mirage-apis.adoc
----

This is plain log output, not an animated progress indicator.
The plugin deliberately avoids Gradle's internal, unsupported console/progress APIs, since their shape can change between Gradle versions and this plugin is published on the Gradle Plugin Portal for consumers on Gradle versions this project doesn't control.
Each line is printed once and never overwritten in place, so it plays back cleanly in CI logs as well as an interactive terminal.

Scanning WireMock stubs, when `scanMocks` is `true`, does not currently report per-file progress the way scanning `@RestController` classes does.

== Tracking Contract History

NOTE: For a complete field-by-field reference to `contractHistoryFile` - its exact JSON schema, fingerprint algorithm, lifecycle semantics, and guidance for building tooling (including a visualization UI) around it - see link:docs/contract-history-file-format.adoc[Contract History File Format].

Setting `trackContractHistory = true` persists, across builds, a history of when each endpoint first reached each stage of its contract lifecycle - declared, implemented, stubbed, verified.
The history is keyed by a fingerprint of the endpoint's own HTTP verb and path, not by which plugin observed it, so Shadow, Mirage, and Doppelganger API Detector can all advance the *same* record when pointed at the same `contractHistoryFile` - useful if you run more than one of these plugins against the same API.
Mirage API Detector always has evidence for the `declared` and `implemented` stages, from the OpenAPI documentation and `controllerDirs` respectively, and additionally for `stubbed`, from `stubDirs` and `stubSourceDirs` merged together, whenever `scanMocks` is `true` - all three can advance from the very same run. It never advances `verifiedAt`, since it has no visibility into contract verification evidence.
The plugin itself has no dependency on git or any other version control system - branch-based control over when to advance the history (e.g. "only on `main`") is entirely a CI concern, expressed through `updateContractHistory`.

[CAUTION]
====
`implementedAt` means **real implementation evidence only** - a WireMock stub match never sets it. This is a deliberate, breaking change from earlier versions of this plugin, which stamped `implementedAt` from *either* a real controller *or* a stub match, with no way to tell which after the fact.

If you have an existing `contractHistoryFile` from before this change (9 fields, no `stubbedAt`), every `detectMirageApis`/`detectShadowApis`/`detectDoppelgangerApis` run against it now fails outright with a clear error, rather than silently reinterpreting its ambiguous `implementedAt` values under the new, narrower meaning. Run `./gradlew migrateContractHistory` once to upgrade the file in place - see <<migrating-legacy-contract-history>> below - or point `contractHistoryFile` at a new location to start a fresh history instead.
====

[cols="1,1,1,3",options="header"]
|===
| Property                | Type    | Default                                                    | Description
| `trackContractHistory`  | Boolean | `false`                                                    | When `true`, loads, advances, and reports from a persisted contract progress history file.
| `contractHistoryFile`   | File    | `mirage-api-detector-contract-history.ndjson` (project directory) | The NDJSON file the history is read from and, when `updateContractHistory` is `true`, written back to.
Deliberately defaults into the project directory, not `build/`, since it's meant to be committed. Only consulted when `trackContractHistory` is `true`.
| `updateContractHistory` | Boolean | same as `trackContractHistory`                             | When `true`, `contractHistoryFile` is written back to disk after being updated with the current run's endpoints.
The file is always *read* when `trackContractHistory` is `true`, regardless of this property - so the generated report always reflects the up-to-date history, whether or not this run persists it. Overridable for the whole build via the `-PmirageApiDetector.updateContractHistory` project property.
|===

`contractHistoryFile` is newline-delimited JSON (NDJSON) - one line per endpoint - sorted by fingerprint so that git diffs stay minimal and stable:

[source,json]
----
{"schemaVersion":1}
{"fingerprint":"a1f3c9d0e21b7f44","verb":"GET","path":"/orders/{id}","declaringClass":"com.example.OrderController","declaredAt":"2026-01-14T09:02:11Z","implementedAt":"2026-02-20T11:15:44Z","stubbedAt":null,"verifiedAt":null,"lastSeenAt":"2026-08-12T07:00:00Z","removedAt":null}
----

The first line is a file-level `{"schemaVersion":N}` marker, always written, giving a future format change something to check against and branch reading logic on. It's purely additive: a file written before this existed simply has no such line, and is read exactly as it always was - the marker is optional on read, never required.

A missing `contractHistoryFile` is treated as an empty history, not an error.
A line that fails to parse (e.g. hand-edited into something invalid) is skipped with a `WARNING`-level `java.util.logging` message identifying its line number; it never fails the build.
A previously persisted record whose fingerprint is no longer present in the current scan is *never deleted* - it's kept exactly as it was, except its `removedAt` is stamped the first time it goes missing.

[IMPORTANT]
====
An endpoint becoming removed is not, by itself, a sign of a problem. It commonly means the endpoint was scoped for an upcoming release and postponed to a later one - a common outcome when an OpenAPI document is written ahead of the code it describes, to plan a release before implementation begins - or that it was considered obsolete and deliberately dropped, or that it had an error in its original definition (a wrong path, a typo, an inconsistent verb) and was replaced by a corrected declaration, which then appears as its own new record rather than a continuation of the old one, since the two have different fingerprints. If an endpoint with the same verb and path reappears in a later run, its `removedAt` is cleared automatically and its progress resumes from where it left off. See "About Removed Endpoints" in the generated report itself for the same explanation, written directly next to the `Removed (no longer seen)` figure it applies to.
====

The generated report reflects the loaded (and possibly just-advanced) history as a `== Progress Over Time` section, once `trackContractHistory` finds at least one record: a human-friendly `Tracked since` timestamp, how many endpoints were declared/implemented/stubbed/verified in the last 7 and 30 days, and how many previously tracked endpoints are no longer seen in the current run.

[#migrating-legacy-contract-history]
=== Migrating legacy contract history (9-field format)

[CAUTION]
====
This is a **one-off, manually-invoked task, not part of the normal build**. It re-scans your project's *current* `controllerDirs` and `stubDirs` to reconstruct, for every legacy record, whether its old `implementedAt` value should now count as real implementation evidence, stub evidence, both, or neither - it has no way to know what those directories looked like back when the timestamp was first recorded, so this is a best-effort reconstruction, not a lossless one. The original file is backed up alongside itself as `<file>.bak` before being overwritten, but **review the migrated file (or its version-controlled diff) before committing the result.**
====

[source,shell]
----
./gradlew migrateContractHistory
----

Every legacy record with a non-null `implementedAt` is reconstructed as follows; records with no `implementedAt` (declared-only) are carried over unchanged:

[cols="1,3",options="header"]
|===
| Current state (re-scanned) | Outcome
| Matches a controller only | `implementedAt` kept; `stubbedAt` stays `null`; `declaringClass` refreshed.
| Matches a stub only | `implementedAt` becomes `null`; `stubbedAt` takes the old value; `declaringClass` becomes `null`.
| Matches both | Both `implementedAt` and `stubbedAt` take the old value; `declaringClass` refreshed from the controller match.
| Matches neither, not already removed | Both `implementedAt` and `stubbedAt` take the old value; `removedAt` is stamped with the migration's own run time.
| Already marked `removedAt` | Both `implementedAt` and `stubbedAt` are cleared to `null` - nothing left to re-verify for an endpoint that's already gone.
|===

See link:docs/contract-history-file-format.adoc#legacy-format[the full format reference's "Migrating from the legacy 9-field format" section] for the complete rationale behind each rule.

Like any other Gradle task, `detectMirageApis` is skipped as `UP-TO-DATE` when none of its declared inputs have changed since the last run.
`contractHistoryFile`'s configured *path* (not its content, which the task itself manages) is one of those tracked inputs, so renaming or relocating it in the build script is, on its own, enough to make the task run again and write history to the newly configured location.
If a run is skipped for some other reason and you need to force it regardless (e.g. after manually editing `contractHistoryFile`), pass `--rerun`:

[source,shell]
----
./gradlew detectMirageApis --rerun
----

== System Under Test Version

Every generated report includes a line just below the title identifying the version of the system under test that was scanned:

[source,asciidoc]
----
System Under Test version: 1.0.0
----

By default, this is the project's own `version`, exactly as set in `build.gradle`/`build.gradle.kts` or a `gradle.properties` file. Set `systemUnderTestVersion` to override it - useful when the `@RestController` classes in `controllerDirs` belong to a different, independently versioned artifact than the one Gradle is building:

[source,groovy]
----
mirageApiDetector {
    systemUnderTestVersion = 'v1.0.0'
}
----

== Report output

After the task runs, an AsciiDoc report is written to the configured `reportDir` (default: `build/reports/mirage-api-detector/mirage-apis.adoc`), listing every mirage API grouped by its OpenAPI tag (or `(untagged)` when the operation declares none), with its HTTP verb, path, and `operationId`.

Every report opens with a preamble explaining what a mirage API is, how it differs from a shadow API and a zombie API, what the risks are, and a link to the https://owasp.org/API-Security/editions/2023/en/0x11-t10/[OWASP API Security Top 10] (specifically https://owasp.org/API-Security/editions/2023/en/0xa9-improper-inventory-management/[API9:2023 Improper Inventory Management]). The preamble text lives in its own bundled resource - `mirage-api-preamble.adoc` in the plugin's `src/main/resources` - so it can be revised independently of the report-writing code.

When `scanMocks` is `true`, a second preamble - `== About Stub Evidence`, from `mirage-api-stub-scanning-preamble.adoc` - follows it, covering the same ground as "Matching a stub's id segment..." and "Interpreting a stub whose evidence never merges..." above directly in the report itself: what the stub scan looks at, what it can and cannot match, shadow stubs, and multiple stub files legitimately covering one endpoint. This is deliberate - a reader looking at a generated report's `Stubbed` figures shouldn't need to go find this README to understand what they mean.

When `failOnMirage` is `true` and at least one mirage API was found, the task fails the build after writing the report, so the report is always available for inspection regardless of build outcome.

== Full example

[source,groovy]
----
plugins {
    id 'java'
    id 'org.springframework.boot' version '<version>'
    id 'com.arc-e-tect.mirage-api-detector' version '<version>'
}

mirageApiDetector {
    rootDocument = file('src/main/resources/openapi/openapi.yaml')
    failOnMirage = true
}

tasks.named('check') {
    dependsOn 'detectMirageApis'
}
----

With this setup, running `./gradlew check` will fail the build - after writing the report - as soon as any operation in `openapi.yaml` (or any document it links to) is found with no matching `@RestController` endpoint.

== Relationship to the Shadow API Detector

This plugin and link:../shadow-api-detector/README.adoc[Shadow API Detector] scan the same two sources of truth - your `@RestController` classes and your OpenAPI documentation - and compare them in opposite directions:

[cols="1,3",options="header"]
|===
| Plugin                | Finds
| Shadow API Detector   | `@RestController` endpoints with no matching OpenAPI operation (implemented, undocumented)
| Mirage API Detector   | OpenAPI operations with no matching `@RestController` endpoint (documented, unimplemented)
|===

Applying both plugins to the same project gives full-coverage drift detection between your code and your contract in either direction. The two plugins share the same DSL shape and configuration property names (mapped one-to-one, e.g. `failOnShadow` / `failOnMirage`) so switching between - or applying both alongside - them requires no relearning.
