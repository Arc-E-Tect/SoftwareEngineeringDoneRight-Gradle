== About Stub Evidence

`scanMocks = true` additionally scans WireMock stub mapping files and/or WireMock's Java DSL for stub
evidence, recorded as `stubbedAt` in contract history and, for an excluded mirage, as this run's
`Stubbed` status below - see this plugin's own README for the full `stubDirs`/`stubSourceDirs`
configuration. This section explains what that scan can and cannot tell you, so its figures are read
correctly.

=== What Gets Scanned

* Every `*.json` file under `stubDirs` is read structurally for its first `method` field and its first
  `url`, `urlPath`, `urlPattern`, or `urlPathPattern` field - deliberately without a JSON parser or the
  WireMock library itself on this plugin's classpath.
* Every WireMock Java DSL `stubFor(...)` call found under `stubSourceDirs` is recognised the same way,
  by simple method-call shape rather than by executing - or even compiling - the code.

=== What It Can and Cannot Match

A stub mapping has no concept of a named path variable the way an OpenAPI document or a
`@RequestMapping` does - only a regular expression or a literal example value for the path it matches.
To compare a stub against a declared/implemented endpoint's `{customerId}`-style path variable at all,
every path segment that *looks like* it stands in for one - a regular-expression id class, or a purely
numeric literal value - is rewritten into a generic `{id}` placeholder before comparison.

This is a deliberately imprecise heuristic, not a certainty. A genuinely literal, non-variable numeric
path segment - a year in a URL, for example - is indistinguishable from an example id by shape alone,
and is rewritten the same way; the reverse is also true, since a WireMock regular expression can
express far more than "any id here" and this scanner never attempts to parse one as such. A stub whose
evidence never appears to merge with its declared/implemented endpoint's record is not necessarily a
scanner error - it may equally be a bug in the stub itself (a mistyped path, a doubled base path, a
verb the endpoint doesn't actually accept), a stub written against an earlier shape of the API that has
since been renamed or removed, or the "shadow stub" case below.

=== Shadow Stubs

A stub can be entirely correct and still never contribute to a `declaredAt`/`implementedAt` record:
stub evidence is only ever compared against what this plugin - and any sibling detector sharing the
same `contractHistoryFile` - has found declared or implemented. If the `@RestController` method behind
a stub genuinely exists but was never added to the OpenAPI documentation, its stub evidence has nothing
to merge with here, no matter how precisely its path is written - a *shadow stub*, the stub-evidence
equivalent of a shadow API. Run the companion Shadow API Detector plugin against the same
`controllerDirs` to check for this directly: if it reports the endpoint, the stub is correct and the
gap is in the OpenAPI documentation, not the stub suite.

=== Multiple Stubs, One Endpoint

Real-world stub suites commonly cover the same request - the same verb and path - with several separate
stub files, one per response scenario: a success case, a validation failure, a not-found case, and so
on. All of them contribute to the *same* tracked endpoint - `stubbedAt` records only the first time any
of them was observed, not one timestamp per file. A project with many more stub files than distinct
stubbed endpoints is expected, not a sign this scan is missing coverage.
