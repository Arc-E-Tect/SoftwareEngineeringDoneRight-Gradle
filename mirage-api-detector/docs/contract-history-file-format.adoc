= Contract History File Format
:toc: left
:toc-title: Contents
:toclevels: 2

This document is a complete, precise reference for the NDJSON file `mirageApiDetector.contractHistoryFile` reads and writes.
It is written for two audiences at once: a human maintainer, and an AI coding assistant (GitHub Copilot, JetBrains Junie, Claude, or similar) that needs to parse this file, reason about its semantics correctly, or build tooling - such as a visualization UI - around it.
Every claim below is backed by the actual source referenced in <<source-of-truth>>; if this document and the source ever disagree, the source is authoritative.

== What this file is

`contractHistoryFile` is a durable, git-committed log of *when each API endpoint first reached each stage of its contract lifecycle*: declared in the OpenAPI documentation, implemented by a `@RestController` method, and verified by a contract-verification source.
It exists to answer questions a single build's report cannot: "how long did it take this endpoint to go from declared to implemented?", "how many endpoints were newly implemented in the last week?", "has this endpoint's implementation quietly disappeared?"

It is only written when `mirageApiDetector.trackContractHistory` is set to `true`; see link:../README.adoc#_tracking_contract_history[the README's "Tracking Contract History" section] for the DSL properties that control it.
The file format itself, and the classes that read/write it, are **shared** across all three Arc-E-Tect detector plugins - Shadow, Mirage, and Doppelganger API Detector - via the `com.arc_e_tect.gradle.detector.core.progress` package in the `api-detector-core` library. Pointing more than one of these plugins at the *same* `contractHistoryFile` lets them merge their partial views of the same endpoints into one unified history; see <<cross-plugin-sharing>>.

[#source-of-truth]
== Source of truth

The format, parsing, and update logic are implemented in the `api-detector-core` library (`SoftwareEngineeringDoneRight-Library` repository), not in this plugin:

[cols="1,3",options="header"]
|===
| Class | Responsibility
| `com.arc_e_tect.gradle.detector.core.progress.ContractProgressRecord` | The record type - one Java `record` per history entry, described field-by-field below.
| `com.arc_e_tect.gradle.detector.core.progress.ContractHistoryStore` | Reads/writes the NDJSON file. Hand-rolled JSON serialization (no library dependency) via a fixed regex per line.
| `com.arc_e_tect.gradle.detector.core.progress.ContractHistoryUpdater` | Computes the *next* history map from the previous one plus the current run's observed endpoints. This is where the "stamped once, never overwritten" and "never deleted, only marked removed" rules actually live.
| `com.arc_e_tect.gradle.detector.core.progress.EndpointFingerprint` | Computes the stable identifier described in <<fingerprint>>.
| `com.arc_e_tect.gradle.detector.core.progress.ContractProgressTableWriter` | Renders the `== Progress Over Time` section of the generated AsciiDoc report *from* this file's loaded content - see <<relationship-to-report>>.
|===

This plugin's own task, `DetectMirageApisTask` (`com.arc_e_tect.gradle.mirage.DetectMirageApisTask`), is a thin caller: it loads the file, calls the updater with whatever endpoints it observed this run, optionally saves the result, and passes it to the report writer. It never touches the file format directly.

== Quick facts

[cols="1,3",options="header"]
|===
| |
| Format | Newline-delimited JSON (NDJSON) - exactly one JSON object per line, no enclosing array, no trailing comma.
| Encoding | UTF-8.
| Line ending | `\n` (written via `PrintWriter.println`, platform default - in practice `\n` on Linux/macOS CI).
| Ordering | Every write sorts all records by `fingerprint` (lexicographic string sort) before writing, so re-saving an unchanged history byte-for-byte reproduces the same file - git diffs stay minimal regardless of which endpoints changed or how they were originally discovered.
| Default location | `mirage-api-detector-contract-history.ndjson`, directly in the project directory (**not** under `build/`) - deliberately, since the file is meant to be committed to version control.
| Configurable via | `mirageApiDetector.contractHistoryFile` (a `RegularFileProperty`).
| Created when | The first time `detectMirageApis` runs with `trackContractHistory = true` and `updateContractHistory` resolving to `true`, and the file does not already exist.
| Missing file | Treated as an empty history - **not** an error. Every currently-observed endpoint is then written as a brand-new record.
| Malformed line | Skipped with a `WARNING`-level `java.util.logging` message identifying the line number. Never fails the build. The rest of the file is still loaded normally.
| Schema version field | **None.** There is no `"version"` or similar marker in the JSON. A tool consuming this file should treat the field set documented below as the only contract, and should not assume forward compatibility with a future field set.
|===

== When it is written

`mirageApiDetector.contractHistoryFile` is:

* *Always read* when `trackContractHistory` is `true`, on every run, regardless of `updateContractHistory`.
* *Written back* only when `trackContractHistory` **and** `updateContractHistory` are both `true`. `updateContractHistory` defaults to the same value as `trackContractHistory`, and is typically driven from CI (e.g. only on `main`) via the `-PmirageApiDetector.updateContractHistory` project property - the plugin itself has no notion of git branches.

A run with `trackContractHistory = true` and `updateContractHistory = false` still loads and reports against the file's current content (so the generated report reflects reality), it simply doesn't persist any changes back to disk.

Because `contractHistoryFile`'s *path* (not its content) is a tracked Gradle task input, renaming or relocating it in the build script is enough on its own to make `detectMirageApis` run again rather than being skipped as `UP-TO-DATE` - see link:../README.adoc#_tracking_contract_history[the README] for the `--rerun` escape hatch if a run is ever skipped for some other reason.

== Record schema

Every line is one JSON object with exactly these eight keys, always present (using JSON `null` for an absent value - never an omitted key):

[cols="1,1,1,4",options="header"]
|===
| Key | JSON type | Nullable | Meaning
| `fingerprint` | string | No | Stable identifier for this endpoint. See <<fingerprint>>. Acts as this record's primary key - the map this file round-trips through is keyed by this field.
| `verb` | string (enum name) | No | The HTTP verb, one of `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`, `TRACE`, `ANY`. `ANY` only ever appears when the endpoint was observed from a Spring `@RequestMapping` that does not restrict its `method` attribute - it never appears for an endpoint sourced purely from OpenAPI, since every OpenAPI operation is described under exactly one concrete verb.
| `path` | string | No | The endpoint's path template, e.g. `/orders/{id}`. Since `fingerprint` is a hash of `verb` + `path`, this value is immutable for a given fingerprint by construction - if either changes, it produces a *different* fingerprint (a new record), never an in-place edit of this field on the existing one.
| `declaringClass` | string | Yes | Fully-qualified name of the `@RestController` class implementing this endpoint. `null` until an implementation is observed. Refreshed on every run that observes an implementation (so a class rename shows up), but is **never** set from verification evidence alone - a test class or contract file supplying `verifiedAt` evidence does not count as "declaring" the implementation class.
| `declaredAt` | string (ISO-8601 instant) or `null` | Yes | The instant this endpoint was *first* observed as declared in the OpenAPI documentation. Stamped once; never overwritten on subsequent runs, even if the endpoint's declaration is later removed and re-added (see `removedAt` below for how disappearance/reappearance is tracked instead).
| `implementedAt` | string (ISO-8601 instant) or `null` | Yes | The instant this endpoint was *first* observed as implemented. Same "stamped once" rule as `declaredAt`. Mirage API Detector populates this from a scanned `@RestController` method by default, or from a matching WireMock stub mapping file when `scanMocks = true` - either way counts as "implementation evidence" for this field; Shadow can also populate it, from its own controller scan only.
| `verifiedAt` | string (ISO-8601 instant) or `null` | Yes | The instant this endpoint was *first* observed as verified by an enabled contract-verification source. **Mirage API Detector never sets this field** - it has no visibility into verification evidence at all, so every record it ever writes has `verifiedAt: null` unless a *different* plugin (Doppelganger) sharing the same file has advanced it. See <<cross-plugin-sharing>>.
| `lastSeenAt` | string (ISO-8601 instant) or `null` | Yes | The instant of the *most recent* run that observed this endpoint in any of the sets it checked. Unlike the three stage timestamps above, this is refreshed forward on *every* run the endpoint is seen in - it is not a "first observed" timestamp. If a record stops being observed, `lastSeenAt` freezes at its last real value while `removedAt` (below) gets set instead.
| `removedAt` | string (ISO-8601 instant) or `null` | Yes | `null` while the endpoint is still present in the most recent run. Set to the instant of the *first* run that failed to observe it anywhere. Records are **never deleted** from the file once written - a removed endpoint's row persists indefinitely with this field set. If the same fingerprint reappears in a later run, `removedAt` reverts to `null` automatically and the record resumes advancing normally.
|===

Instants are serialized via plain `Instant.toString()` - standard ISO-8601 UTC, e.g. `"2026-02-20T11:15:44Z"` (always `Z`/UTC, always second-or-finer precision, never a bare date).

=== JSON Schema

The following JSON Schema (2020-12) validates a single *line* of this file (one JSON object) - it does not describe the file as a whole, since the file is NDJSON, not a single JSON document. A tool ingesting this file should parse it one line at a time and validate each line independently against this schema.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://arc-e-tect.com/schemas/contract-history-record.json",
  "title": "ContractProgressRecord",
  "description": "One line of a shadowApiDetector/mirageApiDetector/doppelgangerApiDetector contractHistoryFile.",
  "type": "object",
  "additionalProperties": false,
  "required": ["fingerprint", "verb", "path", "declaringClass", "declaredAt", "implementedAt", "verifiedAt", "lastSeenAt", "removedAt"],
  "properties": {
    "fingerprint": {
      "type": "string",
      "pattern": "^[0-9a-f]{16}$",
      "description": "First 16 hex characters of SHA-256(\"<VERB> <path>\")."
    },
    "verb": {
      "type": "string",
      "enum": ["GET", "HEAD", "POST", "PUT", "PATCH", "DELETE", "OPTIONS", "TRACE", "ANY"]
    },
    "path": {
      "type": "string",
      "minLength": 1
    },
    "declaringClass": {
      "type": ["string", "null"],
      "description": "Fully-qualified @RestController class name, or null if no implementation has been observed."
    },
    "declaredAt":    { "type": ["string", "null"], "format": "date-time" },
    "implementedAt": { "type": ["string", "null"], "format": "date-time" },
    "verifiedAt":    { "type": ["string", "null"], "format": "date-time" },
    "lastSeenAt":    { "type": ["string", "null"], "format": "date-time" },
    "removedAt":     { "type": ["string", "null"], "format": "date-time" }
  }
}
----

[#fingerprint]
=== How `fingerprint` is computed

`fingerprint` is the first 16 hex characters of the SHA-256 hash of the string `"<VERB> <path>"`, where `<VERB>` is the enum constant name (e.g. `GET`) and `<path>` is the path template with leading/trailing whitespace trimmed - nothing else about the endpoint (its declaring class, its method signature, the line it's declared on, its OpenAPI operation ID) affects it. Two endpoints with the same verb and path are always the same fingerprint, regardless of which plugin or which run discovered them.

Pseudocode, matching `EndpointFingerprint.fingerprint(Described)` exactly:

[source,text]
----
normalized = verb.name() + " " + path.trim()
fingerprint = sha256_hex(normalized)[0:16]
----

A tool that wants to independently verify or recompute a fingerprint from a `verb`/`path` pair read out of a record can do so directly with this formula - no other input is needed, and no other field in this file participates in the hash.

[#cross-plugin-sharing]
== Sharing one file across Shadow, Mirage, and Doppelganger

Because the fingerprint depends only on verb and path, three separate Gradle plugins - each with a fundamentally different view of "what's implemented" or "what's verified" - can safely write into the *same* `contractHistoryFile` and have their observations merge into one coherent per-endpoint timeline, rather than three separate, siloed histories. This is a deliberate design goal, not an accident of the shared library.

[cols="1,1,1,1",options="header"]
|===
| Plugin | Populates `declaredAt` | Populates `implementedAt` | Populates `verifiedAt`
| Shadow API Detector | Yes | Yes | Never
| Mirage API Detector (this plugin) | Yes | Yes (from controllers, or from WireMock stubs when `scanMocks = true`) | Never
| Doppelganger API Detector | Yes | Yes | Yes - the only one of the three
|===

If you are consuming a `contractHistoryFile` and want to know which plugin(s) actually wrote to it, this file format itself carries no such marker - you would need to know that out-of-band (e.g. from the consuming project's own build configuration).

== Example file content

A realistic `contractHistoryFile` after several months of builds, showing every lifecycle state this format can express - an endpoint tracked end-to-end, one still only declared, and one that has disappeared:

[source,json]
----
{"fingerprint":"1a2b3c4d5e6f7089","verb":"GET","path":"/orders","declaringClass":"com.example.OrderController","declaredAt":"2026-01-14T09:02:11Z","implementedAt":"2026-01-15T10:30:00Z","verifiedAt":"2026-02-01T08:00:00Z","lastSeenAt":"2026-08-12T07:00:00Z","removedAt":null}
{"fingerprint":"7be04412aa3390d1","verb":"POST","path":"/orders","declaringClass":null,"declaredAt":"2026-06-01T08:00:00Z","implementedAt":null,"verifiedAt":null,"lastSeenAt":"2026-08-12T07:00:00Z","removedAt":null}
{"fingerprint":"c3d4e5f607182934","verb":"DELETE","path":"/orders/{id}","declaringClass":"com.example.OrderController","declaredAt":"2026-02-20T11:15:44Z","implementedAt":"2026-02-20T11:15:44Z","verifiedAt":null,"lastSeenAt":"2026-05-01T07:00:00Z","removedAt":"2026-05-08T07:00:00Z"}
----

Reading these three lines: the first endpoint went from declared to implemented in one day and was verified about two weeks later, and is still present as of the most recent run. The second is declared but has never been implemented - exactly the endpoint shape this plugin exists to find, a "mirage API" - note `declaredAt` and `implementedAt` land on the same day here only because that endpoint happened to be declared and implemented simultaneously; `implementedAt` is otherwise fully independent of `declaredAt`. The third was declared and implemented on the same day, never verified, and stopped being observed after `2026-05-01` - `removedAt` records when that absence was *first* detected, one run later.

[#relationship-to-report]
== Relationship to the generated report

Every `detectMirageApis` run that has `trackContractHistory = true` and at least one record in the (loaded or just-updated) history renders a `== Progress Over Time` section in `mirage-apis.adoc`, computed *entirely* from this file's content by `ContractProgressTableWriter`:

[cols="1,3",options="header"]
|===
| Report row | Computed as
| `Tracked since` | The minimum non-null value across `declaredAt`, `implementedAt`, `verifiedAt`, `lastSeenAt`, and `removedAt`, over *every* record in the file. Rendered as `yyyy-MM-dd HH:mm:ss 'UTC'`, not the raw ISO-8601 string.
| `Declared in the last 7/30 days` | Count of records whose `declaredAt` falls within `[now - 7 days, now]` / `[now - 30 days, now]`.
| `Implemented in the last 7/30 days` | Same windowed count, over `implementedAt`.
| `Verified in the last 7/30 days` | Same windowed count, over `verifiedAt`. For a `contractHistoryFile` written only by Mirage (never shared with Doppelganger), this is always `0`, correctly - not omitted, since it honestly reflects that no verification evidence has ever been observed.
| `Removed (no longer seen)` | Count of records where `removedAt` is non-null, as of this run.
|===

A tool building richer visualizations than this fixed six-row table has the *entire* underlying file available to compute anything else these summary numbers only sample - see <<visualization-ideas>>.

[#visualization-ideas]
== Building a visualization UI: what's meaningful to show

The report above is a static snapshot. The file itself is a genuine time series - every record carries up to five independent timestamps - so a UI with access to the raw file (or, better, several historical revisions of it from git) can show meaningfully more than the report does. Ideas, roughly in order of implementation effort:

Contract lifecycle timeline (per-endpoint)::
One row per endpoint (labelled by `verb` + `path`, keyed internally by `fingerprint`), one horizontal timeline per row, with markers at `declaredAt`, `implementedAt`, and `verifiedAt` in sequence, and a distinct visual treatment (e.g. greyed out, or a tombstone marker) for rows where `removedAt` is set. This is the single most direct visualization of what the file actually contains.

Coverage funnel::
A simple three-stage funnel (or stacked bar) of *how many* records currently have a non-null `declaredAt`, `implementedAt`, and `verifiedAt` respectively, as of "now" - the single-point-in-time version of what the report's summary table already computes, but rendered as a funnel rather than a table makes the drop-off between stages visually obvious.

Rolling-window trend lines::
The report's "last 7/30 days" counts are single numbers computed against "now". Recompute the *same* windowed count for many historical values of "now" (e.g. once per day, for the last 90 days) to produce a trend line per stage - this shows velocity and whether it's accelerating, flat, or stalling, which the report alone cannot.

Removed/stale watchlist::
A simple table of every record with non-null `removedAt`, sorted by `removedAt` descending, showing how long ago each endpoint disappeared. Useful for catching an accidental removal (a controller method deleted by mistake) versus an intentional deprecation.

Per-controller heatmap::
Group records by `declaringClass` and show, per controller, what fraction of its endpoints have reached each stage. Directly answers "which controller most needs contract-verification work" - something no single report currently surfaces.

Data-age indicator::
Surface `Tracked since` (or its raw components) prominently in any dashboard: a history file only a few days old cannot yet support meaningful 30-day trend claims, and a UI that hides this risks over-interpreting sparse data.

== Parsing this file yourself

Since there is no JSON library dependency in the writer (`ContractHistoryStore` hand-rolls its own line format via a fixed regular expression - see <<source-of-truth>>), a tool that wants strict format compatibility, including exactly how a malformed line is tolerated, should mirror that same parser rather than assuming a generic JSON-lines parser will behave identically on edge cases (e.g. embedded escaped quotes in `declaringClass`). For everyday consumption, however, each line is valid standalone JSON, and any standard JSON parser applied line-by-line will correctly read every well-formed record; the escaping rules only matter for `declaringClass`, the one free-text field (backslash and double-quote are backslash-escaped, nothing else).
