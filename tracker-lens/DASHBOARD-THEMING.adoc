= Theming the Tracker Lens Dashboard

`dashboard.html` is generated by `generateTrackerLensDashboard` and then styled entirely at runtime
by CSS: no template changes are needed to add a new look, only a new lens (see "Writing a lens"
below). A template change is for the dashboard's static structure and wording instead - see
"Writing a template" below. This document is the human-readable form of the same content contract
enforced in code by `ContractRule` and `LensContractValidator`, regardless of which template
produced the HTML - the two are kept in sync by a unit test
(`ContractDocumentationConsistencyTest`) that fails the build if this file falls out of step with
the enum.

== The contract, in a sentence

Every element listed below is *data-bound*: it is rendered from a `LifecycleRecord` or a
`Projection`, so its class name, `data-*` attributes, and position in the document are the stable
surface a lens's CSS can select against, and must not change casually across versions.

Everything else in the generated HTML - headings, captions, labels, disclaimer text - is free text.
It is never part of this contract, may be reworded at any time, and no rule below (and no lens's
CSS) should ever select on it.

== Rules

[cols="1,1,1",options="header"]
|===
|Selector |Cardinality |Meaning

|`.dashboard`
|Exactly one
|The single root element wrapping the entire dashboard.

|`.tracker[data-tracker]`
|At least one
|One section per registered tracker; `data-tracker` holds the tracker's registered id.

|`.metric-card[data-stage]`
|At least one per tracker
|One metric card per stage, within each tracker section; `data-stage` holds the stage name.

|`.metric-card[style*='--percent']`
|Same count as `.metric-card[data-stage]`
|Every metric card also carries the `--percent` custom-property styling hook, so a lens can render it as a bar, ring, or anything else.

|`.projection[data-status]`
|At most one per tracker
|The completion projection, when at least 7 days of history is available; `data-status` holds the confidence tier (`low`/`medium`/`high`). Absent (not present with an empty state) when no projection is available yet.

|`.chart canvas`
|Same count as trackers
|One chart canvas per tracker section, for the Chart.js line chart built by the dashboard's fixed bootstrap script.

|`.stale-items__table`
|At most one
|A single dashboard-wide table of active items that haven't reached their tracker's final stage and have seen no recent activity. Omitted entirely when there are no stale items.

|`.lens-switcher[data-lens-count]`
|At most one
|The lens switcher; `data-lens-count` holds the number of discovered lenses.
|===

== Writing a lens

A lens is a single CSS file. It may style any of the selectors above, plus ordinary elements
(`body`, headings, tables) freely. These custom properties are read by the fixed bootstrap script
at render time, via `getComputedStyle`, to color the Chart.js series - one per stage the tracker's
source defines, currently four for the built-in `API_CONTRACT` source:

- `--dashboard-stage-1`
- `--dashboard-stage-2`
- `--dashboard-stage-3`
- `--dashboard-stage-4`

Define these on `:root` (or `.dashboard`) alongside whatever other custom properties your lens
needs for its own use (the built-in lenses, for example, layer `--dashboard-bg`,
`--dashboard-surface`, `--dashboard-text`, and similar tokens on top of this contract - those are
this lens's own convention, not part of the contract itself).

`--percent` is set inline per metric card by the generator (`style="--percent: 42"`, a number from
0 to 100 with no unit) - a lens reads it with `var(--percent, 0)` to draw a bar, ring, or bar-behind-text
fill; see either built-in lens's `.metric-card` rule for a working example.

See `README.adoc` for how to package a lens (or several) into a publishable style pack, and for the
`-lens` naming recommendation for lens ids.

== Writing a template

A template is a single Mustache file, starting from this plugin's own bundled default
(`dashboard.html.mustache`) and overridden via `trackerLens.template`. Every selector in the table
above must still appear in a template's output with the same cardinality - the data-bound elements
are the contract, regardless of which template rendered them - but everything else (headings,
captions, column labels) is the template's own literal text, free to reword or translate directly
in your copy.

See `README.adoc`'s "Customizing the Dashboard with a Template" section for the full list of
Mustache variables a template can use.

== Shadow / Mirage / Doppelganger / Compliant math

A template built against an `API_CONTRACT` tracker (see `examples/tracker-lens/dashboard-extra-charts`
for a worked example) often wants to talk about the same four states this repository's
`shadow-api-detector`, `mirage-api-detector`, and `doppelganger-api-detector` plugins classify an
endpoint into, rather than the plugin's own raw `declared`/`implemented`/`verified` stage counts.
The four states are a strict partition - every endpoint is in exactly one:

NOTE: This quadrant is built from exactly `declared`/`implemented`/`verified`, unchanged since before the `API_CONTRACT` source gained a fourth stage, `stubbed` (an endpoint backed by a WireMock stub mapping - see `mirage-api-detector`'s `scanMocks` option). `stubbed` is an orthogonal evidence-type dimension, not a fifth named state to fold into this partition - `stubbedCount` is available from `#dashboard-data`/the metric cards like any other stage, but the derivation below neither needs nor accounts for it.

[cols="1,3",options="header"]
|===
| State | Meaning

| Shadow
| Implemented, *not* declared - exists in code but not in the OpenAPI description.

| Mirage
| Declared, *not* implemented - exists in the OpenAPI description but not in code.

| Doppelganger
| Declared *and* implemented, but *not* verified - no test confirms the two still agree.

| Compliant
| Declared, implemented, *and* verified.
|===

Only two independent totals are available from `#dashboard-data` (or the metric cards) for an
`API_CONTRACT` tracker: `declaredCount` and `implementedCount` (each a count of endpoints
independently satisfying that one condition, regardless of the others), plus the tracker's
`totalCount` and `verifiedCount`. `declaredCount` includes every state except Shadow (Shadow is
specifically the *not declared* endpoints); `implementedCount` includes every state except Mirage;
`verifiedCount` includes only Compliant (verified always implies declared and implemented). That's
enough to derive all four state sizes:

[source]
----
overlap        = declaredCount + implementedCount - totalCount   // declared AND implemented
Shadow         = totalCount - declaredCount
Mirage         = totalCount - implementedCount
Compliant      = verifiedCount
Doppelganger   = overlap - Compliant
             = declaredCount + implementedCount - totalCount - verifiedCount
----

`overlap` (declared-and-implemented, regardless of verified) splits entirely between Doppelganger
and Compliant, so `Doppelganger <= overlap` is the only constraint on choosing example or test data
- picking `declaredCount`/`implementedCount`/`totalCount`/`verifiedCount` values first and deriving
the rest from them (rather than picking Shadow/Mirage/Doppelganger/Compliant directly and hoping
they're consistent) is the reliable way to avoid contradicting yourself, since the four states are
not four independent numbers - fixing any two of {declaredCount, implementedCount, totalCount,
verifiedCount} pins the other two.

Worked example, from `dashboard-extra-charts`' own sample data: `declaredCount=16`,
`implementedCount=13`, `totalCount=20`, `verifiedCount=4`.

----
overlap      = 16 + 13 - 20 = 9
Shadow       = 20 - 16      = 4
Mirage       = 20 - 13      = 7
Compliant    = 4
Doppelganger = 9 - 4        = 5

Shadow + Mirage + Doppelganger + Compliant = 4 + 7 + 5 + 4 = 20 = totalCount ✓
----
