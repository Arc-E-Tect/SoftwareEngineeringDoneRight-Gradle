The Tracker Lens plugin generates a themeable, standalone HTML dashboard from Gherkin scenario and API contract lifecycle history.
It reads the NDJSON progress-history files written by `gherkin-to-asciidoc` and the API-detector plugins directly - there is no code dependency on either.
The dashboard's look is fully swappable at runtime through a multi-lens style-pack system: pick from the three built-in lenses, publish your own, or point the plugin at a single custom stylesheet.

== Configuration

The plugin registers the `trackerLens` extension and a `lensStyle` resolvable configuration that external style packs are declared against.
All properties are lazy Gradle properties so they work with configuration cache and multi-module builds.

.Groovy DSL
[source,groovy]
----
trackerLens {
    trackers {
        // At least one tracker must be registered, or the build fails immediately with a clear
        // error naming the missing configuration.
        register("bdd-scenarios") {
            // NDJSON history file(s) to read: one or more individual files, and/or a directory
            // containing them (every *.ndjson file directly within it). A configured entry that
            // doesn't exist yet at task-run time is skipped with a LIFECYCLE warning, not a build
            // failure - the producing plugin may simply not have run yet. The tracker still
            // appears on the dashboard, showing zero progress, once history starts being written.
            historyFiles.from(file('gherkin-progress-history.ndjson'))

            // Which built-in reader knows this file's shape: GHERKIN_SCENARIO or API_CONTRACT
            // (see "Registering Trackers" below for what each one reads and its stages).
            // Fully qualified because Gradle's Groovy DSL does not auto-import a plugin's own
            // classes into the build script - see the TIP below.
            source = com.arc_e_tect.gradle.trackerlens.TrackerSourceKind.GHERKIN_SCENARIO
        }
        register("api-contracts") {
            // Split across one file per detector plugin instead of all three sharing one - see
            // "Splitting a tracker's history across files" below. Records sharing the same id
            // across files are merged into a single item, never rendered as duplicates.
            historyFiles.from(
                file('shadow-api-detector-contract-history.ndjson'),
                file('mirage-api-detector-contract-history.ndjson'),
                file('doppelganger-api-detector-contract-history.ndjson'))
            source = com.arc_e_tect.gradle.trackerlens.TrackerSourceKind.API_CONTRACT
        }
    }

    // Optional single CSS file contributing a lens called "custom-lens" to the switcher, always
    // resolved with the highest precedence for that one id.
    // Default: unset
    // lensStylesheet = file('my-theme.css')

    // Optional Maven coordinate ('group:artifact') restricting the switcher to one external
    // lensStyle pack's lenses, for suppressing a transitively-pulled-in pack you don't want
    // offered. Unrelated to id-collision handling, which never needs this property to resolve.
    // Default: unset (every resolved pack's lenses are offered)
    // preferredLensPack = 'com.example:midnight-theme'

    // Lens id active on first load. When unset: the lens literally called "light-lens" if
    // discovered, otherwise the first lens id in alphabetical order - deterministic, no silent
    // randomness.
    // Default: unset
    // defaultLens = 'dark-lens'

    // Optional Mustache template overriding the bundled default for dashboard.html's static
    // structure and wording - see "Customizing the Dashboard with a Template" below.
    // Default: unset (this plugin's own bundled template)
    // template = file('dashboard-template.html')

    // Optional id of a lens-pack-provided template to render instead - see "Lens packs can ship
    // templates too" below and `listTrackerLensTemplates`. Mutually exclusive with template.
    // Default: unset
    // templateId = 'venn-diagram-view'

    // Where dashboard.html and its lens CSS files are written.
    // Default: layout.buildDirectory.dir('reports/tracker-lens')
    outputDir = layout.buildDirectory.dir('reports/tracker-lens')

    // The dashboard's displayed name, shown in the browser tab title and the page heading.
    // Whatever this is set to is used verbatim, with no " Lens" suffix added.
    // Default: "${project.name} Lens"
    // dashboardName = 'Checkout Service Lens'

    // Version shown alongside the dashboard's name - the same convention as the API-detector
    // plugins' own systemUnderTestVersion.
    // Default: project.version
    // version = '2.3.0'
}

dependencies {
    // External style packs contributing additional lenses (see "Publishing an external style
    // pack" below), resolved against the lensStyle configuration this plugin registers.
    lensStyle('com.example:midnight-theme:1.2.0')
}
----

.Kotlin DSL
[source,kotlin]
----

            historyFiles.from(file("gherkin-progress-history.ndjson"))
            source.set(TrackerSourceKind.GHERKIN_SCENARIO)
        }
        register("api-contracts") {
            historyFiles.from(
                file("shadow-api-detector-contract-history.ndjson"),
                file("mirage-api-detector-contract-history.ndjson"),
                file("doppelganger-api-detector-contract-history.ndjson"))
            source.set(TrackerSourceKind.API_CONTRACT)
        }
    }
    // lensStylesheet.set(file("my-theme.css"))
    // preferredLensPack.set("com.example:midnight-theme")
    // defaultLens.set("dark-lens")
    // template.set(file("dashboard-template.html"))
    // templateId.set("venn-diagram-view")
    outputDir.set(layout.buildDirectory.dir("reports/tracker-lens"))
    // dashboardName.set("Checkout Service Lens")
    // version.set("2.3.0")
}

dependencies {

=== Extension Properties

[cols="1,1,3",options="header"]
|===
| Property | Default | Purpose
| `trackers` | none - at least one required | The registered trackers, each pairing `historyFiles` (one or more files and/or directories) with a `TrackerSourceKind` (see "Registering Trackers" below).
| `lensStylesheet` | unset | Optional single CSS file contributing a `custom-lens` lens with the highest precedence for that id.
| `preferredLensPack` | unset | Optional `group:artifact` coordinate restricting which one external pack's lenses are offered.
| `defaultLens` | unset (`light-lens` if discovered, else alphabetically first) | Lens id active on first load.
| `template` | unset (bundled default) | Optional Mustache template overriding `dashboard.html`'s static structure and wording.
| `templateId` | unset | Optional id of a lens-pack-provided template to render instead (see `listTrackerLensTemplates`). Mutually exclusive with `template`.
| `outputDir` | `layout.buildDirectory.dir('reports/tracker-lens')` | Where `dashboard.html` and its lens CSS files are written.
| `dashboardName` | `"${project.name} Lens"` | The dashboard's displayed name, shown verbatim in the browser tab title and the page heading.
| `version` | `project.version` | Version shown alongside `dashboardName` - the same convention as the API-detector plugins' `systemUnderTestVersion`.
|===

== Registering Trackers

A *tracker* pairs one or more NDJSON history files with the built-in reader that knows their shape.
Three `TrackerSourceKind` values are built in.

[cols="1,2,2",options="header"]
|===
| Kind | Producing plugin | Stages
| `GHERKIN_SCENARIO` | `gherkin-to-asciidoc` (`trackProgress` history file) | `listed`, `defined`, `implemented`
| `API_CONTRACT` | The Shadow/Mirage/Doppelganger API detectors' contract history file(s) | `declared`, `implemented`, `stubbed`, `verified`
| `RESPONSE_COVERAGE` | Doppelganger API Detector's `responseCoverageHistoryFile` (only written when `includeResponseCoverage` is enabled) | `declared`, `covered`
|===

`RESPONSE_COVERAGE` is a true dependency chain (`stagesFormADependencyChain = true`) - a response code can never be `covered` without first being `declared` - unlike `API_CONTRACT`'s four independent conditions. Each record's `group` is the response code's class (`2xx`, `4xx`, `5xx`, ...), derived from its first character; see "The `seriesByGroup` And `matrix` Fields" below for what a template can build from that.

=== Splitting a tracker's history across files

`historyFiles` accepts more than one entry, and any entry may be a directory instead of a file - every `*.ndjson` file directly within it (non-recursive) is picked up.
This matters most for `API_CONTRACT` trackers: Shadow, Mirage, and Doppelganger each have their own `contractHistoryFile` property, and nothing requires a consumer to point all three at the same file.
If they're left pointed at separate files - one written by each detector, from its own partial view of an endpoint's lifecycle - register them all on the same tracker rather than picking just one.

[source,groovy]
----
register("api-contracts") {
    historyFiles.from(
        file('shadow-api-detector-contract-history.ndjson'),
        file('mirage-api-detector-contract-history.ndjson'),
        file('doppelganger-api-detector-contract-history.ndjson'))
    // Equivalently, if all three are written into one directory:
    // historyFiles.from(file('contract-histories'))
    source = com.arc_e_tect.gradle.trackerlens.TrackerSourceKind.API_CONTRACT
}
----

An endpoint (or scenario) observed in more than one file is never rendered as a duplicate: records sharing the same id are merged into a single item, taking the earliest timestamp per stage, the most recent `lastSeenAt`, and treating the item as removed only when every file that mentions it agrees it's gone.

Run the generator with:

[source]
----
./gradlew generateTrackerLensDashboard
----

== Tasks

[cols="2,1,3",options="header"]
|===
| Task name                      | Group        | Description
| `generateTrackerLensDashboard` | reporting    | Reads every registered tracker, resolves the merged lens set, and writes `dashboard.html` plus one CSS file per discovered lens.
| `listTrackerLensStyles`        | reporting    | Lists every lens style available through a lens pack - built-in and external `lensStyle` packs - without generating a dashboard. Scoped to lens packs only: `lensStylesheet`'s single `custom-lens` lens still appears in the real switcher, but never in this listing (it isn't a discoverable, id-namespaced pack).
| `listTrackerLensTemplates`     | reporting    | Lists every dashboard template available through a lens pack - built-in and external `lensStyle` packs - selectable via `templateId`, without generating a dashboard. Scoped to lens packs only, the same way `listTrackerLensStyles` is: a project's own `template` file is a different mechanism entirely and never appears here.
| `initTrackerLens`              | tracker lens | Generates a complete, heavily-commented boilerplate lens CSS file to start a new lens from.
| `bootstrapTrackerLensProject`  | tracker lens | Generates a boilerplate lens-pack project and a sample consumer project, for developing and testing a new lens end-to-end.
| `generateTrackerLensFixture`   | tracker lens | Generates a calibrated pair of `gherkin-progress-history.ndjson` / `api-contract-progress.ndjson` fixture files whose forecast lands a predictable distance in the future.
|===

None of these tasks is wired into `check` or `build` automatically - the dashboard is a report, not a verification gate, and the last two are one-time developer conveniences, not part of the ordinary build.

`listTrackerLensStyles` and `listTrackerLensTemplates` need no tracker to be registered; they only resolve lens packs.

[source]
----
$ ./gradlew listTrackerLensStyles

Tracker Lens styles available (5):

Built-in:
  light-lens
  dark-lens
  high-contrast-lens

midnight-theme:
  midnight
  dark-lens (midnight-theme)
----

The example above shows what a collision looks like in the listing: `midnight-theme` also ships a lens called `dark-lens`, and since the built-in `dark-lens` resolves first, the pack's own gets auto-namespaced to `dark-lens (midnight-theme)` (see "Id collisions across packs" below) - exactly the id that would appear in the switcher.

`listTrackerLensTemplates` works the same way, one directory over - see "Lens packs can ship templates too" below for what it lists.

[source]
----
$ ./gradlew listTrackerLensTemplates

Tracker Lens templates available (2):

Built-in:
  default

venn-view-pack:
  venn-diagram-view

=== Scaffolding a new lens

`initTrackerLens` and `bootstrapTrackerLensProject` generate the boilerplate `LENS_TUTORIAL.adoc` otherwise has you write by hand.

[source]
----
./gradlew initTrackerLens
----

Writes a single, complete lens CSS file - `src/main/resources/META-INF/arc-e-tect/tracker-lens/lenses/my-lens.css` by default - covering every selector the dashboard contract defines, each with an inline comment explaining what it's for, and clearly-fake placeholder colors ready to replace.
Refuses to overwrite a file that's already there, so re-running it never discards work in progress.

[source]
----
./gradlew bootstrapTrackerLensProject
----

Generates the full path from `LENS_TUTORIAL.adoc`: a `tracker-lens-bootstrap/` directory containing a `lens-pack/` project (the same boilerplate lens, wired up to publish to a local Maven repository) and a `sample-project/` project (applying `tracker-lens` itself - pinned to the exact plugin version that generated it - already configured to consume `lens-pack`, with `generateTrackerLensDashboard` wired to depend on `generateTrackerLensFixture`, so its first build - and every build after - generates a calibrated sample fixture dated to today before rendering, rather than reading a static file frozen at scaffold time).
Also refuses to run into a non-empty output directory.

Both tasks need no tracker to be registered - they're available as soon as the plugin is applied, whether or not `trackerLens { trackers { ... } }` has been configured yet.

=== Generating a calibrated fixture

`generateTrackerLensFixture` writes an ordinary `gherkin-progress-history.ndjson` / `api-contract-progress.ndjson` pair - indistinguishable from real usage data, since there is no fixture marker in the NDJSON format itself - calibrated so that `generateTrackerLensDashboard`, pointed at the result, projects a forecast landing approximately `forecastTargetDaysOut` days from `asOf`.
That calibration is verified against the real `ProgressProjector` at generation time, not merely aimed at: the task builds a candidate dataset, runs it through a real projector instance, reads back the resulting forecast date, and adjusts until it lands within a day or two of the target - so the fixture stays correct automatically even if the projector's own lookback/velocity math changes later.

Generating the fixture and rendering the dashboard from it are always two separate Gradle invocations - `generateTrackerLensFixture` runs, writes the files, and exits; some time later, `generateTrackerLensDashboard` runs and reads them back with its own, independently-called "now".
The calibration accounts for that gap: it verifies each candidate not only at `asOf` itself but across a short window of realistic delay after it, so the forecast a real, separate dashboard build renders lands on target too, not just a value computed internally at generation time that nothing ever double-checks against an actual second build.
The practical implication is the same one that makes any snapshot fixture trustworthy: generate it as part of, or immediately before, the build step that consumes it - which is exactly what leaving `asOf` at its default already does, since every run computes a fresh instant and a fresh calibration from scratch.
A fixture that sits unused for a long time before its dashboard is finally built still renders something reasonable, since the underlying data doesn't change, but the tight day-or-two tolerance is only guaranteed for prompt, same-session use; regenerate rather than reuse a stale one.

[source]
----
./gradlew generateTrackerLensFixture
----

Left at its defaults, `asOf` resolves to the current instant at task-execution time, not at configuration time - so re-running the task always regenerates a fixture that's fresh relative to whenever it's run.
Every property is optional; unset ones fall back to the same defaults as the plain Java API below.

[cols="2,3",options="header"]
|===
| Property                | Default
| `asOf`                  | the current instant (ISO-8601 string, e.g. `2026-08-16T00:00:00Z`, to pin a fixed instant)
| `historyStartDaysAgo`   | `60`
| `forecastTargetDaysOut` | `30`
| `workingDaysPerWeek`    | `5` - must stay `5`, matching `ProgressProjector`'s own, currently non-configurable business-days-per-week assumption
| `bddScenarioCount`      | `8`
| `apiContractCount`      | `20`
| `bddScenarioHistoryFile` | `gherkin-progress-history.ndjson` in the project directory
| `apiContractHistoryFile` | `api-contract-progress.ndjson` in the project directory
|===

The default counts produce more than a thin example: the API-contract tracker always includes at least one record in each of the Shadow, Mirage, Stubbed, Doppelganger, and Compliant conditions - with a dedicated record that is simultaneously Compliant and still has a stub, proving stub status is irrelevant once real implementation and verification are both present - and the BDD-scenario tracker always includes a representative at each stage plus a scenario that skipped straight from `listed` to `implemented`.
Both trackers always include at least one removed record, to populate a lens's stale-items table.
Requesting more than the default count scales every category proportionally rather than padding a fixed handful of them.

Point a tracker's `historyFiles` straight at the fixture's own defaults and run both tasks together:

[source,groovy]
----
trackerLens {
    trackers {
        register('bdd-scenarios') {
            historyFiles.from(file('gherkin-progress-history.ndjson'))
            source = com.arc_e_tect.gradle.trackerlens.TrackerSourceKind.GHERKIN_SCENARIO
        }
        register('api-contracts') {
            historyFiles.from(file('api-contract-progress.ndjson'))
            source = com.arc_e_tect.gradle.trackerlens.TrackerSourceKind.API_CONTRACT
        }
    }
}
----

[source,bash]
----
./gradlew generateTrackerLensFixture generateTrackerLensDashboard
----

TIP: `generateTrackerLensDashboard` doesn't currently treat a tracker's history file *contents* as a tracked Gradle input - only that its configuration hasn't changed - so if you've already built the dashboard once and then only regenerate the fixture (its content changes, but the file path doesn't), a subsequent `generateTrackerLensDashboard` run may report `UP-TO-DATE` and keep showing the old data, even chained in the same invocation as above. Add `--rerun-tasks` if the dashboard doesn't seem to reflect a freshly-regenerated fixture.

==== Using it from a test, with no Gradle involvement

The same generator is a plain Java API, usable directly from an automated test - including one written by an AI agent - with no filesystem round trip required:

[source,java]
----
FixtureSpec spec = FixtureSpec.defaults().withAsOf(Instant.parse("2026-08-16T00:00:00Z"));
FixtureResult result = new TrackerLensFixtureGenerator().generate(spec);

// Inspect result.bddScenarios() / result.apiContracts() directly, or write them out:
result.writeTo(new File("gherkin-progress-history.ndjson"), new File("api-contract-progress.ndjson"));
----

Where the Gradle task's `asOf` defaults to the current instant so a prototyping run is always fresh, a test instead pins `asOf` explicitly via `withAsOf(...)`, producing byte-identical output on every run regardless of what day it's run on - both are the same `FixtureSpec` and the same generator, only whether `asOf` is left at its default or overridden differs.

See link:LENS_TUTORIAL.adoc[LENS_TUTORIAL.adoc]'s "Step 3: consume it from a sample project" for this task used to give a brand-new lens something realistic to render against, instead of hand-writing sample history.

== The Lens System

A *lens* is a single CSS file that styles the dashboard.
The dashboard always embeds every discovered lens and renders a runtime switcher: pick a lens from the `<select>`, and the choice is remembered in the browser's `localStorage` for next time.
This is a real, standalone HTML file you open directly in a browser, not a sandboxed preview, so `localStorage` works as expected.

=== Built-in lenses

Three lenses ship with the plugin: `light-lens`, `dark-lens`, and `high-contrast-lens`.
`high-contrast-lens` is aimed at visually impaired users: maximum-contrast black/white with thick borders and bold text, and it deliberately never uses red or green anywhere (including its chart series and projection-status colors) since that distinction is invisible to the most common forms of color blindness - it relies only on blue, yellow, and purple instead.

=== Publishing an external style pack

A style pack is any jar (or, during development, any directory on the classpath) that ships one or more lens CSS files under a fixed resource path.

[source]
----
META-INF/arc-e-tect/tracker-lens/lenses/<lens-id>.css
----

Each file's base name, lower-cased, becomes its lens id.
A pack can contribute as many lenses as it likes; there's nothing special about a "single-lens" pack versus a pack with several.

.Worked example: a minimal external style pack
[source,groovy]
----
// midnight-theme/build.gradle
plugins {
    id 'java-library'
}
----

[source]
----
// midnight-theme/src/main/resources/META-INF/arc-e-tect/tracker-lens/lenses/midnight.css
:root {
    --dashboard-bg: #05050a;
    --dashboard-stage-1: #6a5acd;
    --dashboard-stage-2: #20b2aa;
    --dashboard-stage-3: #daa520;
}
body { background: var(--dashboard-bg); }
----

Publish that jar however you publish any other artifact, then consume it from the project applying `tracker-lens` (see the `dependencies { lensStyle(...) }` block under "Configuration" above).
The pack's lens (`midnight`, in this example) now appears in the switcher alongside the three built-in lenses.

TIP: Naming a built-in-style lens with a `-lens` suffix (as `light-lens` and `dark-lens` do) is a recommendation, not a rule - it makes an accidental id collision with another pack unlikely, but a pack author naming a lens `midnight` or `corporate-brand` is completely valid and nothing enforces the suffix.

=== Lens packs can ship templates too

A lens isn't only a color scheme - it can be a whole alternate *view* over the same tracking data, structuring the dashboard differently rather than just recoloring it. Any style pack (built-in or external, same jar or the same directory a pack's CSS lives in) can ship one or more Mustache dashboard templates under a second fixed resource path, right alongside its `lenses/`:

[source]
----
META-INF/arc-e-tect/tracker-lens/templates/<template-id>.html
----

Each file's base name, lower-cased, becomes its template id - exactly the same convention `lenses/*.css` uses for lens ids, including auto-namespacing on a cross-pack id collision (see link:LENS_TUTORIAL.adoc#id-collisions-across-packs[LENS_TUTORIAL.adoc's "Id collisions across packs"], which applies identically to templates). A consuming project selects one by id via `trackerLens.templateId`:

[source,groovy]
----
trackerLens {
    templateId = 'venn-diagram-view'
}
----

`templateId` and `template` (a project's own local file, see "Customizing the Dashboard with a Template" below) are two different answers to the same question - which template renders `dashboard.html` - so setting both fails the build with a clear error. Setting neither keeps today's default: this plugin's own bundled template, itself just the `default` id under its own built-in pack (see `listTrackerLensTemplates`'s own output above).

A template selected this way still goes through exactly the same rendering and validation `template` does - the same Mustache context (see "Customizing the Dashboard with a Template" below for the full variable reference), the same unconditional `ContractRule` validation as the last step of generation. Nothing about *how* a template is chosen changes what it's allowed to render.

== The Dashboard Content Contract

Every data-bound element on the dashboard - metric cards, the projection block, chart canvases, the stale-items table, the lens switcher - follows a fixed, enforced structural contract: stable class names and `data-*` attributes that a lens's CSS can rely on across versions.
Generation always validates its own output against this contract as the last step of `generateTrackerLensDashboard`, failing the build if the two have drifted apart.

See link:DASHBOARD-THEMING.adoc[DASHBOARD-THEMING.adoc] for the full contract and for how to write a lens against it.

== Customizing the Dashboard with a Template

`generateTrackerLensDashboard` fully overwrites `dashboard.html` on every run - the whole file is regenerated from scratch, every time, so hand-editing its wording (to translate a heading, say) is lost on the next run.
The `template` property solves this the same way `gherkin-to-asciidoc`'s own `template` option does: point it at your own Mustache template, and that template's literal text - not the plugin's - is what gets regenerated on every run.

[source,groovy]
----
trackerLens {
    template = file('dashboard-template.html')
}
----

Everything below - the bundled default's own structure, the Mustache context variables available, `ContractRule` validation - applies identically whether the rendered template comes from `template` (a project's own file) or `templateId` (a lens pack's own template, selected by id - see "Lens packs can ship templates too" above). The two are mutually exclusive ways of answering the same question; nothing about validation or context distinguishes between them.

Start from the bundled default template and edit its static text directly - headings, captions, column labels are all literal text in the template, not a separate variable you look up and override.
The dynamic parts stay as Mustache variables and sections, resolved from the data collected on each run.

[cols="1,3",options="header"]
|===
| Variable | Meaning
| `dashboardName` | The dashboard's displayed name - `trackerLens.dashboardName`, or `"${project.name} Lens"` when unset. Used verbatim; the bundled template puts it in both `<title>` and `<h1>`.
| `version` | `trackerLens.version`, or `project.version` when unset. The bundled template shows it just below `dashboardName`.
| `defaultLensCssFile` | The CSS file name for the lens active on first load; goes in the stylesheet `<link>`'s `href`.
| `lensCount` | Number of discovered lenses.
| `lenses` | List of `{id, selected}` - one `<option>` per lens.
| `trackers` | List of trackers, each `{id, metrics, projection}`.
| `trackers.metrics` | List of `{stage, count, totalCount, percent}` - one per stage. For `GHERKIN_SCENARIO` trackers, `count` is each stage's `stageBreakdown` value (mutually exclusive "currently at this stage", summing to `totalCount`), since a scenario can only reach a later stage by having already passed through every earlier one. For `API_CONTRACT` trackers, `count` stays cumulative "reached at least this stage" (declared/implemented/stubbed/verified are independent conditions, not a dependency chain, so no single item ever has one "current" stage).
| `trackers.projection` | `{status, projectedDate, currentCount, totalCount, velocityPerDay, disclaimer}`, present only when at least 7 days of history is available - use `{{#projection}}...{{/projection}}` / `{{^projection}}...{{/projection}}` to branch on it. `projectedDate` is workday-aware: the remaining-work estimate is treated as business days (Monday-Friday), converted to a calendar date by skipping any weekends it spans - "7 days to go" lands 9 calendar days out, not 7, since nobody's plan should read as expecting weekend work.
| `hasStaleItems` | `true` when at least one tracker has a stale item - gate the whole stale-items table on this, not on `staleItems` directly (a Mustache list section repeats its contents once per item, which would duplicate the table itself).
| `staleItems` | List of `{trackerId, label, group, lastSeen}`.
| `dashboardDataScript` | The fixed `<script type="application/json" id="dashboard-data">...</script>` tag Chart.js reads from. Insert with triple mustaches - `{{{dashboardDataScript}}}` - so it isn't HTML-escaped.
| `bootstrapScript` | The fixed `<script>` that builds the charts and drives the lens switcher. Also needs triple mustaches: `{{{bootstrapScript}}}`.
|===

A custom template's own `<script>` can read the `#dashboard-data` JSON `dashboardDataScript` embeds
directly (`JSON.parse(document.getElementById('dashboard-data').textContent)`) to compute views
neither `trackers.metrics` nor `trackers.projection` covers - see
`examples/tracker-lens/dashboard-extra-charts` for a worked example. Per tracker, it carries:

[cols="1,3",options="header"]
|===
| Field | Meaning
| `stages` | The tracker's canonical stage names, in order.
| `dates` | The chart dates plotted, ascending: starting on the tracker's earliest recorded timestamp, extended 7 days past its latest for trailing breathing room - or further, padded out to 30 days total, whenever the data span alone would otherwise make for a cramped chart. This padding is purely about chart width and can land after the tracker's latest real data point, even after today for a tracker whose history is very recent; see `series`/`breakdownByDate` below for what actually gets plotted there.
| `series` | `{stage: [count, ...]}` - cumulative "reached at least this stage" count per date, aligned index-for-index with `dates`. Two stages can both include the same item, so these do not sum to the tracker's total. A date after the tracker's last real data point (pure `dates` padding - see above) always reads `0` for every stage, never a flat repeat of the last real count: there is nothing in the history to compute a value from, and no forecasting feature (yet) to project one.
| `stageBreakdown` | `{stage: count}` - the number of currently-active items whose *furthest* reached stage is each one, in `stages` order. Unlike `series`, these are mutually exclusive and always sum to the tracker's total - this is the field to read for a pie chart of "what stage is each item at right now", since naively subtracting consecutive `series` values back into exclusive buckets silently misattributes any item whose source skipped a stage (see `GherkinScenarioTrackerSource`'s "jumps straight from listed to implemented" case) - `stageBreakdown` is computed once, server-side, from each item's full history, and is never wrong the way that subtraction can be. Always reflects "now", regardless of any `dates` padding.
| `breakdownByDate` | `[{stage: count}, ...]` - `stageBreakdown`, recomputed as of each date in `dates` instead of "now", aligned index-for-index with it. Each entry has the same mutually-exclusive, sums-to-that-date's-total shape as `stageBreakdown`; reading it is what makes a stacked bar chart or a hover-scrubbable pie possible without re-deriving history from `series` yourself, which has the same skipped-stage pitfall `stageBreakdown` avoids - see `examples/tracker-lens/dashboard-extra-charts` and the `sedr-tracker-lens-pack` external lens for worked examples of both. Same zero-fill rule as `series` applies past the tracker's last real data point - every stage reads `0` there, not a repeat of that last known breakdown.
| `seriesByGroup` | `{group: {stage: [count, ...]}}` - `series`, partitioned by each record's `group` (e.g. `API_CONTRACT`'s `declaringClass`, `RESPONSE_COVERAGE`'s response-code class). Empty (`{}`) when no record in the tracker carries a non-null group. Same per-date shape and zero-fill rule as `series` itself, just one nested level deeper; see "The `seriesByGroup` And `matrix` Fields" below.
| `matrix` | `[{verb, path, responseCode, testCount, covered}, ...]` - a flat, current-state snapshot, non-empty only for `RESPONSE_COVERAGE` trackers. Not derived from any timestamp field above it; see below.
|===

=== The `seriesByGroup` And `matrix` Fields

Both exist to support `RESPONSE_COVERAGE` trackers specifically, though `seriesByGroup` is computed for every tracker kind whose records carry a `group` (today, that includes `API_CONTRACT`'s `declaringClass` too, at no extra cost - a template could chart per-controller coverage trends from it without this plugin needing another field).

`seriesByGroup` is exactly `series`, computed once per distinct group instead of once overall - useful for a per-category stacked or grouped bar chart, e.g. coverage-by-response-code-class over time. `matrix` is fundamentally different: it is not a timestamp-derived view at all, but a raw re-read of the same NDJSON into `(verb, path, responseCode, testCount, covered)` rows, current state only. This exists because `testCount` is a *live gauge* Doppelganger API Detector's `responseCoverageHistoryFile` overwrites on every run - unlike every other field this plugin models, there is no preserved history of it to plot a trend from, so `matrix` can only ever reflect the most recent scan, and only currently-declared rows (a record with a non-null `removedAt` is excluded).

See `examples/tracker-lens/dashboard-extra-charts` for a worked example building a 0-100% stacked coverage-by-class bar chart from `seriesByGroup` and a filterable coverage-depth grid from `matrix`.

Every other value is HTML-escaped automatically by `{{variable}}`, including inside attributes (`data-tracker="{{id}}"` is safe even if an id ever contained a quote).

Your template's output is validated against `ContractRule` exactly like the bundled default's - the same `LensContractValidator`, the same unconditional last step, no special-casing for a user-supplied template versus this plugin's own.
Get a class name or `data-*` attribute wrong and the build fails with the same violation list it would report against a broken built-in template, not a silent, half-working dashboard.
