== Installation

Apply the plugin with `com.arc-e-tect.architecture-validator`.
The examples in this repository consume it through a composite build.
Normal projects can use the Gradle Plugin Portal once the plugin is published.

== Core Workflow

The plugin creates a `testArchitecture` suite.
That suite compiles generated tests from `build/generated/testArchitecture/java`, user tests from `src/testArchitecture/java`, and external rule packs added to `testArchitectureImplementation`.

== Typical Configuration

[source,groovy]
----
plugins {
    id 'java'
    id 'com.arc-e-tect.architecture-validator' version '<version>'
}

architectureValidator {
    basePackage = 'com.example.order'
    failOnViolation = true
    maxAllowedViolations = 0
    ignoreFailures = false

    hexagonalArchitecture {
        inPorts = ['..application.port.in..']
        outPorts = ['..application.port.out..']
        domainModel = ['..application.domain..']
        adapters = ['..adapter..', '..adapters..']
        applicationServices = ['..application.service..']
        commonPackages = ['..application.common..']
    }
}
----

== Reports

Run `./gradlew testArchitecture`.
The suite emits HTML and XML reports under `build/reports/architecture-validator/`.
The HTML report is the fastest way to inspect which rule failed and which classes triggered the failure.

== Generated Tests

The plugin regenerates its built-in tests under `build/generated/testArchitecture/java`.
Those sources are derived artifacts and must not be committed.

If you need to disable the built-in vanilla `HexagonalArchitectureTest`, set `useBuiltInHexagonalRulePack = false`.
With this setting, the built-in validator is skipped while user tests from `src/testArchitecture/java` and external rule-pack tests from `testArchitectureImplementation` still run.

== Built-In Hexagonal Architecture Rules

The plugin provides six built-in architecture rules that enforce key Hexagonal Architecture (also known as Ports & Adapters) principles:

=== Rule: `domain_must_not_depend_on_adapters`
Domain classes (identified by the `domainModel` package pattern) must not depend on adapter classes (identified by the `adapters` package pattern).
This rule ensures that the domain logic remains independent of external technology concerns like databases, web frameworks, or message brokers.

=== Rule: `domain_must_not_depend_on_application_services`
Domain classes must not depend on application service classes (identified by the `applicationServices` package pattern).
This preserves the domain's isolation from orchestration logic and keeps the domain layer focused solely on business rules.

=== Rule: `inbound_ports_reside_in_correct_package`
Inbound port interfaces—identified by names ending with `UseCase` or `InputPort`—must reside in the configured `inPorts` package.
This centralizes the definition of use cases and ensures the application's entry points are clearly located and discoverable.

=== Rule: `outbound_ports_reside_in_correct_package`
Outbound port interfaces—identified by names ending with `Repository` or `OutputPort`—must reside in the configured `outPorts` package.
This centralizes the definition of outbound dependencies (e.g., persistence, external APIs) and makes them easily identifiable.

=== Rule: `adapters_must_not_access_domain_directly`
Adapters must not depend directly on domain classes; they must access the domain only through inbound and outbound ports.
This enforces the Ports & Adapters principle that all external technology interactions are decoupled from domain logic through well-defined interfaces.

=== Rule: `application_services_must_not_depend_on_adapters`
Application services must not depend on adapter classes.
This prevents leakage of infrastructure concerns into the application service layer and ensures that orchestration logic remains independent of specific technology choices.

All six rules are configured with `allowEmptyShould(true)`, meaning they will pass without failure if no classes match the rule criteria (e.g., if the domain layer is empty). When violations occur, the HTML report clearly identifies the offending classes and the rule that triggered the violation.

== Handling Violations

Set `ignoreFailures = true` when the suite should report but not fail the build.
Use `maxAllowedViolations` when teams want a gradual ratchet instead of an immediate zero-violation gate.

== Spring Rule Pack

Spring is treated as the first general rule-pack.
Add it explicitly through `testArchitectureImplementation`.

[source,groovy]
----
dependencies {
    testArchitectureImplementation 'com.arc-e-tect.architecture-validator:architecture-validator-hexagonal-spring-rules:<version>'
}
----

The companion artifact is published to Maven Central and GitHub Packages.

== Multi-Module Builds

Apply the plugin to each Java subproject.
Keep shared conventions in the root build and override patterns only in the modules that differ from the default layout.
