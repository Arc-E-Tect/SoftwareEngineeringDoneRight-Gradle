== Installation

Apply the plugin with `com.arc-e-tect.architecture-validator`.
The examples in this repository consume it through a composite build.
Normal projects can use the Gradle Plugin Portal once the plugin is published.

== Core Workflow

The plugin creates a `testArchitecture` suite.
That suite compiles generated tests from `build/generated/testArchitecture/java`, user tests from `src/testArchitecture/java`, and external rule packs added to `testArchitectureImplementation`.

== Typical Configuration

[source,groovy]
----
plugins {
    id 'java'
    id 'com.arc-e-tect.architecture-validator' version '<version>'
}

architectureValidator {
    basePackage = 'com.example.order'
    failOnViolation = true
    maxAllowedViolations = 0
    ignoreFailures = false
    junitVersion = '6.1.0'

    hexagonalArchitecture {
        inPorts = ['..application.port.inbound..']
        outPorts = ['..application.port.outbound..']
        domainModel = ['..application.domain.model..']
        domainServices = ['..application.domain.service..']
        inboundAdapters = ['..adapter.inbound..', '..adapters.inbound..']
        outboundAdapters = ['..adapter.outbound..', '..adapters.outbound..']
        adapters = ['..adapter..', '..adapters..']
        configurationPackages = ['..configuration..']
        portDataTypePackages = ['..command..', '..query..', '..result..']
        commonPackages = ['..application.common..']
        domainAllowedPackages = ['java.lang..', 'java.time..', 'java.util..', 'java.math..']
        frameworkDenylistPackages = []
        namingConventionsEnabled = true
    }
}
----

`junitVersion` controls the JUnit Jupiter and JUnit Platform Suite versions used by the `testArchitecture` suite.
Use the same major line across all JUnit modules in the project.
Set `junitVersion` to a 5.x version when your dependency management stack pins JUnit 5.
Set `junitVersion` to a 6.x version when your stack is already on JUnit 6.
When `junitVersion` is set to 5.x, the plugin automatically maps JUnit Platform Suite dependencies to 1.x (for example, `5.10.2` maps to `1.10.2`).
When `junitVersion` is set to 6.x, JUnit Platform Suite dependencies use the same 6.x line.

== Version Catalog Example

Use a version catalog to keep the Architecture Validator JUnit line aligned with the rest of the build.

[source,toml]
----
[versions]
architecture-validator-junit-iff = "5.10.2"
----

[source,groovy]
----
architectureValidator {
    junitVersion = libs.versions.architecture.validator.junit.iff.get()
}
----

`inboundAdapters` and `outboundAdapters` define the preferred split package layout.
`adapters` remains useful as an aggregate fallback when a project still keeps all adapters in a shared package.
The default package patterns use `inbound` and `outbound` instead of `in` and `out` to avoid collisions with repository conventions that ignore top-level `out` directories.

If `basePackage` is not set, generated tests resolve it from the `src/main/java` package layout first and then fall back to the project group.
Generated tests never run with an empty root package.
If the plugin cannot resolve a non-empty package root, generation fails fast and requests an explicit `architectureValidator.basePackage` value.

== Reports

Run `./gradlew testArchitecture`.
The suite emits HTML and XML reports under `build/reports/architecture-validator/`.
The HTML report is the fastest way to inspect which rule failed and which classes triggered the failure.
Console output keeps the violation message but suppresses Java stack traces by default to keep failures readable.
Use `--stacktrace` if you need full stack traces for deep debugging.

== Generated Tests

The plugin regenerates its built-in tests under `build/generated/testArchitecture/java`.
Those sources are derived artifacts and must not be committed.

If you need to disable the built-in vanilla `HexagonalArchitectureTest`, set `useBuiltInHexagonalRulePack = false`.
With this setting, the built-in validator is skipped while user tests from `src/testArchitecture/java` and external rule-pack tests from `testArchitectureImplementation` still run.

== Built-In Hexagonal Architecture Rules

The plugin provides ten built-in architecture rules that enforce key Hexagonal Architecture (also known as Ports & Adapters) principles, plus four optional bidirectional naming-convention rules.

=== Rule: `domain_must_only_depend_on_domain_or_jdk_core`
Domain model classes (identified by the `domainModel` package pattern) may only depend on other classes inside the `domainModel` packages themselves or on the configured `domainAllowedPackages` JDK allow-list (`java.lang..`, `java.time..`, `java.util..`, and `java.math..` by default).
This is an allow-list, not a deny-list: it exhaustively keeps the domain free of adapters, domain services, ports, `commonPackages`, and any third-party or framework dependency (Jackson, JPA, Lombok, Spring, …).
The rule also inspects source annotations before compilation, so source-retained annotations such as Lombok's `@Getter` cannot bypass the allow-list.
`domainAllowedPackages` is a plain, user-configurable list — a project may extend it with another JDK package, or shrink it (including removing `java.math..`, or every JDK-core entry) if it wants the domain model held to an even stricter standard.

=== Rule: `domain_services_must_only_depend_on_domain_core_and_ports`
Domain service classes (identified by the `domainServices` package pattern) may depend on the domain model, other domain services, inbound/outbound ports, or `domainAllowedPackages` — but never on adapters or any third-party/framework class.
Source annotations are evaluated against this same allow-list, including annotations with `SOURCE` retention that do not appear in compiled bytecode.
The `domainServices` package covers what the accompanying book calls both "application services" (which orchestrate the flow through the hexagon) and "domain services" (which enforce cross-aggregate business rules): in practice both live in the same package and are held to the same architectural constraints, since the distinction is one of intent/semantics rather than package location.

=== Rule: `ports_must_only_depend_on_domain_ports_or_jdk_core`
Port-freedom: inbound and outbound port interfaces may only depend on the domain model, other ports, or `domainAllowedPackages`.
A port contract may therefore reference concrete Command, Query, and Result DTOs in the configured port packages; these are port contract types, not domain-model types.
A port contract must stay completely framework-free — its *implementation* is free to depend on whatever framework or library it needs, but the port interface itself, and any types it references in its signature, must not.
The same restriction applies to source annotations on port declarations and their members.

=== Source Annotation Findings and Duplicate Violations
The built-in allow-list rules inspect both compiled dependencies through ArchUnit and annotation usages from the Java source. The source analysis exists because annotations with `SOURCE` retention, such as many Lombok annotations, are removed by compilation and cannot be seen by ArchUnit.

An ordinary imported type is checked only by ArchUnit. A source-retained annotation is checked only by source analysis. An annotation with `CLASS` or `RUNTIME` retention may be visible to both mechanisms, depending on how ArchUnit models that annotation as a dependency. In that case, the report can show two violations for the same forbidden annotation: one from the relevant ArchUnit rule and one from `source_annotation_dependencies_must_obey_core_allow_lists`.

This duplication is intentional. Both violations apply the same allow-list policy and identify separate evidence sources: the compiled class and the original Java source. The source finding should not be disabled merely to reduce report counts, because doing so would reopen the gap for source-retained annotations.

=== Rule: `inbound_ports_must_be_interfaces` / `outbound_ports_must_be_interfaces`
Classes in the `inPorts`/`outPorts` packages (excluding `portDataTypePackages`, such as command/query/result DTOs that legitimately live alongside ports) must be interfaces, not concrete classes.

=== Rule: `inbound_ports_reside_in_correct_package`
Inbound port interfaces—identified by names ending with `UseCase` or `InputPort`—must reside in the configured `inPorts` package.
This centralizes the definition of use cases and ensures the application's entry points are clearly located and discoverable.
There is no equivalent built-in rule for outbound ports: real projects use inconsistent suffixes for outbound ports (`Repository`, `Gateway`, `Publisher`, `Generator`, and others all coexist legitimately depending on what the port abstracts), so no single suffix convention can be enforced without creating loopholes. Projects wanting to enforce their own outbound naming convention should add a custom `testArchitecture` test or their own rule pack.

=== Rule: `core_layer_must_not_depend_on_adapters`
The domain model, domain services, and ports are outer-layer-unaware; none of them may depend on any class in the aggregate adapter package set (`adapters`, `inboundAdapters`, `outboundAdapters` combined).

=== Rule: `adapters_must_not_depend_on_domain_services_directly`
Adapters must not depend directly on domain service implementation classes; they must go through a port instead.
This enforces the entry-path rule of Hexagonal Architecture: adapters should invoke port interfaces instead of binding directly to service implementations.

=== Rule: `only_configuration_may_depend_on_domain_service_implementations`
Only classes in the `configurationPackages` package may depend directly on a concrete domain service implementation class; every other caller — including adapters — must go through a port.
This is the counterpart to `adapters_must_not_depend_on_domain_services_directly`: it generalizes the same principle to any non-configuration, non-domain-service caller, not just adapters.

=== Rule: `core_application_layer_must_have_no_denylisted_dependencies`
The domain model, domain services, and ports must not depend on any package configured in `frameworkDenylistPackages` (empty by default). Set this property to enforce a project-specific framework-freedom policy in the core application layer, for example `['org.springframework..', 'jakarta.persistence..']`.

=== Optional naming-convention rules (`namingConventionsEnabled = true`)
When enabled, four additional rules enforce *strict, bidirectional* naming for inbound ports and domain services — a class with the conventional suffix must live in the matching package, and a class in that package must carry the conventional suffix, with no loopholes in either direction:

* `inbound_ports_should_have_conventional_suffix` and `conventionally_named_inbound_ports_reside_in_inbound_port_package` (suffix `UseCase` or `InputPort`)
* `domain_services_should_have_conventional_suffix` and `conventionally_named_domain_services_reside_in_domain_service_package` (suffix `Service` or `Policy`)

All rules are configured with `allowEmptyShould(true)`, meaning they will pass without failure if no classes match the rule criteria (e.g., if the domain layer is empty). When violations occur, the HTML report clearly identifies the offending classes and the rule that triggered the violation.

`domainModel`, `domainServices`, `inPorts`, `outPorts`, and `adapters` (together with `inboundAdapters`/`outboundAdapters`) are expected to be mutually exclusive package patterns.
A pattern that nests one layer's packages inside another's (for example, a `domainServices` pattern that is itself a sub-package of `domainModel`) makes classes match both layers simultaneously and corrupts every rule that reads those two lists — keep the defaults, or any overrides, disjoint.

== Handling Violations

Set `ignoreFailures = true` when the suite should report but not fail the build.
Use `maxAllowedViolations` when teams want a gradual ratchet instead of an immediate zero-violation gate.

== Spring Rule Pack

Spring is treated as the first general rule-pack.
Add it explicitly through `testArchitectureImplementation`.

[source,groovy]
----
dependencies {
    testArchitectureImplementation 'com.arc-e-tect.architecture-validator:architecture-validator-hexagonal-spring-rules:<version>'
}
----

The companion artifact is published to Maven Central and GitHub Packages.

== Multi-Module Builds

Apply the plugin to each Java subproject.
Keep shared conventions in the root build and override patterns only in the modules that differ from the default layout.

== Canonical Acceptance Example

The focused regression example lives at `examples/architecture-validator/hexagonal-violations`.
It should fail with exactly six intended rule names:

- `domain_must_only_depend_on_domain_or_jdk_core`
- `domain_services_must_only_depend_on_domain_core_and_ports`
- `inbound_ports_reside_in_correct_package`
- `core_layer_must_not_depend_on_adapters`
- `adapters_must_not_depend_on_domain_services_directly`
- `only_configuration_may_depend_on_domain_service_implementations`
