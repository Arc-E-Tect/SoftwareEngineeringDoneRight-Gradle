The Architecture Validator plugin generates and runs ArchUnit-based architecture tests from a small Gradle DSL.
It focuses on Hexagonal Architecture by default and can also attach external rule packs, including the companion Spring rule pack maintained in the SoftwareEngineeringDoneRight-Library repository.

This plugin is now maintained as a standalone Gradle project under `architecture-validator`.
The Spring companion rules are published from the separate `spring-rules` project in SoftwareEngineeringDoneRight-Library.

[TIP]
====
Run `./gradlew updateArchitectureValidatorDSL` any time to add any missing `architectureValidator { }` properties, set to the same defaults their own `convention(...)` calls already resolve to - always a no-op.
Add `--generateArchitectureValidatorDSL` to generate a whole new `architectureValidator { }` block when the project doesn't have one yet, or `--cleanupArchitectureValidatorDSL` to strip comments from the managed block.
See "Updating the DSL to the latest properties" below for the full details.
====

== What the Plugin Adds

The plugin creates a `testArchitecture` JVM test suite.
It generates the built-in `HexagonalArchitectureTest` class under `build/generated/testArchitecture/java`.
It compiles user-provided tests from `src/testArchitecture/java` by default.
It can discover external rule packs on the `testArchitectureImplementation` classpath and generate a bridge suite that runs those rule-pack tests through JUnit Platform.

== Configuration

The plugin registers the `architectureValidator` extension.
All properties are lazy Gradle properties so they work with configuration cache and multi-module builds.

[source,groovy]
----
architectureValidator {
    basePackage = 'com.example.architecture'
    testDirectory = file('src/testArchitecture/java')

    failOnViolation = true
    maxAllowedViolations = 0
    ignoreFailures = false
    rulesDisabled = ['DomainIsolationTest.domainServicesShouldNotCarrySpringStereotypes']
    failOnDuplicateRules = false
    useBuiltInHexagonalRulePack = true
    junitVersion = '6.1.0'

    hexagonalArchitecture {
        inPorts = ['..application.port.inbound..']
        outPorts = ['..application.port.outbound..']
        domainModel = ['..application.domain.model..']
        domainServices = ['..application.domain.service..']
        inboundAdapters = ['..adapter.inbound..', '..adapters.inbound..']
        outboundAdapters = ['..adapter.outbound..', '..adapters.outbound..']
        adapters = ['..adapter..', '..adapters..']
        configurationPackages = ['..configuration..']
        portDataTypePackages = ['..command..', '..query..', '..result..']
        commonPackages = ['..application.common..']
        domainAllowedPackages = ['java.lang..', 'java.time..', 'java.util..', 'java.math..']
        frameworkDenylistPackages = []
        inboundAdapterDenylistPackages = []
        namingConventionsEnabled = true
    }
}
----

`inboundAdapters` and `outboundAdapters` define the preferred split package layout.
`adapters` remains available as an aggregate fallback for legacy projects that still keep adapters together.
The default package patterns use `inbound` and `outbound` names to avoid collisions with repository conventions that ignore top-level `out` directories.

=== Extension Properties

[cols="1,1,3",options="header"]
|===
| Property | Default | Purpose
| `basePackage` | inferred from `src/main/java` package layout, then project group | Package root imported by generated tests and companion rule packs. Generated tests never use an empty package root.
| `testDirectory` | `src/testArchitecture/java` | Location for user-supplied ArchUnit tests.
| `failOnViolation` | `true` | Enables the post-test violation threshold check.
| `maxAllowedViolations` | `0` | Maximum number of failing architecture rule tests before the build fails.
| `ignoreFailures` | `false` | Keeps the build green even when architecture tests fail.
| `rulesDisabled` | `[]` | Comma-joined rule identifiers that built-in or external rule packs may choose to skip at runtime.
| `failOnDuplicateRules` | `false` | Turns duplicate rule detection across local and external rule packs into a build failure instead of a warning.
| `useBuiltInHexagonalRulePack` | `true` | Enables generation and execution of the built-in `HexagonalArchitectureTest`.
| `junitVersion` | `6.1.0` | Selects the JUnit Jupiter and JUnit Platform Suite version line used by the generated `testArchitecture` suite. Use a 5.x value to align with a JUnit 5 stack; the plugin maps JUnit Platform Suite dependencies to the matching 1.x or 6.x line automatically.
|===

If no non-empty package root can be resolved for generated tests, the plugin fails fast and asks you to configure `architectureValidator.basePackage` explicitly.

To run only external/user rule packs and disable the built-in vanilla validator, set `useBuiltInHexagonalRulePack = false`.

=== `hexagonalArchitecture` Block Properties

The `hexagonalArchitecture { }` block nested inside `architectureValidator` configures the package patterns and toggles used by the built-in Hexagonal Architecture rule set.

[cols="1,1,3",options="header"]
|===
| Property | Default | Purpose
| `inPorts` | `['..application.port.inbound..']` | Package pattern(s) identifying inbound port (use case) interfaces, checked by the `inbound_ports_reside_in_correct_package` rule and, when naming conventions are enabled, by `conventionally_named_inbound_ports_reside_in_inbound_port_package`.
| `outPorts` | `['..application.port.outbound..']` | Package pattern(s) identifying outbound port (repository/gateway) interfaces. There is no built-in outbound naming-convention rule — real outbound ports use inconsistent suffixes (`Repository`, `Gateway`, `Publisher`, `Generator`, ...), so consumers who want a suffix rule for their own project should add it via a custom `testArchitecture` test or their own rule pack.
| `domainModel` | `['..application.domain.model..']` | Package pattern(s) identifying pure domain classes, which may only depend on themselves or on `domainAllowedPackages` — never ports, domain services, or adapters. Checked by `domain_must_only_depend_on_domain_or_jdk_core`.
| `domainServices` | `['..application.domain.service..']` | Package pattern(s) identifying domain service classes (this covers both what's sometimes called "application services" and "domain services" — the book distinguishes them by role, but they live in the same package and are checked by the same rules). May depend on the domain model, other domain services, inbound/outbound ports, and `domainAllowedPackages`, but never on adapters. Checked by `domain_services_must_only_depend_on_domain_core_and_ports`.
| `adapters` | `['..adapter..', '..adapters..']` | Aggregate adapter package pattern(s), merged with `inboundAdapters`/`outboundAdapters` for the rules that must recognize every adapter class; useful as a fallback for projects that keep adapters together instead of splitting them.
| `inboundAdapters` | `['..adapter.inbound..', '..adapters.inbound..']` | Package pattern(s) identifying inbound adapters, merged into the aggregate adapter pattern set used by `core_layer_must_not_depend_on_adapters` and `adapters_must_not_depend_on_domain_services_directly`.
| `outboundAdapters` | `['..adapter.outbound..', '..adapters.outbound..']` | Package pattern(s) identifying outbound adapters, merged the same way as `inboundAdapters`. Outbound adapters are allowed to implement outbound ports using domain objects.
| `configurationPackages` | `['..configuration..']` | Package pattern(s) identifying the wiring/configuration layer — the only layer allowed to depend on concrete domain-service implementation classes directly, checked by `only_configuration_may_depend_on_domain_service_implementations`.
| `portDataTypePackages` | `['..command..', '..query..', '..result..']` | Package pattern(s) for port-adjacent data-carrier types (commands, queries, results, and similar DTOs) that live alongside ports but are excluded from the `inbound_ports_must_be_interfaces`/`outbound_ports_must_be_interfaces` interface checks, since they are legitimately concrete classes.
| `commonPackages` | `['..application.common..']` | Package pattern(s) for shared/common classes; not referenced by the built-in rule set directly, but exposed via the `architectureValidator.commonPackages` system property for external rule packs to use.
| `domainAllowedPackages` | `['java.lang..', 'java.time..', 'java.util..', 'java.math..']` | JDK package pattern(s) the domain model, domain services, and ports may depend on in addition to their own layer. Fully user-configurable via the DSL — including dropping `java.math..`, or any other entry, entirely, since the property is a plain `ListProperty<String>` with no hard-coded fallback.
| `frameworkDenylistPackages` | `[]` | Package pattern(s) that the domain model, domain services, and ports must never depend on, checked by `core_application_layer_must_have_no_denylisted_dependencies`. Empty by default; set it (for example, to `['org.springframework..', 'jakarta.persistence..']`) to enforce framework-freedom in the core application layer.
| `inboundAdapterDenylistPackages` | `[]` | Additional package pattern(s) inbound adapters must never depend on. The `inbound_adapters_must_access_application_through_inbound_ports` rule already blocks direct dependencies on the domain model, outbound ports, outbound adapters, and configuration; this property extends that deny-list without broadly restricting framework or third-party dependencies.
| `namingConventionsEnabled` | `false` | Generates additional, strictly bidirectional naming-convention `@ArchTest` rules for inbound ports (`UseCase`/`InputPort` suffix) and domain services (`Service`/`Policy` suffix) — a class with the conventional suffix must live in the expected package, *and* a class in the expected package must have the conventional suffix. Also exposes an `architectureValidator.namingConventions.enabled` system property so external rule packs, such as the Spring companion rule pack, can opt into their own naming checks.
|===

Port-freedom is enforced independently of naming: `ports_must_only_depend_on_domain_or_jdk_core` keeps inbound and outbound port contracts free of framework dependencies regardless of how the port implementation itself is wired — only the implementation, never the port interface, may depend on a framework.

`domainModel`, `domainServices`, `inPorts`, `outPorts`, and `adapters` (together with `inboundAdapters`/`outboundAdapters`) are expected to be mutually exclusive package patterns.
A pattern that nests one layer's packages inside another's (for example, a `domainServices` pattern that is itself a sub-package of `domainModel`) makes classes match both layers simultaneously and corrupts every rule that reads those two lists — keep the defaults, or any overrides, disjoint.

== Built-in Vanilla Hexagonal Rules

The generated `HexagonalArchitectureTest` provides the built-in vanilla Hexagonal rule set for the plugin.
It enforces ten `@ArchTest` rules, plus four optional bidirectional naming-convention rules when `namingConventionsEnabled = true`.

[cols="1,3",options="header"]
|===
| Rule | Checks
| `domain_must_only_depend_on_domain_or_jdk_core` | The domain model depends only on itself or the configured JDK allow-list — never ports, domain services, adapters, or any third-party/framework class.
| `domain_services_must_only_depend_on_domain_core_and_ports` | Domain services depend only on the domain model, other domain services, inbound/outbound ports, or the JDK allow-list — never adapters or any third-party/framework class.
| `ports_must_only_depend_on_domain_or_jdk_core` | Port-freedom: inbound and outbound port contracts depend only on the domain model, other ports, or the JDK allow-list — a port interface stays framework-free even though its implementation need not.
| `inbound_ports_must_be_interfaces` | Inbound port contracts are interfaces, not concrete classes (port data-carrier types such as commands/queries/results are excluded).
| `outbound_ports_must_be_interfaces` | Outbound port contracts are interfaces, not concrete classes (same data-carrier exclusion).
| `inbound_ports_reside_in_correct_package` | Classes conventionally named as inbound ports (`UseCase`/`InputPort` suffix) reside in the inbound ports package.
| `core_layer_must_not_depend_on_adapters` | The domain model, domain services, and ports are outer-layer-unaware; none of them may depend on adapter classes.
| `adapters_must_not_depend_on_domain_services_directly` | Adapters reach the application core only through ports — never by depending directly on a domain service implementation.
| `inbound_adapters_must_access_application_through_inbound_ports` | Inbound adapters must not depend directly on the domain model, outbound ports, outbound adapters, configuration, or `inboundAdapterDenylistPackages`. They enter the application through inbound ports and freely use adapter-local, framework, and third-party types.
| `only_configuration_may_depend_on_domain_service_implementations` | Concrete domain service implementations are only referenced from the configuration layer wiring up their beans — every other caller must go through a port.
| `core_application_layer_must_have_no_denylisted_dependencies` | The domain model, domain services, and ports are free of any package configured in `frameworkDenylistPackages` (empty by default).
|===

There is deliberately no built-in outbound-port naming-convention rule: real projects use inconsistent suffixes for outbound ports (`Repository`, `Gateway`, `Publisher`, `Generator`, and others all coexist legitimately), so no single suffix rule can apply without loopholes. Projects that want to enforce their own convention should add it as a custom `testArchitecture` test or their own rule pack.

When `namingConventionsEnabled = true`, four additional rules apply strict, bidirectional naming for inbound ports and domain services — a conventionally-suffixed class must live in the matching package, and a class in that package must carry the conventional suffix:

* `inbound_ports_should_have_conventional_suffix` / `conventionally_named_inbound_ports_reside_in_inbound_port_package`
* `domain_services_should_have_conventional_suffix` / `conventionally_named_domain_services_reside_in_domain_service_package`

== Companion Spring Rule Pack

The companion spring-rules project publishes `architecture-validator-hexagonal-spring-rules` as a separate JAR.
The artifact is available from Maven Central and GitHub Packages.
The rule pack focuses on genuinely Spring-specific checks (stereotype annotations, controller/repository wiring) — framework-agnostic checks such as dependency direction, port contracts, port-freedom, and bidirectional naming now live in the built-in rule set above, so the two rule packs no longer overlap.

Spring is treated as the first general rule-pack.
It is enabled the same way as any other external rule-pack: add it to `testArchitectureImplementation`.
No plugin toggle is required.

[source,groovy]
----
architectureValidator {
    rulesDisabled = ['DomainIsolationTest.domainServicesShouldNotCarrySpringStereotypes']
    hexagonalArchitecture {
        namingConventionsEnabled = true
    }
}

dependencies {
    testArchitectureImplementation 'com.arc-e-tect.architecture-validator:architecture-validator-hexagonal-spring-rules:<version>'
}
----

See `examples/architecture-validator/single-module-spring` for a runnable example that exercises
both properties against the companion rule pack and shows the resulting skipped/failed rules in
the report.

== Library-Based Rule Packs

Any JAR added to `testArchitectureImplementation` can contribute rule-pack tests.
The plugin scans dependency directories and JARs for classes whose names end with `Test`.
It then generates an `ExternalRulePackSuite` class that selects the discovered packages through JUnit Platform.

[source,groovy]
----
dependencies {
    testArchitectureImplementation 'com.org.ea:layer-validator:1.0.0'
}
----

If two rule packs contribute the same simple test class name, the plugin logs a warning by default.
Set `failOnDuplicateRules = true` if duplicate rules should fail the build.

== Canonical Acceptance Example

The repository contains a deliberately broken example at `examples/architecture-validator/hexagonal-violations`.
It is the canonical acceptance example for the plugin.
Running it should fail with exactly six intended violations:

- `domain_must_only_depend_on_domain_or_jdk_core`
- `domain_services_must_only_depend_on_domain_core_and_ports`
- `inbound_ports_reside_in_correct_package`
- `core_layer_must_not_depend_on_adapters`
- `adapters_must_not_depend_on_domain_services_directly`
- `only_configuration_may_depend_on_domain_service_implementations`

Adapters are allowed to implement outbound ports whose signatures use domain objects.
The built-in rule set distinguishes inbound adapters from outbound adapters for this reason.

[source,bash]
----
cd examples/architecture-validator/hexagonal-violations
./gradlew clean testArchitecture
----

[source,bash]
----
./gradlew testArchitecture

== Updating the DSL to the latest properties

`updateArchitectureValidatorDSL` reads the project's own `build.gradle` and adds any `architectureValidator { }` properties missing from it, set to the same default value each one's `convention(...)` already resolves to - so setting an added property explicitly afterwards is a no-op.
This lets a project pick up new plugin properties introduced by a later version without going back to the docs and hand-copying them in.

[source,shell]
----
./gradlew updateArchitectureValidatorDSL
----

Every top-level property except `junitVersion` is eligible: `testDirectory`, `basePackage`, `failOnViolation`, `maxAllowedViolations`, `ignoreFailures`, `failOnDuplicateRules`, `useBuiltInHexagonalRulePack`, and `rulesDisabled`.
Unlike every other plugin in this repository, `architectureValidator`'s extension sets every one of its own defaults in its own constructor rather than in the plugin's `apply()` method - `basePackage` is the one exception, additionally overridden with a lazy default derived from `project.group`.
An existing assignment is never touched, even when its value differs from the default - only a *missing* property is ever added.

`junitVersion` is excluded on purpose: alongside the normal `junitVersion = '...'` assignment form, the extension also exposes a plain `setJunitVersion(String)` method, used by a project pulling the version from a catalog (e.g. `setJunitVersion(libs.versions.junit.get())`).
`updateArchitectureValidatorDSL` only recognizes the `name = value` assignment form as "already configured" - it would not recognize the method-call form, and would append a second, conflicting `junitVersion = '6.1.0'` line that executes after the real one and silently overrides it.

`hexagonalArchitecture { }` is a nested block, not a top-level property, and is handled differently: it's only ever added as part of a whole new `architectureValidator { }` block generated from scratch (see `--generateArchitectureValidatorDSL` below), never added to or completed inside an *existing* block - even a block with no `hexagonalArchitecture { }` sub-block at all, or one missing some of its own thirteen properties.
This is a real limitation of not having true nested-block support yet, but a safe one: `hexagonalArchitecture`'s own thirteen properties already have real defaults via their own `convention(...)`, regardless of whether the DSL text shows them, so an absent or partial sub-block is still behaviorally a no-op either way.

If the project has no `architectureValidator { }` block at all, `updateArchitectureValidatorDSL` leaves it alone by default.
Pass `--generateArchitectureValidatorDSL` to generate a full new block instead, appended to the end of the build file - including a `hexagonalArchitecture { }` sub-block set to its own real default values (not a commented-out example, since those defaults already apply either way):

[source,shell]
----
./gradlew updateArchitectureValidatorDSL --generateArchitectureValidatorDSL
----

Pass `--cleanupArchitectureValidatorDSL` to strip every comment from inside the managed block - both pre-existing ones and any doc comment `updateArchitectureValidatorDSL` itself would otherwise add - leaving only properties.
Combined with `--generateArchitectureValidatorDSL`, this also skips the `hexagonalArchitecture { }` stub's contents entirely, leaving an empty sub-block - still behaviorally identical, just less self-documenting:

[source,shell]
----
./gradlew updateArchitectureValidatorDSL --cleanupArchitectureValidatorDSL
----

Run with Gradle's own `--info` flag to see exactly which properties were added and what value each was set to.

Before writing any change, `updateArchitectureValidatorDSL` copies the file exactly as it was to `build.gradle.bak`, alongside it - a plain-file fallback even for a project not using version control (or one that just hasn't committed the file yet).
Only written on a run that actually changes something; each subsequent changing run overwrites the previous backup.

Groovy DSL (`build.gradle`) only - Kotlin DSL (`build.gradle.kts`) isn't supported.

== Multi-Module Usage

The plugin is designed to be applied per module.
A root build can supply shared defaults and each subproject can override package patterns locally.

[source,groovy]
----
subprojects {
    apply plugin: 'java'
    apply plugin: 'com.arc-e-tect.architecture-validator'

    architectureValidator {
        basePackage = 'com.example.multi'
        hexagonalArchitecture {
            inPorts = ['..application.port.inbound..']
            outPorts = ['..application.port.outbound..']
        }
    }
}
----
