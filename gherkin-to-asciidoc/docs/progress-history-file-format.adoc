= Progress History File Format
:toc: left
:toc-title: Contents
:toclevels: 2

This document is a complete, precise reference for the NDJSON file `gherkinToAsciidoc.progressHistoryFile` reads and writes.
It is written for two audiences at once: a human maintainer, and an AI coding assistant (GitHub Copilot, JetBrains Junie, Claude, or similar) that needs to parse this file, reason about its semantics correctly, or build tooling - such as a visualization UI - around it.
Every claim below is backed by the actual source referenced in <<source-of-truth>>; if this document and the source ever disagree, the source is authoritative.

== What this file is

`progressHistoryFile` is a durable, git-committed log of *when each Gherkin scenario first reached each stage of its implementation lifecycle*: listed (a title only, no steps written yet), defined (steps written, but at least one has no matching glue code), and implemented (every step has matching glue code). It exists to answer questions a single build's report cannot: "how long did it take this scenario to go from listed to implemented?", "how many scenarios were newly implemented in the last week?", "has a previously-implemented scenario quietly disappeared from the feature files?"

It is only written when `gherkinToAsciidoc.trackProgressHistory` is set to `true` (which itself requires `trackProgress = true`); see link:../README.adoc#_tracking_progress_history[the README's "Tracking Progress History" section] for the DSL properties that control it.

Unlike the equivalent history file in the Arc-E-Tect Shadow/Mirage/Doppelganger API Detector plugins - which share one format across all three plugins - this format is **local to gherkin-to-asciidoc only**: nothing else reads or writes it, and its schema is unrelated to (not merely different from) the API detectors' `contractHistoryFile` schema. Do not assume the two are interchangeable or that tooling built for one applies to the other.

== Source of truth

[cols="1,3",options="header"]
|===
| Class | Responsibility
| `com.arc_e_tect.gradle.gherkin.progress.ScenarioProgressRecord` | The record type - one Java `record` per history entry, described field-by-field below.
| `com.arc_e_tect.gradle.gherkin.progress.ProgressHistoryStore` | Reads/writes the NDJSON file. Hand-rolled JSON serialization (no library dependency) via a fixed regex per line.
| `com.arc_e_tect.gradle.gherkin.progress.ProgressHistoryUpdater` | Computes the *next* history map from the previous one plus the current run's scenarios. This is where the "stamped once, never overwritten" and "never deleted, only marked removed" rules actually live.
| `com.arc_e_tect.gradle.gherkin.progress.ScenarioFingerprint` | Computes the stable identifier described in <<fingerprint>>.
| `com.arc_e_tect.gradle.gherkin.progress.ScenarioClassifier` | Classifies a scenario as `LISTED`/`DEFINED`/`IMPLEMENTED` for a given run - the input to the updater above, not something this file records directly (see <<current-status-vs-history>>).
| `com.arc_e_tect.gradle.gherkin.progress.ProgressReportWriter` | Renders both the `== Progress Summary` and `== Progress Over Time` sections of the generated AsciiDoc report *from* this file's loaded content - see <<relationship-to-report>>.
|===

`GenerateFeatureDocsTask` (`com.arc_e_tect.gradle.gherkin.GenerateFeatureDocsTask`) is a thin caller: it loads the file, calls the updater with the current run's scenarios, optionally saves the result, and passes it to the report writer. It never touches the file format directly.

== Quick facts

[cols="1,3",options="header"]
|===
| |
| Format | Newline-delimited JSON (NDJSON) - exactly one JSON object per line, no enclosing array, no trailing comma.
| Encoding | UTF-8.
| Line ending | `\n` (written via `PrintWriter.println`, platform default - in practice `\n` on Linux/macOS CI).
| Ordering | Every write sorts all records by `fingerprint` (lexicographic string sort) before writing, so re-saving an unchanged history byte-for-byte reproduces the same file - git diffs stay minimal regardless of scenario reordering or scenarios moving between feature files.
| Default location | `gherkin-progress-history.ndjson`, directly in the project directory (**not** under `build/`) - deliberately, since the file is meant to be committed to version control.
| Configurable via | `gherkinToAsciidoc.progressHistoryFile` (a `RegularFileProperty`).
| Created when | The first time `generateFeatureDocs` runs with `trackProgressHistory = true` and `updateProgressHistory` resolving to `true`, and the file does not already exist.
| Missing file | Treated as an empty history - **not** an error. Every currently-observed scenario is then written as a brand-new record.
| Malformed line | Skipped with a `WARN`-level Gradle log message identifying the line number. Never fails the build. The rest of the file is still loaded normally.
| Schema version field | **None.** There is no `"version"` or similar marker in the JSON. A tool consuming this file should treat the field set documented below as the only contract, and should not assume forward compatibility with a future field set.
|===

== When it is written

`gherkinToAsciidoc.progressHistoryFile` is:

* *Always read* when `trackProgressHistory` is `true`, on every run, regardless of `updateProgressHistory`.
* *Written back* only when `trackProgressHistory` **and** `updateProgressHistory` are both `true`. `updateProgressHistory` defaults to the same value as `trackProgressHistory`, and is typically driven from CI (e.g. only on `main`) via the `-PgherkinToAsciidoc.updateProgressHistory` project property - the plugin itself has no notion of git branches.

`trackProgressHistory` additionally requires `trackProgress = true` and does **not** imply it - enabling `trackProgressHistory` while `trackProgress` is `false` fails `generateFeatureDocs` with a descriptive error, since history tracking is meaningless without scenario classification also being active.

A run with `trackProgressHistory = true` and `updateProgressHistory = false` still loads and reports against the file's current content (so the generated report reflects reality), it simply doesn't persist any changes back to disk.

Because `progressHistoryFile`'s *path* (not its content) is a tracked Gradle task input, renaming or relocating it in the build script is enough on its own to make `generateFeatureDocs` run again rather than being skipped as `UP-TO-DATE` - see link:../README.adoc#_tracking_progress_history[the README] for the `--rerun` escape hatch if a run is ever skipped for some other reason.

== Record schema

Every line is one JSON object with exactly these eight keys, always present (using JSON `null` for an absent value - never an omitted key):

[cols="1,1,1,4",options="header"]
|===
| Key | JSON type | Nullable | Meaning
| `fingerprint` | string | No | Stable identifier for this scenario. See <<fingerprint>>. Acts as this record's primary key - the map this file round-trips through is keyed by this field.
| `scenarioName` | string | No | The scenario's display title, e.g. `1.2 - User logs in`, with only the `Scenario:`/`Scenario Outline:` keyword prefix removed. Unlike `fingerprint`, this field is **not** stripped of a numbering prefix, so its exact text can change run-to-run for the *same* fingerprint purely because `indexing` renumbered the scenario - see <<fingerprint>> for why that doesn't create a new record. Refreshed on every run that observes the scenario, so a renamed-in-place scenario always shows its current title here.
| `featureTitle` | string | No | The title of the `Feature:` the scenario currently lives under. Refreshed on every run, so a scenario moved to a different feature file shows up under its new feature immediately - this is the entire point of fingerprinting by scenario name alone rather than by (feature, scenario) pair.
| `listedAt` | string (ISO-8601 instant) or `null` | Yes | The instant this scenario was *first* observed with `LISTED` status (a title with no `Given`/`When`/`Then` steps at all). Stamped once; never overwritten on subsequent runs.
| `definedAt` | string (ISO-8601 instant) or `null` | Yes | The instant this scenario was *first* observed with `DEFINED` status (has steps, but at least one has no matching glue code). Same "stamped once" rule. **Can remain permanently `null`** even for a fully implemented scenario, if it jumped directly from `LISTED` to `IMPLEMENTED` between two runs (e.g. all its glue code was added in one commit) - see <<current-status-vs-history>>.
| `implementedAt` | string (ISO-8601 instant) or `null` | Yes | The instant this scenario was *first* observed with `IMPLEMENTED` status (every step has matching glue code). Same "stamped once" rule.
| `lastSeenAt` | string (ISO-8601 instant) or `null` | Yes | The instant of the *most recent* run that observed this scenario at all, in *any* of the three statuses. Unlike the three stage timestamps above, this is refreshed forward on *every* run the scenario is present in - it is not a "first observed" timestamp. If a record stops being observed, `lastSeenAt` freezes at its last real value while `removedAt` (below) gets set instead.
| `removedAt` | string (ISO-8601 instant) or `null` | Yes | `null` while the scenario is still present in the most recent run's parsed feature files. Set to the instant of the *first* run that no longer found it anywhere. Records are **never deleted** from the file once written - a removed scenario's row persists indefinitely with this field set. If a scenario with the same fingerprint reappears in a later run (e.g. a revert), `removedAt` reverts to `null` automatically and the record resumes advancing normally.
|===

Instants are serialized via plain `Instant.toString()` - standard ISO-8601 UTC, e.g. `"2026-02-20T11:15:44Z"` (always `Z`/UTC, always second-or-finer precision, never a bare date).

[#current-status-vs-history]
=== Current status is not stored directly - only the stage timestamps are

A scenario's status on any *given* run (`LISTED`, `DEFINED`, or `IMPLEMENTED`, computed by `ScenarioClassifier` from its steps and the available glue code) is mutually exclusive - a scenario is exactly one of the three at any point in time, never more than one at once. This file does **not** store that current status as a field. Instead, each run's classification determines *which one* of `listedAt`/`definedAt`/`implementedAt` gets stamped with `now`, *if it hasn't been stamped already*.

This means, unlike a simple three-state field, the three timestamps accumulate independently over the scenario's lifetime: a scenario that progressed `listed → defined → implemented` across three separate runs ends up with all three timestamps populated, forming a genuine progression history. A scenario whose glue code was written in one commit, skipping straight from `listed` to `implemented` between two consecutive runs, ends up with `listedAt` and `implementedAt` both set but `definedAt` permanently `null` - this is expected, not a data-quality problem, and a tool should not treat a `null` `definedAt` on an otherwise-populated record as a parsing error or missing data.

A consumer that wants to know a scenario's *current* status from this file alone can derive it: the highest-reached non-null stage among `listedAt`/`definedAt`/`implementedAt` (in that order) is the scenario's last known status as of `lastSeenAt` - but only as of `lastSeenAt`; if `removedAt` is set, the scenario is no longer present at all, regardless of what its last-known stage was.

[#fingerprint]
=== How `fingerprint` is computed

`fingerprint` is the first 16 hex characters of the SHA-256 hash of the scenario's *normalized* title - normalized by stripping both the `Scenario:`/`Scenario Outline:` keyword prefix and any existing index-numbering prefix (the `\d+(?:\.\d+)? - ` format the `indexing` feature writes), then trimming and lower-casing what remains. Nothing else about the scenario (which feature file it lives in, its steps, its line number) affects it - this is deliberate, so a scenario keeps its history across being cut from one feature file and pasted into another, and across being renumbered, as long as its own title text doesn't otherwise change.

Pseudocode, matching `ScenarioFingerprint.fingerprint(String)` exactly:

[source,text]
----
withoutKeyword = strip_if_matches(title, /^(?:Scenario Outline|Scenario):\s*(.*)$/)
withoutIndex   = strip_if_matches(withoutKeyword, /^\d+(?:\.\d+)? - (.*)$/)
normalized     = withoutIndex.trim().toLowerCase()
fingerprint    = sha256_hex(normalized)[0:16]
----

Note this differs from `scenarioName` (the persisted display field), which only has the keyword prefix stripped, not the index prefix - so two records can legitimately show *different* `scenarioName` text (e.g. `"1 - User logs in"` in one snapshot, `"2 - User logs in"` in a later one, after renumbering) while sharing the *same* `fingerprint`. A tool that joins or deduplicates records must use `fingerprint`, never `scenarioName`, as the identity key.

== Example file content

A realistic `progressHistoryFile` after several months of builds, showing every lifecycle state this format can express - a scenario tracked end-to-end, one that skipped straight from listed to implemented, and one that has disappeared:

[source,json]
----
{"fingerprint":"a1f3c9d0e21b7f44","scenarioName":"User logs in","featureTitle":"User authentication","listedAt":"2026-01-14T09:02:11Z","definedAt":"2026-02-03T16:40:00Z","implementedAt":"2026-02-20T11:15:44Z","lastSeenAt":"2026-08-12T07:00:00Z","removedAt":null}
{"fingerprint":"7be04412aa3390d1","scenarioName":"User resets password","featureTitle":"User authentication","listedAt":"2026-06-01T08:00:00Z","definedAt":null,"implementedAt":"2026-06-01T08:00:00Z","lastSeenAt":"2026-08-12T07:00:00Z","removedAt":null}
{"fingerprint":"c3d4e5f607182934","scenarioName":"2 - Admin locks an account","featureTitle":"Account management","listedAt":"2026-02-20T11:15:44Z","definedAt":"2026-03-01T09:00:00Z","implementedAt":null,"lastSeenAt":"2026-05-01T07:00:00Z","removedAt":"2026-05-08T07:00:00Z"}
----

Reading these three lines: the first scenario progressed through all three stages over about five weeks and is still present. The second went straight from `listed` to `implemented` in the same run (`listedAt` and `implementedAt` are equal) with `definedAt` permanently `null` - a real, valid state, not missing data. The third was listed and later defined, but never implemented, and stopped being observed after `2026-05-01`; its `scenarioName` still carries an index prefix (`"2 - ..."`), which its `fingerprint` ignores entirely.

[#relationship-to-report]
== Relationship to the generated report

Every `generateFeatureDocs` run that has `trackProgressHistory = true` and at least one record in the (loaded or just-updated) history renders a `== Progress Over Time` section in the generated report, directly below `== Progress Summary`, computed *entirely* from this file's content by `ProgressReportWriter`:

[cols="1,3",options="header"]
|===
| Report row | Computed as
| `Tracked since` | The minimum non-null value across `listedAt`, `definedAt`, `implementedAt`, `lastSeenAt`, and `removedAt`, over *every* record in the file. Rendered as `yyyy-MM-dd HH:mm:ss 'UTC'`, not the raw ISO-8601 string.
| `Listed in the last 7/30 days` | Count of records whose `listedAt` falls within `[now - 7 days, now]` / `[now - 30 days, now]`.
| `Defined in the last 7/30 days` | Same windowed count, over `definedAt`.
| `Implemented in the last 7/30 days` | Same windowed count, over `implementedAt`.
| `Removed (no longer seen)` | Count of records where `removedAt` is non-null, as of this run.
|===

A tool building richer visualizations than this fixed table has the *entire* underlying file available to compute anything else these summary numbers only sample - see <<visualization-ideas>>.

[#visualization-ideas]
== Building a visualization UI: what's meaningful to show

The report above is a static snapshot. The file itself is a genuine time series - every record carries up to five independent timestamps - so a UI with access to the raw file (or, better, several historical revisions of it from git) can show meaningfully more than the report does. Ideas, roughly in order of implementation effort:

Scenario lifecycle timeline (per-scenario)::
One row per scenario (labelled by `scenarioName`, grouped by `featureTitle`, keyed internally by `fingerprint`), one horizontal timeline per row, with markers at `listedAt`, `definedAt`, and `implementedAt` in sequence (some rows will legitimately skip the `definedAt` marker - see <<current-status-vs-history>>), and a distinct visual treatment (e.g. greyed out, or a tombstone marker) for rows where `removedAt` is set.

Coverage funnel::
A simple three-stage funnel (or stacked bar) of *how many* records currently have a non-null `listedAt`, `definedAt`, and `implementedAt` respectively, as of "now" - the single-point-in-time version of what the report's summary table already computes, but rendered as a funnel rather than a table makes the drop-off between stages visually obvious.

Rolling-window trend lines::
The report's "last 7/30 days" counts are single numbers computed against "now". Recompute the *same* windowed count for many historical values of "now" (e.g. once per day, for the last 90 days) to produce a trend line per stage - this shows implementation velocity and whether it's accelerating, flat, or stalling, which the report alone cannot.

Removed/stale watchlist::
A simple table of every record with non-null `removedAt`, sorted by `removedAt` descending, showing how long ago each scenario disappeared. Useful for catching a scenario accidentally deleted from a feature file versus one intentionally retired.

Per-feature heatmap::
Group records by `featureTitle` and show, per feature, what fraction of its scenarios have reached each stage. Directly answers "which feature most needs implementation work" - something no single report currently surfaces.

Data-age indicator::
Surface `Tracked since` (or its raw components) prominently in any dashboard: a history file only a few days old cannot yet support meaningful 30-day trend claims, and a UI that hides this risks over-interpreting sparse data.

== Parsing this file yourself

Since there is no JSON library dependency in the writer (`ProgressHistoryStore` hand-rolls its own line format via a fixed regular expression - see <<source-of-truth>>), a tool that wants strict format compatibility, including exactly how a malformed line is tolerated, should mirror that same parser rather than assuming a generic JSON-lines parser will behave identically on edge cases (e.g. embedded escaped quotes in `scenarioName`/`featureTitle`). For everyday consumption, however, each line is valid standalone JSON, and any standard JSON parser applied line-by-line will correctly read every well-formed record; the escaping rules only matter for `scenarioName` and `featureTitle`, the two free-text fields (backslash and double-quote are backslash-escaped, nothing else).

=== JSON Schema

The following JSON Schema (2020-12) validates a single *line* of this file (one JSON object) - it does not describe the file as a whole, since the file is NDJSON, not a single JSON document. A tool ingesting this file should parse it one line at a time and validate each line independently against this schema.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://arc-e-tect.com/schemas/scenario-progress-record.json",
  "title": "ScenarioProgressRecord",
  "description": "One line of a gherkinToAsciidoc progressHistoryFile.",
  "type": "object",
  "additionalProperties": false,
  "required": ["fingerprint", "scenarioName", "featureTitle", "listedAt", "definedAt", "implementedAt", "lastSeenAt", "removedAt"],
  "properties": {
    "fingerprint": {
      "type": "string",
      "pattern": "^[0-9a-f]{16}$",
      "description": "First 16 hex characters of SHA-256(normalized scenario title)."
    },
    "scenarioName": {
      "type": "string",
      "minLength": 1,
      "description": "Display title with only the Scenario:/Scenario Outline: keyword stripped; may still carry an index-numbering prefix."
    },
    "featureTitle": {
      "type": "string",
      "minLength": 1
    },
    "listedAt":      { "type": ["string", "null"], "format": "date-time" },
    "definedAt":     { "type": ["string", "null"], "format": "date-time" },
    "implementedAt": { "type": ["string", "null"], "format": "date-time" },
    "lastSeenAt":    { "type": ["string", "null"], "format": "date-time" },
    "removedAt":     { "type": ["string", "null"], "format": "date-time" }
  }
}
----
