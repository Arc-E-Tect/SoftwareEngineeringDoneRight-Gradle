A Gradle plugin that scans `.feature` files for `Scenario` and `Scenario Outline` titles and generates an AsciiDoc file (`features.adoc`) listing all scenarios found.

The generated document gives teams a living, human-readable index of every behaviour specification defined in Gherkin, ready to be included directly into AsciiDoc-based project documentation.

Every generated document declares `:toc:`, so any AsciiDoc renderer (Asciidoctor, GitHub/GitLab previews, IDE
plugins, ...) shows a navigable table of contents alongside it - one entry per category (e.g. `Listed`,
`Defined`, `Implemented`, or each top-level `== <Feature>` heading when `groupByFeature` is enabled) and, when
`trackProgress` is also enabled, one nested entry per `=== <Feature>` sub-heading within each category. A flat,
ungrouped report has no headings below the title, so its table of contents is correspondingly empty.

== Gherkin Configuration

The plugin registers a `gherkinToAsciidoc` extension that accepts the following properties.
All properties have sensible defaults and do not need to be set for a typical project.

.Groovy DSL
[source,groovy]
----
import com.arc_e_tect.gradle.gherkin.indexing.IndexingMode // only needed if you set `indexing`

gherkinToAsciidoc {
    // One or more directories containing .feature files to scan (scanned recursively by
    // default - see includeSubDirs below). Default: 'src/test/resources/features' relative
    // to the project directory, used only when sourceDirs is left empty and sourceFile is not set.
    // Mutually exclusive with sourceFile.
    sourceDirs.from('src/test/resources/features')
    // Add more directories by calling .from(...) again, or in the same call:
    // sourceDirs.from('src/test/resources/features', 'src/test/resources/more-features')

    // Single .feature file to parse instead of sourceDirs.
    // Mutually exclusive with sourceDirs and includeSubDirs.
    // sourceFile = file('src/test/resources/features/login.feature')

    // When true, recursively scan all sub-directories of every directory in sourceDirs.
    // Cannot be used when sourceFile is set - explicitly set this to false when using sourceFile.
    // Default: true
    includeSubDirs = true

    // Directory where the generated AsciiDoc file will be written.
    // Default: build/generated-docs
    outputDir = layout.buildDirectory.dir('generated-docs')

    // Name of the generated AsciiDoc file.
    // Default: 'features.adoc'
    outputFileName = 'features.adoc'

    // When true, classifies every scenario as "listed", "defined", or "implemented"
    // and adds a progress summary to the generated AsciiDoc file (see "Tracking
    // Implementation Progress" below).
    // Requires sourceDirs and glueCodeDirs to be set; implies includeSubDirs = true.
    // Default: false
    trackProgress = false

    // One or more directories containing the Cucumber-JVM glue code (step definitions),
    // each scanned recursively for @Given/@When/@Then/@And/@But step definition patterns.
    // Required when trackProgress is true; ignored otherwise.
    // glueCodeDirs.from('src/test/java/com/example/steps')

    // When true, groups scenarios under their enclosing Feature instead of a flat list
    // (see "Grouping by Feature" below). Forced to true whenever trackProgress is true.
    // Default: true
    groupByFeature = true

    // Directory that the listed.adoc/defined.adoc/implemented.adoc report snippets are written
    // to when trackProgress is true (see "Report Snippets and Custom Templates" below).
    // Default: build/generated-docs/features/snippets
    // snippetDir = layout.buildDirectory.dir('generated-docs/features/snippets')

    // Optional Mustache template used to render the report so it references the snippets via
    // include:: directives instead of embedding their content verbatim. Only consulted when
    // trackProgress is true. When not set, the report looks exactly like it does without this
    // property - the snippets are still written either way.
    // template = file('templates/report.mustache')

    // Version of the system under test that the reported scenarios exercise, printed near the
    // top of the generated document (see "System Under Test Version" below).
    // Default: the project's own `version`
    // systemUnderTestVersion = 'v1.0.0'

    // Numbers Feature/Scenario titles directly in the source .feature files (see "Numbering
    // Features and Scenarios" below). Requires includeSubDirs = true; FEATURE and ALL also
    // require groupByFeature = true.
    // Default: IndexingMode.OFF
    indexing = IndexingMode.OFF

    // When true, indexing renumbers every Feature/Scenario from scratch. When false, a line
    // whose existing number already reflects the currently configured indexing value is left
    // untouched - only lines that aren't yet correctly numbered are numbered.
    // Default: false
    forceRewrite = false

    // Persists a per-scenario history of when each scenario first reached listed/defined/
    // implemented status (see "Tracking Progress History" below). Requires trackProgress = true.
    // Default: false
    trackProgressHistory = false

    // NDJSON file the history is read from/written to. Defaults into the project directory
    // (not build/), since it's meant to be committed.
    // Default: file('gherkin-progress-history.ndjson')
    // progressHistoryFile = file('gherkin-progress-history.ndjson')

    // When true, progressHistoryFile is written back to disk. Only consulted when
    // trackProgressHistory is true; the file is always read either way.
    // Default: same as trackProgressHistory
    // updateProgressHistory = true
}
----

.Kotlin DSL (`build.gradle.kts`)
[source,kotlin]
----
import com.arc_e_tect.gradle.gherkin.indexing.IndexingMode // only needed if you set `indexing`

gherkinToAsciidoc {
    sourceDirs.from("src/test/resources/features")
    includeSubDirs.set(true)
    outputDir.set(layout.buildDirectory.dir("generated-docs"))
    outputFileName.set("features.adoc")
    trackProgress.set(false)
    // glueCodeDirs.from("src/test/java/com/example/steps")
    groupByFeature.set(true)
    // snippetDir.set(layout.buildDirectory.dir("generated-docs/features/snippets"))
    // template.set(file("templates/report.mustache"))
    // systemUnderTestVersion.set("v1.0.0")
    indexing.set(IndexingMode.OFF)
    forceRewrite.set(false)
    trackProgressHistory.set(false)
    // progressHistoryFile.set(file("gherkin-progress-history.ndjson"))
    // updateProgressHistory.set(true)
}
----

=== Configuration Properties

[cols="1,1,1,3",options="header"]
|===
| Property        | Type            | Default                              | Description
| `sourceDirs`    | File collection | `src/test/resources/features`        | One or more directories containing `.feature` files to scan.
Mutually exclusive with `sourceFile`.
| `sourceFile`    | File            | —                                    | Single `.feature` file to parse.
Mutually exclusive with `sourceDirs` and `includeSubDirs`.
| `includeSubDirs`| Boolean         | `true`                               | When `true`, recursively scans all sub-directories of every directory in `sourceDirs`.
Cannot be combined with `sourceFile` - explicitly set this to `false` when using `sourceFile`.
| `outputDir`     | Directory       | `build/generated-docs`               | Directory where the generated AsciiDoc file is written.
| `outputFileName`| String          | `features.adoc`                      | Name of the generated AsciiDoc file.
| `trackProgress` | Boolean         | `false`                              | When `true`, classifies every scenario as `listed`, `defined`, or `implemented` and adds a progress summary to the generated document.
Requires `sourceDirs` and `glueCodeDirs`; implies `includeSubDirs = true`.
| `glueCodeDirs`  | File collection | —                                    | One or more directories containing the Cucumber-JVM glue code, each scanned recursively for step definitions.
Required when `trackProgress` is `true`.
| `groupByFeature`| Boolean         | `true`                               | When `true`, groups scenarios under their enclosing `Feature` instead of a flat list.
Forced to `true` whenever `trackProgress` is `true`.
| `snippetDir`    | Directory       | `build/generated-docs/features/snippets` | Directory that the `listed.adoc`/`defined.adoc`/`implemented.adoc` report snippets are written to.
Only used when `trackProgress` is `true`.
| `template`      | File            | —                                    | Optional Mustache template used to render the report so it references the snippets via `include::` directives instead of embedding their content verbatim.
Only consulted when `trackProgress` is `true`.
| `systemUnderTestVersion` | String | the project's `version`             | Version of the system under test that the reported scenarios exercise, printed near the top of the generated document (see "System Under Test Version" below).
| `indexing`      | `IndexingMode` (`OFF`/`FEATURE`/`SCENARIO`/`ALL`/`CI`) | `OFF` | Numbers `Feature`/`Scenario` titles directly in the source `.feature` files (see "Numbering Features and Scenarios" below).
`FEATURE`/`SCENARIO`/`ALL` require `includeSubDirs = true`; `FEATURE` and `ALL` additionally require `groupByFeature = true`. `CI` skips indexing entirely and is always allowed; overridable for the whole build via the `-PgherkinToAsciidoc.indexing` project property.
| `forceRewrite`  | Boolean         | `false`                              | When `true`, `indexing` renumbers every `Feature`/`Scenario` from scratch. When `false`, a line already correctly numbered for the currently configured `indexing` value is left untouched.
Has no effect when `indexing` is `OFF` or `CI`. Overridable for the whole build via the `-PgherkinToAsciidoc.forceRewrite` project property.
| `trackProgressHistory` | Boolean  | `false`                              | When `true`, persists a per-scenario history of when each scenario first reached `listed`/`defined`/`implemented` status (see "Tracking Progress History" below).
Requires `trackProgress = true`.
| `progressHistoryFile` | File      | `gherkin-progress-history.ndjson` (project directory) | NDJSON file the progress history is read from and, when `updateProgressHistory` is `true`, written back to.
Only consulted when `trackProgressHistory` is `true`.
| `updateProgressHistory` | Boolean | same as `trackProgressHistory`       | When `true`, writes `progressHistoryFile` back to disk after updating it with the current run's scenarios.
The file is always read when `trackProgressHistory` is `true`, regardless of this property. Overridable for the whole build via the `-PgherkinToAsciidoc.updateProgressHistory` project property.
|===

[IMPORTANT]
====
`sourceDirs` and `sourceFile` are mutually exclusive.
Setting both will cause the `generateFeatureDocs` task to fail with a descriptive error.

`includeSubDirs` cannot be combined with `sourceFile`. Since `includeSubDirs` now defaults to `true`,
a project using `sourceFile` must explicitly set `includeSubDirs = false` - otherwise
`generateFeatureDocs` fails with a descriptive error.

`trackProgress` can only be enabled when `sourceDirs` is configured, and requires `glueCodeDirs` to be set.
Enabling it implies `includeSubDirs = true` and `groupByFeature = true`, regardless of those properties' own
configured values.

`snippetDir` and `template` are only consulted when `trackProgress` is `true`; both are ignored otherwise.

`trackProgressHistory` requires `trackProgress = true` and does *not* imply it - both must be set explicitly.
Enabling `trackProgressHistory` while `trackProgress` is `false` fails `generateFeatureDocs` with a descriptive
error. See "Tracking Progress History" below.

`OFF` and `CI` are always allowed for `indexing`. `FEATURE`, `SCENARIO`, and `ALL` require `includeSubDirs`
to be `true`; `FEATURE` and `ALL` additionally require `groupByFeature` to be `true` - with
`groupByFeature = false`, only `SCENARIO` of those three is allowed. Setting an invalid combination fails
`generateFeatureDocs` with a descriptive error.

The `-PgherkinToAsciidoc.indexing=<value>` and `-PgherkinToAsciidoc.forceRewrite=<true|false>` project
properties, when set, each override their respective DSL property for every project in the build
regardless of what any project's own `gherkinToAsciidoc { }` block configures - see "Overriding
`indexing`/`forceRewrite` from the Command Line" below. An unrecognised value fails `generateFeatureDocs`
with a descriptive error too.
====

== Running the Task

The plugin registers a single task named `generateFeatureDocs` in the `documentation` group:

[source,bash]
----
./gradlew generateFeatureDocs
----

The task scans the configured source location, collects every `Scenario` and `Scenario Outline` title, and writes the result to `<outputDir>/<outputFileName>`.

== Progress Reporting

Parsing a large tree of `.feature` files, reindexing them, and scanning glue code directories for step definitions can all take a while on a real project.
The task periodically logs progress at `LIFECYCLE` level so a long-running scan doesn't sit silently until it finishes.

[source,shell]
----
> Task :generateFeatureDocs
gherkinToAsciidoc: parsing feature files...
Parsing feature files: 50/210 (23%)
Parsing feature files: 100/210 (47%)
Parsing feature files: done, 210 item(s)
gherkinToAsciidoc: scanning glue code...
Scanning glue code: 340 processed so far
Scanning glue code: done, 458 item(s)
Generated 640 scenario title(s) to build/docs/feature-scenarios.adoc
----

This is plain log output, not an animated progress indicator.
The plugin deliberately avoids Gradle's internal, unsupported console/progress APIs, since their shape can change between Gradle versions and this plugin is published on the Gradle Plugin Portal for consumers on Gradle versions this project doesn't control.
Each line is printed once and never overwritten in place, so it plays back cleanly in CI logs as well as an interactive terminal.

Reindexing gets its own banner and progress lines too, but only when `indexing` is actually numbering something (`feature`, `scenario`, or `all`); with `indexing = off` or `indexing = ci`, that phase is silent, and glue code scanning only reports when `trackProgress` is `true`.

[[multi-project-builds]]
== Multi-Project Builds

The plugin can be applied to every project in a Gradle multi-project build, not just a single one. Apply it
in the root project's `build.gradle` using `allprojects` (or `subprojects` plus the root project itself) so
that every project - root and sub-projects alike - gets its own `generateFeatureDocs` task and its own
generated report:

.Groovy DSL (`build.gradle`, root project)
[source,groovy]
----
allprojects {
    apply plugin: 'com.arc-e-tect.gherkin-to-asciidoc'
}

gherkinToAsciidoc {
    // Applies to every project below that doesn't override a given property itself.
    trackProgress = true
    outputFileName = 'features.adoc'
}
----

Configuring `gherkinToAsciidoc { }` on the root project sets *defaults* that every other project inherits;
configuring the same block in a sub-project's own `build.gradle` overrides those defaults for that
sub-project only, property by property - a sub-project only needs to configure the properties it wants to
differ from the root project's.

[cols="1,3",options="header"]
|===
| Property                 | Multi-project behaviour

| `trackProgress`
| Inherited from the root project by default; a sub-project can enable/disable it independently. A
sub-project that inherits or sets `trackProgress = true` still needs its own `glueCodeDirs` configured.
| `includeSubDirs`
| Inherited from the root project by default (subject to the usual `trackProgress` implication).
| `groupByFeature`
| Inherited from the root project by default (subject to the usual `trackProgress` implication).
| `indexing`
| Inherited from the root project by default; a sub-project can override it independently, subject to
the usual `includeSubDirs`/`groupByFeature` validation constraints for whichever value is in effect. The
`-PgherkinToAsciidoc.indexing` command-line override (see "Overriding `indexing`/`forceRewrite` from the
Command Line" above) takes precedence over both, for every project in the build at once.
| `forceRewrite`
| Inherited from the root project by default; a sub-project can override it independently. The
`-PgherkinToAsciidoc.forceRewrite` command-line override takes precedence over both, for every project in
the build at once.
| `outputFileName`
| Inherited from the root project by default.
| `template`
| Inherited from the root project by default.
| `systemUnderTestVersion`
| Inherited from the root project's own `systemUnderTestVersion` (or the root project's `version`, if
neither is set) by default - useful when every project documents scenarios for the same overall system.
| `sourceDirs` / `sourceFile` / `glueCodeDirs`
| Inherited from the root project when a sub-project configures neither `sourceDirs` nor `sourceFile`
itself - but re-resolved against the sub-project's own directory rather than copied verbatim (see below).
| `outputDir` / `snippetDir`
| *Never* inherited from the root project - each project always defaults to a location under its own
`build` directory, even when the root project sets a custom `outputDir`/`snippetDir`, so that every
project's report is written to its own build output instead of colliding with another project's. Set
either explicitly on a specific project to relocate that project's report.
|===

=== Inheriting `sourceDirs`/`sourceFile`/`glueCodeDirs` - Convention Over Configuration

Unlike the other properties, `sourceDirs`, `sourceFile`, and `glueCodeDirs` are directories/files, so
inheriting the root project's *literal* value would point every sub-project at the root project's own
directories - not what you want when every sub-project follows the same standard layout. Instead, when a
sub-project configures none of `sourceDirs`/`sourceFile` itself:

* Any root-configured `sourceDirs`/`sourceFile`/`glueCodeDirs` entry that lives *inside the root project's own
  directory* is re-resolved against the sub-project's own directory instead. This means a standard layout
  only needs to be declared once, at the root:
+
[source,groovy]
----
// Root build.gradle - every sub-project keeps its features and glue code in the same relative place.
gherkinToAsciidoc {
    sourceDirs.from('src/test/resources/features')
    glueCodeDirs.from('src/test/java/steps')
}
----
+
A sub-project at `service-a/` then resolves these to `service-a/src/test/resources/features` and
`service-a/src/test/java/steps`, without repeating the block itself.
* A root-configured entry that lives *outside* the root project's own directory (e.g. a directory shared by
  every module, elsewhere on disk) is used as-is, unchanged, by every sub-project that inherits it - it isn't
  something a per-project relative layout convention could sensibly apply to.
* A sub-project that configures its own `sourceDirs` or `sourceFile` ignores the root project's configuration
  for source location entirely, exactly like the other properties above.

See the
link:../examples/gherkin-to-asciidoc/multi-project/README.adoc[multi-project example]
for a root project and two sub-projects, one of which overrides several of the root project's defaults.

== System Under Test Version

Every generated document - whether a plain scenario listing or a full progress report - includes a line
just below the title identifying the version of the system under test that the reported scenarios exercise:

[source,asciidoc]
----
System Under Test version: 1.0.0
----

By default, this is the project's own `version`, exactly as set in `build.gradle`/`build.gradle.kts` or a
`gradle.properties` file. Set `systemUnderTestVersion` to override it - useful when the scenarios in
`sourceDirs` exercise a different, independently versioned artifact than the one Gradle is building:

[source,groovy]
----
gherkinToAsciidoc {
    systemUnderTestVersion = 'v1.0.0'
}
----

The examples below assume the project's `version` is set to `1.0.0`.

== Grouping by Feature

By default, scenarios are grouped under their enclosing `Feature`, as shown above — useful once `sourceDirs`
spans more than one feature area, as with two feature files:

[source,gherkin]
----
Feature: User authentication

  Scenario: User logs in successfully
    Given the login page is open

Feature: Invoice payment

  Scenario: User pays an invoice
    Given an outstanding invoice
----

[source,asciidoc]
----
= Feature Scenarios
:toc:
:toclevels: 2

System Under Test version: 1.0.0

This document lists every `Scenario` and `Scenario Outline` found under the configured feature file directories.

== User authentication

* Scenario: User logs in successfully

== Invoice payment

* Scenario: User pays an invoice
----

Setting `groupByFeature = false` instead lists every scenario as one flat list, regardless of which
`.feature` file it came from:

[source,asciidoc]
----
= Feature Scenarios
:toc:
:toclevels: 2

System Under Test version: 1.0.0

This document lists every `Scenario` and `Scenario Outline` found under the configured feature file directories.

* Scenario: User logs in successfully
* Scenario: User pays an invoice
----

== Numbering Features and Scenarios

Setting `indexing` numbers `Feature`/`Scenario` titles directly in the source `.feature` files - not just in
the generated report - so the numbering is visible wherever the feature file itself is read (in an editor, in
a Cucumber test run, ...), not only in `generateFeatureDocs`'s own output.

[cols="1,3",options="header"]
|===
| Value      | Effect

| `OFF`      | Nothing is numbered (default). Any numbering left over from a previous run is removed.
| `FEATURE`  | Every feature is numbered, e.g. `Feature: 1 - User authentication`. Scenario titles are untouched.
| `SCENARIO` | Every scenario is numbered continuously across all feature files, e.g. `Scenario: 1 - User logs in`. Feature titles are untouched.
| `ALL`      | Both are numbered; scenarios are numbered per feature as `<featureNumber>.<scenarioNumber>`, e.g. `Scenario: 1.1 - User logs in` within `Feature: 1 - User authentication`.
| `CI`       | Indexing is skipped entirely: the source files aren't touched at all - unlike `OFF`, not even to strip prior numbering. See "Overriding `indexing`/`forceRewrite` from the Command Line" below.
|===

Feature files are processed - and numbered - in the same order the generated report lists them in: for each
source directory (directories themselves ordered alphabetically by path when more than one is configured),
that directory's own feature files first, alphabetically by file name, and only then its sub-directories'
files, each sub-directory visited the same way, alphabetically by name. Scenario numbers additionally follow
document order within each file.

Given two feature files, `features-auth/authentication.feature`:

[source,gherkin]
----
Feature: User authentication

  Scenario: User requests a password reset

  Scenario: User logs in successfully
    Given the login page is open
----

and `features-billing/invoice.feature`:

[source,gherkin]
----
Feature: Invoice payment

  Scenario: User pays an invoice
    Given an outstanding invoice
----

with `indexing = IndexingMode.ALL`, the plugin rewrites both files in place:

[source,gherkin]
----
Feature: 1 - User authentication

  Scenario: 1.1 - User requests a password reset

  Scenario: 1.2 - User logs in successfully
    Given the login page is open
----

[source,gherkin]
----
Feature: 2 - Invoice payment

  Scenario: 2.1 - User pays an invoice
    Given an outstanding invoice
----

and the generated report reflects the same numbering, since it's parsed from the now-rewritten source files:

[source,asciidoc]
----
== 1 - User authentication

* Scenario: 1.1 - User requests a password reset
* Scenario: 1.2 - User logs in successfully

== 2 - Invoice payment

* Scenario: 2.1 - User pays an invoice
----

[IMPORTANT]
====
`indexing` mutates files that are also its own inputs - commit the resulting numbered `.feature` files like
any other source change.
====

=== Not Renumbering Already-Numbered Lines (`forceRewrite`)

By default (`forceRewrite = false`), a `Feature`/`Scenario` line whose existing number already matches the
format the currently configured `indexing` value would itself produce is left completely untouched - only
lines that aren't yet correctly numbered are numbered. Continuing the `ALL`-mode example above, adding a
third feature file that sorts alphabetically *before* `authentication.feature` does *not* renumber the
two files already numbered `1`/`2`:

[source,gherkin]
----
Feature: Access control
----

[source,asciidoc]
----
== 3 - Access control

== 1 - User authentication

* Scenario: 1.1 - User requests a password reset
* Scenario: 1.2 - User logs in successfully

== 2 - Invoice payment

* Scenario: 2.1 - User pays an invoice
----

The new feature is numbered `3` - the next number not already in use - rather than `1`, which would have
required renumbering the two already-numbered files after it. Re-running `generateFeatureDocs` with no
further changes is a complete no-op: every line is already correctly numbered, so nothing is rewritten.

Numbering isn't preserved *unconditionally*, though - only when it already reflects the *currently
configured* `indexing` value. A number left over from a *different* `indexing` value doesn't reflect the
current one, and is still stripped and replaced. For example, with `indexing = IndexingMode.SCENARIO`, a
scenario already reading `Scenario: 3 - ...` keeps that number - but changing `indexing` to
`IndexingMode.ALL` gives that same scenario a fresh `<featureNumber>.<n>` number instead, since its old `3`
doesn't match `ALL`'s format. Setting `indexing` back to `OFF` still always strips every number,
regardless of `forceRewrite`, since `OFF`'s canonical state for every line is unnumbered.

Setting `forceRewrite = true` instead restores the original behaviour (present before `forceRewrite`
existed): every `Feature`/`Scenario` number is recomputed from scratch on every run, exactly as if none of
them had ever been numbered before - the third feature file above would instead become `1`, bumping
`authentication.feature`/`invoice.feature` to `2`/`3`.

=== Reindexing Colliding Numbers

Two developers numbering features or scenarios independently on separate branches can easily end up
assigning the *same* number - there's nothing in either branch alone to reveal the clash. Once both
branches are merged, `generateFeatureDocs` detects the collision and resolves it automatically: whichever
`Feature`/`Scenario` line is encountered first (in the same file/directory order described above) keeps
the colliding number, and every other line claiming that same number is treated as unnumbered and given
the next available one - exactly as if it had never been numbered at all. This applies at both levels:
two features sharing a number, or two scenarios *within the same feature* sharing a number.

For example, if `authentication.feature` and `invoice.feature` are merged from two branches that each
independently numbered their own feature `1`:

[source,gherkin]
----
Feature: 1 - User authentication
----

[source,gherkin]
----
Feature: 1 - Invoice payment
----

running `generateFeatureDocs` with `indexing = IndexingMode.FEATURE` leaves the first file (in file order)
as `1` and renumbers the second to the next free number:

[source,gherkin]
----
Feature: 1 - User authentication
----

[source,gherkin]
----
Feature: 2 - Invoice payment
----

This happens automatically on the next `generateFeatureDocs` run after the merge, with `forceRewrite`
left at its default `false` - there's no need to set `forceRewrite = true` just to resolve a collision, and
doing so would additionally renumber every other already-correctly-numbered line in the process.

=== Overriding `indexing`/`forceRewrite` from the Command Line

A CI pipeline typically shouldn't have `generateFeatureDocs` rewrite committed `.feature` files during a
build - a fresh checkout has no numbering to add, and a build that mutates its own source tree can leave a
CI job with unexpected local changes for no benefit, since nothing there will ever commit them. Rather than
requiring every project's build script to special-case CI, override `indexing` from the command line
instead:

[source,bash]
----
./gradlew generateFeatureDocs -PgherkinToAsciidoc.indexing=ci
----

This sets `indexing` to `IndexingMode.CI` for every project in the build - root and every sub-project alike
- regardless of what each project's own `gherkinToAsciidoc { }` block configures. A project can keep
`indexing = IndexingMode.FEATURE` (or any other value) for local/day-to-day use and still build cleanly in
CI without any source file ever being mutated there, with no change to the build script itself. The
property's value is matched against `IndexingMode` case-insensitively and accepts any of the five values
(`off`, `feature`, `scenario`, `all`, `ci`), not just `ci` - useful for e.g. temporarily forcing a specific
mode across an entire multi-project build without editing every sub-project's configuration.

`-PgherkinToAsciidoc.forceRewrite=<true|false>` works the same way for `forceRewrite`, e.g. to force a full
renumber for a single run without permanently setting `forceRewrite = true` in any build script:

[source,bash]
----
./gradlew generateFeatureDocs -PgherkinToAsciidoc.forceRewrite=true
----

See the
link:../examples/gherkin-to-asciidoc/indexing/README.adoc[indexing example]
for all five modes applied to the same feature files side by side, with the exact before/after content and
generated reports for each, plus the command-line override in action.

== Tracking Implementation Progress

Setting `trackProgress = true` (with `sourceDirs` and `glueCodeDirs` configured) switches the generated document
from a flat list of scenario titles to a breakdown of every scenario's implementation status, plus a summary
table.

Each scenario is classified as exactly one of:

[cols="1,3",options="header"]
|===
| Status        | Meaning
| `listed`      | The scenario has a title only; it has no step lines (`Given`/`When`/`Then`/`And`/`But`/`*`) yet.
| `defined`     | The scenario has steps, but at least one step has no matching glue code in `glueCodeDirs`.
| `implemented` | The scenario has steps, and every step has matching glue code in `glueCodeDirs`.
|===

Glue code is matched by scanning every directory in `glueCodeDirs` recursively for `@Given`/`@When`/`@Then`/`@And`/`@But`
step definitions and comparing each scenario step's text against every step definition pattern found across
all of them, using the same https://github.com/cucumber/cucumber-expressions[Cucumber Expressions] (or regular
expression) matching Cucumber-JVM itself uses at runtime. The step's keyword (`Given`/`When`/`Then`/`And`/`But`)
or `*` is not taken into account, matching Cucumber-JVM's own behaviour of matching step text against all registered
definitions regardless of keyword.

Enabling `trackProgress` also forces `groupByFeature = true` (see "Grouping by Feature" above): within each of
the Listed/Defined/Implemented sections, scenarios are further grouped under their enclosing `Feature`.

`sourceDirs` and `glueCodeDirs` don't need to line up one-to-one — every feature file found across all of
`sourceDirs` is checked against the combined set of step definitions found across all of `glueCodeDirs`. This is
useful when feature files or glue code are split across multiple source sets or modules, e.g.:

[source,groovy]
----
gherkinToAsciidoc {
    sourceDirs.from('src/test/resources/features/auth', 'src/test/resources/features/billing')
    glueCodeDirs.from('src/test/java/com/example/auth/steps', 'src/test/java/com/example/billing/steps')
    trackProgress = true
}
----

Given the following feature file:

[source,gherkin]
----
Feature: User authentication

  Scenario: User requests a password reset
    #  not yet fleshed out

  Scenario: User logs in successfully
    Given the login page is open
    When the user submits valid credentials
    Then the dashboard is displayed

  Scenario Outline: User logs in with different credential sets
    Given the login page is open
    When the user submits "<username>" and "<password>"
    Then the result is "<outcome>"

    Examples:
      | username | password | outcome |
      | alice    | secret   | success |
      | bob      | wrong    | failure |
----

and the following glue code in `glueCodeDirs`:

[source,java]
----
public class LoginSteps {

    @Given("the login page is open")
    public void theLoginPageIsOpen() { }

    @When("the user submits valid credentials")
    public void theUserSubmitsValidCredentials() { }

    @Then("the dashboard is displayed")
    public void theDashboardIsDisplayed() { }
}
----

the plugin generates:

[source,asciidoc]
----
= Feature Scenarios
:toc:
:toclevels: 2

System Under Test version: 1.0.0

This document lists every `Scenario` and `Scenario Outline` found under the configured feature file
directories, classified by how far each one is toward being automated.

Every scenario is classified as exactly one of:

[cols="1,3",options="header"]
|===
| Status | Meaning

| Listed
| Scenarios with a title only. No `Given`/`When`/`Then` steps have been written for them yet.

| Defined
| Scenarios with steps written, but at least one step has no matching glue code yet.

| Implemented
| Scenarios whose every step has matching glue code.
|===

== Progress Summary

[cols="1,1,1",options="header"]
|===
| Status | Count | Percentage

| Listed
| 1
| 33.3%

| Defined
| 1
| 33.3%

| Implemented
| 1
| 33.4%
|===

Scenarios with a title only. No `Given`/`When`/`Then` steps have been written for them yet.

=== User authentication

* Scenario: User requests a password reset

== Defined

Scenarios with steps written, but at least one step has no matching glue code yet.

=== User authentication

* Scenario Outline: User logs in with different credential sets

== Implemented

Scenarios whose every step has matching glue code.

----

[NOTE]
====
The percentages are always rounded so that the three figures add up to exactly 100%.

The `Scenario Outline` shares its first step (`the login page is open`) with the fully implemented scenario

====

== Report Snippets and Custom Templates

Whenever `trackProgress` is `true`, the plugin writes three snippet files to `snippetDir` -
`listed.adoc`, `defined.adoc`, and `implemented.adoc` - containing exactly the scenario bullets
that status's section would otherwise embed. These are written unconditionally, regardless of
whether `template` is configured.

When `groupByFeature` is also `true` (the default whenever `trackProgress` is `true`), a status
with at least one scenario writes one snippet file *per feature* instead of a single flat file, at
`<snippetDir>/<camelCaseFeatureTitle>/<status>.adoc` - e.g. `Feature: User authentication` becomes
the directory `userAuthentication`. A status with no scenarios at all still writes a single flat
`<snippetDir>/<status>.adoc` containing `_None._`, since there's no feature to group under.

By itself, this doesn't change the generated report: without a `template`, scenario titles are still
embedded directly, exactly as described above - the snippet files are simply written alongside it.

=== Rendering the Report From a Template

Setting `template` to a https://github.com/spullara/mustache.java[Mustache] file switches the report
itself from embedding scenario titles verbatim to referencing the snippets via `include::` directives.
The plugin renders `template` with the following context:

[cols="1,3a",options="header"]
|===
| Variable | Description

| `systemUnderTestVersion`
| The configured `systemUnderTestVersion` (or the project's own `version` when not overridden).

| `intro`
| The one-sentence description of what the document contains.

| `legend`
| List of `\{status, meaning}` - the three rows of the status legend table.

| `summary`
| List of `\{status, count, percentage}` - the three rows of the progress summary table.

| `sections`
| List of `\{status, blurb, features, snippet}`, one per status, in Listed/Defined/Implemented order. Each entry has:

* `status` - the same display label as in `legend`, e.g. `Implemented`.
* `blurb` - the same one-sentence explanation as `legend`'s `meaning` for this status, repeated here so a
  template can print it under the status heading without a separate lookup.
* `features` - a list of `\{title, snippet}` when `groupByFeature` is `true` and the status has at least one
  scenario; empty otherwise, in which case `snippet` (below) holds the flat fallback path instead.
* `snippet` - the flat fallback snippet path, only meaningful when `features` is empty.

Every `snippet` path (here and inside `features`) is already relative to the output file's directory, so a
plain +include::{{{snippet}}}[]+ resolves correctly.
|===

[IMPORTANT]
====
Use triple-mustache (+{{{value}}}+) or +{{&value}}+ for every substitution. Plain +{{value}}+
HTML-escapes its output (`<`, `>`, `&`, `'`, `"`), which would corrupt AsciiDoc syntax and any
scenario or feature title containing those characters.
====

== Tracking Progress History

NOTE: For a complete field-by-field reference to `progressHistoryFile` - its exact JSON schema, fingerprint algorithm, lifecycle semantics, and guidance for building tooling (including a visualization UI) around it - see link:docs/progress-history-file-format.adoc[Progress History File Format].

Setting `trackProgressHistory = true` (in addition to `trackProgress = true`) persists, across builds, a per-scenario history of when each scenario first reached `listed`, `defined`, and `implemented` status.
The history is keyed by a fingerprint of the scenario's own name, not by which feature file it lives in, so it survives a scenario being moved between feature files.
The plugin itself has no dependency on git or any other version control system - branch-based control over when to advance the history (e.g. "only on `main`") is entirely a CI concern, expressed through `updateProgressHistory`.

[cols="1,1,1,3",options="header"]
|===
| Property                | Type            | Default                              | Description
| `trackProgressHistory`  | Boolean         | `false`                              | When `true`, loads, advances, and reports from a persisted per-scenario progress history file.
Requires `trackProgress = true`; fails `generateFeatureDocs` with a descriptive error otherwise.
| `progressHistoryFile`   | File            | `gherkin-progress-history.ndjson` (project directory) | The NDJSON file the history is read from and, when `updateProgressHistory` is `true`, written back to.
Deliberately defaults into the project directory, not `build/`, since it's meant to be committed. Only consulted when `trackProgressHistory` is `true`.
| `updateProgressHistory` | Boolean         | same as `trackProgressHistory`       | When `true`, `progressHistoryFile` is written back to disk after being updated with the current run's scenarios.
The file is always *read* when `trackProgressHistory` is `true`, regardless of this property - so the generated report always reflects the up-to-date history, whether or not this run persists it. Overridable for the whole build via the `-PgherkinToAsciidoc.updateProgressHistory` project property.
|===

[IMPORTANT]
====
`trackProgressHistory` does *not* imply `trackProgress` - both must be set explicitly.
Enabling `trackProgressHistory` while `trackProgress` is `false` fails `generateFeatureDocs` with a descriptive error.

The `-PgherkinToAsciidoc.updateProgressHistory=<true|false>` project property, when set, overrides `updateProgressHistory` for every project in the build regardless of what any project's own `gherkinToAsciidoc { }` block configures - see "Advancing History Only on Certain Branches" below. An unrecognised value fails `generateFeatureDocs` with a descriptive error too.
====

Like any other Gradle task, `generateFeatureDocs` is skipped as `UP-TO-DATE` when none of its declared inputs have changed since the last run.
`progressHistoryFile`'s configured *path* (not its content, which the task itself manages) is one of those tracked inputs, so renaming or relocating it in the build script is, on its own, enough to make the task run again and write history to the newly configured location.
If a run is skipped for some other reason and you need to force it regardless (e.g. after manually editing `progressHistoryFile`), pass `--rerun`:

[source,shell]
----
./gradlew generateFeatureDocs --rerun
----

=== How Scenarios Are Matched Across Runs

Every scenario is identified by a fingerprint computed from its own name alone: the `Scenario:`/`Scenario Outline:` keyword and any existing index prefix (see "Numbering Features and Scenarios" above) are stripped, the remainder is trimmed and lower-cased, and the result is hashed with SHA-256, truncated to its first 16 hex characters.
Because the fingerprint never takes the enclosing `Feature` into account, a scenario keeps its history even after being cut from one feature file and pasted into another, as long as its own name doesn't change.

On every run, each of the current scenarios is looked up by fingerprint in the previously persisted history (or given a fresh record, if none exists), and classified exactly as `trackProgress` itself would (see "Tracking Implementation Progress" above).
Whichever of `listedAt`/`definedAt`/`implementedAt` matches that classification is stamped with the current time the first time it's observed, and is never overwritten afterwards - so a scenario that jumps straight from `listed` to `implemented` between two runs never gains a `definedAt` at all, and a scenario that later regresses (e.g. its glue code is deleted) doesn't lose the timestamp it already earned.
A scenario's `scenarioName` and `featureTitle` are refreshed to their current values on every run even though neither is part of the key, so a renamed-in-place scenario or one moved to a different feature shows up-to-date in the persisted file.
Both are persisted with the same keyword/index-prefix stripping the fingerprint itself uses (see above), so a scenario or feature getting renumbered - e.g. because `indexing` is on and an earlier one was inserted or removed elsewhere in the suite - never rewrites these fields; only an actual rename does.

A previously persisted record whose fingerprint is no longer present in the current scan is *never deleted* - it's kept exactly as it was, except its `removedAt` is stamped with the current time the first time it goes missing (and left alone on every subsequent run, once set).
If a scenario with the same fingerprint reappears in a later run (e.g. a revert), its `removedAt` is cleared and its other fields resume advancing normally.

=== File Format

`progressHistoryFile` is newline-delimited JSON (NDJSON) - one line per scenario - sorted by fingerprint so that git diffs stay minimal and stable regardless of how scenarios are reordered or moved between feature files.
Given the following feature file:

[source,gherkin]
----
Feature: User authentication

  Scenario: User logs in
    Given a registered user
    When they submit valid credentials
    Then they are signed in

  Scenario: User resets password
    Given a registered user
    When they request a password reset
----

after a few builds spread over several months, `progressHistoryFile` looks like:

[source,json]
----
{"schemaVersion":1}
{"fingerprint":"a1f3c9d0e21b7f44","scenarioName":"User logs in","featureTitle":"User authentication","listedAt":"2026-01-14T09:02:11Z","definedAt":"2026-02-03T16:40:00Z","implementedAt":"2026-02-20T11:15:44Z","lastSeenAt":"2026-08-12T07:00:00Z","removedAt":null}
{"fingerprint":"7be04412aa3390d1","scenarioName":"User resets password","featureTitle":"User authentication","listedAt":"2026-06-01T08:00:00Z","definedAt":null,"implementedAt":null,"lastSeenAt":"2026-08-12T07:00:00Z","removedAt":null}
----

The first line is a file-level `{"schemaVersion":N}` marker, always written, giving a future format change something to check against and branch reading logic on. It's purely additive: a file written before this existed simply has no such line, and is read exactly as it always was - the marker is optional on read, never required.

A missing `progressHistoryFile` is treated as an empty history, not an error - the first run on a fresh checkout simply starts every scenario's history from scratch.
A line that fails to parse (e.g. hand-edited into something invalid) is skipped with a `WARN`-level log message identifying its line number; it never fails the build.

The generated report reflects the loaded (and possibly just-advanced) history as a `== Progress Over Time` section, directly below `== Progress Summary`, once `trackProgressHistory` finds at least one record: the earliest timestamp across every record ("Tracked since", rendered as `yyyy-MM-dd HH:mm:ss UTC` rather than a raw ISO-8601 instant), how many scenarios were listed, defined, and implemented in the last 7 and 30 days, and how many previously tracked scenarios are no longer seen in the current run.

=== Advancing History Only on Certain Branches

Since the plugin has no notion of git branches (or any other VCS), gating *when* `progressHistoryFile` gets written back is entirely up to the CI pipeline invoking `generateFeatureDocs`, via `updateProgressHistory` (or its command-line override):

[source,bash]
----
# On a release/main branch: advance and commit the history.
./gradlew generateFeatureDocs -PgherkinToAsciidoc.updateProgressHistory=true

# On a feature branch or pull request build: read and report from the existing
# history, but never write it back - leaving it for the target branch's own
# build to advance once the change actually merges.
./gradlew generateFeatureDocs -PgherkinToAsciidoc.updateProgressHistory=false
----

Leaving `updateProgressHistory` at its default (equal to `trackProgressHistory`) works too for a single-branch setup with no CI-driven distinction; the override above is only needed once different branches should behave differently.
