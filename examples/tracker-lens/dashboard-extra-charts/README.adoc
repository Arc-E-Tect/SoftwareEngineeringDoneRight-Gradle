= Tracker Lens — Dashboard Extra Charts Example
:toc: left

== Description

Two trackers - `bdd-scenarios` (Gherkin scenarios) and `api-contracts` (API contracts) - rendered by
a project-supplied Mustache template, `dashboard-template.html`, overriding the plugin's own
bundled `dashboard.html` via `trackerLens.template`. The template's structure and wording are
identical to the bundled one (see `../custom-dashboard-template` for an example that changes those
instead); the only difference here is two extra, non-contract charts it adds beside each tracker's
built-in line chart.

== Intent

This example shows that a project-supplied template isn't limited to what `TrackerView` and
`MetricCardView` hand it via Mustache (`{{#metrics}}`, `{{#projection}}`, and so on) - it can add
its own markup and its own script to derive additional views the plugin itself never computes:

* Beside `bdd-scenarios`' line chart, a *pie chart* of which stage each scenario is *currently* at -
  `listed`, `defined`, or `implemented` - read directly from `#dashboard-data`'s `stageBreakdown`
  field. `bdd-scenarios`' own metric cards are rewritten in place to match: the plugin's default
  cumulative counts (`LISTED 6/6`, `DEFINED 4/6`, `IMPLEMENTED 4/6`) become the same
  `stageBreakdown` numbers the pie plots (`1/6`, `1/6`, `4/6`), so the boxes and the pie never
  disagree.
* `api-contracts`' own metric cards - rewritten in place, client-side, from the plugin's own three
  `declared`/`implemented`/`verified` labels and counts to `Undefined`/`Unimplemented`/`Unverified`
  - the same three checks this repository's `shadow-api-detector`, `mirage-api-detector`, and
  `doppelganger-api-detector` plugins run, named after what's *missing* rather than after the
  plugin that finds it - plus a fourth, appended card for `Compliant`, the endpoints none of the
  three checks flagged. Each card carries a hover-over "?" badge explaining the full compound
  condition it checks.
* Beside `api-contracts`' line chart, one *pie chart* with the same four names and counts as the
  metric cards above it - Undefined, Unimplemented, Unverified, Compliant - as absolute counts, not
  four separate "this check's share of the whole" percentages: since the four states are a genuine
  partition, one pie whose slices sum to the total says it more plainly than four would.

=== Why the Gherkin pie reads `stageBreakdown`, not `series`

A scenario's three stages are a real dependency chain - it can't be `implemented` without first
being `defined`, and can't be `defined` without first being `listed` - so it's tempting to derive
"how many scenarios are currently at each stage" from `series` (each stage's cumulative "reached at
least this stage" count) by subtracting consecutive stages: `series.listed - series.defined`, and so
on. That arithmetic is wrong in a specific, real case: `gherkin-to-asciidoc` stamps only the one
stage matching a scenario's status the *first time it's observed*, and never backfills earlier ones
- so a scenario the scanner first catches already fully implemented never gains a `defined` entry at
all (see that plugin's own `ProgressHistoryUpdater` javadoc). Subtracting `series` values silently
attributes that scenario to `listed` instead of `implemented`.

`stageBreakdown` doesn't have this problem: it's computed server-side, once, directly from each
scenario's own history (`LifecycleRecord.latestStage`), so it always reports the furthest stage
each scenario has actually reached, gaps and all. `gherkin-progress-history.ndjson` includes exactly
this case - `process-a-return`, listed on 2026-06-10 and observed already-implemented on 2026-08-01,
with no `definedAt` ever recorded - to prove it: the pie correctly counts it under `implemented`
(4 of 6), not `listed`.

=== Why the metric cards also get rewritten

Left alone, `bdd-scenarios`' own metric cards would still show the plugin's default cumulative
numbers - `LISTED 6/6`, `DEFINED 4/6`, `IMPLEMENTED 4/6` - each correct on its own terms (six
scenarios have been listed at some point, four have been defined at some point, four have been
implemented at some point), but placed right above a pie built from a *different* metric
(`stageBreakdown`'s 1, 1, 4), the two numbers disagree enough to read as a bug rather than two
legitimately different things being counted. `applyStageBreakdownToMetricCards` rewrites the
cards' count, percentage, and `--percent` fill-bar in place to the same `stageBreakdown` numbers
the pie already uses, so the boxes and the chart beside them always tell the same story:

[source,javascript]
----
function applyStageBreakdownToMetricCards(trackerId, tracker, totalCount) {
  var section = document.querySelector('.tracker[data-tracker="' + trackerId + '"]');
  var breakdown = tracker.stageBreakdown || {};
  tracker.stages.forEach(function (stage) {
    var card = section.querySelector('.metric-card[data-stage="' + stage + '"]');
    var count = breakdown[stage] || 0;
    var percent = totalCount ? Math.round((100 * count) / totalCount) : 0;
    card.style.setProperty('--percent', percent);
    card.querySelector('.metric-card__count').textContent = count + ' / ' + totalCount;
    card.querySelector('.metric-card__percent').textContent = percent + '%';
  });
}
----

Unlike `api-contracts`' cards (below), the stage *names* here stay exactly as the plugin renders
them (`listed`/`defined`/`implemented`) - only the numbers change, since these three genuinely are
the tracker's own canonical stages, just reported a different way.

=== Why Undefined/Unimplemented/Unverified don't sum to 100% (but all four states do)

Undefined (implemented, no OpenAPI description - what `shadow-api-detector` calls a "Shadow API"),
Unimplemented (described, no implementation - a "Mirage API"), and Unverified (described and
implemented, no test confirming the two agree - a "Doppelganger API") are three *independent*
checks on the same 20 endpoints - not stages of one pipeline the way `bdd-scenarios`'
`listed`/`defined`/`implemented` are. An endpoint can fail zero, one, two, or three of them
independently, so nothing says their percentages (20%, 35%, 25%) have to sum to 100%, and they
don't.

That's easy to misread as "the numbers don't add up" in the bad sense, so a fourth card -
`Compliant`, the endpoints none of the three checks flagged - exists specifically so a reader can
check for themselves: `Undefined + Unimplemented + Unverified + Compliant` *does* always equal
`totalCount` (4 + 7 + 5 + 4 = 20 here), because those four states are a complete, non-overlapping
partition, even though the three *checks'* own percentages aren't. `Compliant`'s count is exactly
`verifiedCount` - the plugin's own `verified` metric, already computed, just relabeled. The pie
beside the line chart makes the same point visually: one chart, four slices, summing to the whole -
not four separate pies each needing its own "and the rest" complement explained.

The relationship between all four counts, and the two raw totals (`declared`/`implemented`) the
plugin itself reports, is fully determined - see
link:../../../tracker-lens/DASHBOARD-THEMING.adoc#shadow-mirage-doppelganger-compliant-math[the
tracker-lens documentation] for the worked formula.

== The Template

`dashboard-template.html` keeps the bundled template's `<section class="tracker">`, `<h2>{{id}}</h2>`,
`.metrics` grid of `.metric-card` divs, and `.projection` markup exactly as-is, plus one small
addition - a `data-total="{{totalCount}}"` attribute on each metric card, since `totalCount` is
rendered into the static markup but never included in the `#dashboard-data` JSON blob, and the
script needs it to compute each check's share:

[source,html]
----
<div class="metric-card" data-stage="{{stage}}" data-total="{{totalCount}}" style="--percent: {{percent}}">
----

The only structural addition beyond that is wrapping each tracker's `.chart` div in a flex row
alongside a second, empty `.chart-extra` div the template's own script fills in:

[source,html]
----
<div class="charts-row">
<div class="chart"><canvas></canvas></div>
<div class="chart-extra" data-extra-chart-for="{{id}}"></div>
</div>
----

=== Relabeling The Metric Cards, And Adding A Fourth

The plugin always renders api-contracts' metric cards as `declared`/`implemented`/`verified` -
that's `MetricCardView`'s fixed output, not something a template's Mustache markup can change. This
template's script rewrites those three cards' label, count, percentage, and `--percent` fill-bar
style in place after the page loads, using the exact same `Undefined`/`Unimplemented`/`Unverified`
names and counts the pie below uses - computed once and shared by both, so the two can never drift
apart - then appends a fourth `.metric-card` for `Compliant`, since the plugin never renders one
itself (there's no fourth canonical stage to render it from):

[source,javascript]
----
function computeApiContractBreakdown(tracker, totalCount) {
  var counts = latestCounts(tracker);
  var declared = counts.declared || 0;
  var implemented = counts.implemented || 0;
  var verified = counts.verified || 0;
  return [
    { label: 'Undefined', count: totalCount - declared, cardTotal: implemented, color: stageColors[0] },
    { label: 'Unimplemented', count: totalCount - implemented, cardTotal: declared, color: stageColors[1] },
    { label: 'Unverified', count: declared + implemented - totalCount - verified, cardTotal: totalCount, color: stageColors[2] },
    { label: 'Compliant', count: verified, cardTotal: totalCount, color: COMPLIANT_COLOR }
  ];
}
----

Each entry carries its own `cardTotal` - the denominator *the card* divides by, which for two of the
four is deliberately narrower than `totalCount`. `Undefined` (Shadow) is by definition a subset of
the *implemented* endpoints - implemented, just never declared - so "4 of the 13 implemented
endpoints have no OpenAPI description" is a more useful ratio than "4 of 20 endpoints" would be;
symmetrically, `Unimplemented` (Mirage) is a subset of the *declared* endpoints, so it divides by
`declared` instead. `Unverified` and `Compliant` are both subsets of the declared-and-implemented
overlap rather than of one single other metric, so they keep `totalCount`. The pie beside the line
chart is unaffected by this - its slices are still sized and its tooltip still labeled against the
one shared `totalCount`, since a pie's slices only mean anything as shares of the same whole.

The appended card gets its own fixed color (`COMPLIANT_COLOR`, a violet, picked to stay visually
distinct from all three `--dashboard-stage-*` colors a lens might define) rather than reusing one of
them - `Compliant` isn't one of the plugin's own canonical stages the way
`Undefined`/`Unimplemented`/`Unverified` are, so there's no stage index for a lens to color it by,
and nothing stops a lens's own `--dashboard-stage-2` from also being some shade of green.

=== The Hover-Over Definitions

A small circled `?`, appended next to each card's name - the three relabeled ones and the appended
`Compliant` one alike - carries the check's full definition as a plain HTML `title` attribute, so
hovering it shows the browser's native tooltip with no extra library:

[source,javascript]
----
var CHECK_DEFINITIONS = {
  Undefined: 'Endpoint is implemented using Spring RestController, but there is no OpenAPI description.',
  Unimplemented: 'An OpenAPI description exists, but no implementation.',
  Unverified: 'An OpenAPI description exists, the endpoint is implemented using Spring RestController, '
      + 'but no test exists confirming the implementation still matches the OpenAPI description.',
  Compliant: 'An OpenAPI description exists, the endpoint is implemented using Spring RestController, '
      + 'and at least one test exists confirming the implementation matches the OpenAPI description.'
};
----

== The Sample Data

`gherkin-progress-history.ndjson` has 6 scenarios: 3 fully `implemented`, 1 `defined` only, 1
`listed` only, and 1 - `process-a-return` - that skipped `defined` entirely (see above).

`api-contract-history.ndjson` has 20 endpoints: 4 Undefined/Shadow, 7 Unimplemented/Mirage, 5
Unverified/Doppelganger, and 4 Compliant - e.g. `GET /api/internal/debug-info` (implemented, never
declared: Undefined), `DELETE /api/orders/{id}/archive` (declared, never implemented:
Unimplemented), `PATCH /api/customers/{id}` (declared and implemented in June, still not verified:
Unverified), and `GET /api/orders/{id}` (declared, implemented, and verified: Compliant).

== Configuration

[source,groovy]
----
trackerLens {
    template = file('dashboard-template.html')

    trackers {
        register('bdd-scenarios') {
            historyFiles.from(file('gherkin-progress-history.ndjson'))
            source = com.arc_e_tect.gradle.trackerlens.TrackerSourceKind.GHERKIN_SCENARIO
        }
        register('api-contracts') {
            historyFiles.from(file('api-contract-history.ndjson'))
            source = com.arc_e_tect.gradle.trackerlens.TrackerSourceKind.API_CONTRACT
        }
    }
}
----

== Build And Run

[source,bash]
----
cd examples/tracker-lens/dashboard-extra-charts
./gradlew generateTrackerLensDashboard
----

== What To Expect

The build is expected to pass, including the same `ContractRule` validation every dashboard goes
through regardless of which template rendered it. Open `build/reports/tracker-lens/dashboard.html`:

* `bdd-scenarios` (6 scenarios total) shows three metric cards reading `LISTED 1 / 6 (17%)`,
  `DEFINED 1 / 6 (17%)`, `IMPLEMENTED 4 / 6 (67%)` - `stageBreakdown` numbers, not the plugin's
  default cumulative ones - plus its usual line chart and a pie chart, legend to its left, with the
  same three slices: 1 (`listed` only), 1 (`defined` only), 4 (`implemented`, including the
  skip-scenario) - correctly the largest slice, since most scenarios really are done. Hovering a
  slice shows "listed: 1 / 6", "defined: 1 / 6", "implemented: 4 / 6".
* `api-contracts` shows four metric cards - `UNDEFINED 4 / 13 (31%)`, `UNIMPLEMENTED 7 / 16 (44%)`,
  `UNVERIFIED 5 / 20 (25%)`, and `COMPLIANT 4 / 20 (20%)` - each with a `?` badge; its usual line
  chart (still labeled declared/implemented/verified - the raw history, unchanged); and one pie
  beside it, legend to its left, with four slices sized 4, 7, 5, 4 - summing visibly to 20, the
  tracker's total, each a distinct color including `Compliant`'s violet. Hovering a slice shows
  "Undefined: 4 / 20", and so on for the other three - the pie's own tooltip always divides by the
  shared total, even where the card above it divides by something narrower.

Switching lenses still works exactly as in `../plain`, since the lens switcher and every
contract-bound element are untouched - only the two added charts and their surrounding layout are
this template's own, unlensed markup.
