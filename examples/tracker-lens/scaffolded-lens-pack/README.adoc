= Tracker Lens — Scaffolded Lens Pack Example
:toc: left

== Description

Demonstrates `bootstrapTrackerLensProject`: running one task against an empty project and getting
a working, two-project setup back - the lens CSS, the Gradle project to publish it, and a sample
project to test it against - with nothing hand-written at all.

== Intent

Every other example under `examples/tracker-lens/` is a project written by hand to demonstrate one
feature of the DSL. This one demonstrates the opposite path: run `bootstrapTrackerLensProject` and
get a complete, runnable pair of projects back.

Earlier versions of this example checked the generated output in under `generated/`, as a frozen,
byte-for-byte snapshot of what the task had produced. That stopped being the right approach once
the scaffolded sample project started generating its own calibrated fixture data - dated to
whenever it's actually built - instead of reading a static file: a frozen copy of *that* output
would already be misleading the day after it was captured, and actively wrong the moment the
bootstrap task's own template next changes, with nothing in the repository ever flagging the
mismatch.

This repository's CI workflow for this example runs `bootstrapTrackerLensProject` fresh instead:
publishes the generated lens pack, builds the generated sample project's dashboard, and asserts the
*shape* of what came out - both trackers registered, the dashboard renders, the lens switcher
includes the scaffolded lens - rather than diffing against a golden file. See
`.github/workflows/example-tracker-lens-scaffolded-lens-pack-build.yml` in this repository's root
for exactly what it checks.

== Try It Yourself

[source,bash]
----
mkdir scaffold-demo && cd scaffold-demo
cat > settings.gradle <<'EOF'
rootProject.name = 'scaffold-demo'
EOF
cat > build.gradle <<'EOF'
plugins {
    id 'com.arc-e-tect.tracker-lens' version '1.4.0'
}
EOF
gradle bootstrapTrackerLensProject

cd tracker-lens-bootstrap/lens-pack
gradle publish

cd ../sample-project
gradle generateTrackerLensDashboard
----

== What To Expect

Both builds pass. `lens-pack`'s build publishes to `lens-pack/build/localMaven`; `sample-project`'s
build first generates a calibrated sample fixture via `generateTrackerLensFixture` (wired as a
dependency of `generateTrackerLensDashboard`), then writes
`sample-project/build/reports/tracker-lens/dashboard.html`, whose lens switcher includes `my-lens`
alongside the three built-ins - exactly as `LENS_TUTORIAL.adoc` describes. Re-running
`generateTrackerLensDashboard` days later regenerates the fixture fresh, dated to whenever you
actually run it, rather than showing the same data forever.

See the `tracker-lens` module's own `README.adoc` for what `bootstrapTrackerLensProject` and
`generateTrackerLensFixture` do in more detail.
