= API-Only Suite — With All Three Gaps Example
:toc: left

== Description

This example applies the Arc-E-Tect API-Only Suite plugin to a small `ItemController` and OpenAPI document
that were deliberately drifted apart in all three ways the suite's three underlying plugins each catch:

[cols="1,3",options="header"]
|===
| Gap                       | Endpoint
| Shadow API                | `GET /items/{id}` - implemented by `ItemController.getItem`, never described in `openapi.yaml`.
| Mirage API                | `POST /items` - described in `openapi.yaml` as `createItem`, never implemented.
| Doppelganger API          | `GET /items` - both described and implemented (`ItemController.listItems`), but this module has no `src/test/java` and no `src/test/resources/contracts`, so no verification evidence exists for it.
|===

== Intent

This is the suite plugin's canonical "why this exists" example: one `apiOnlySuite { rootDocument = ... }`
block and one `./gradlew detectAllApiGaps` run finds all three kinds of drift in a single pass, exactly the
way applying all three plugins individually and configuring each one's `rootDocument` separately would - but
in one step, with no plugin left out by oversight.

== A Note On How This Example Applies The Plugin

Like the Doppelganger API Detector example, this example does not resolve `com.arc-e-tect.api-only-suite`
from the Gradle Plugin Portal, since the suite plugin has not had its first release yet (see the module
README's "Versioning" notes). Instead, this example resolves the plugin from `mavenLocal()` -
`settings.gradle` adds `mavenLocal()` (and `mavenCentral()`, for its transitive dependencies) to
`pluginManagement.repositories`, and `build.gradle` applies it as `id 'com.arc-e-tect.api-only-suite' version
'0.0.0'`, matching the version the plugin's own `gradle.properties` currently publishes under.

Before building this example, publish the suite plugin - and `api-detector-core`, `shadow-api-detector`,
`mirage-api-detector`, and `doppelganger-api-detector`, all of which it depends on and all of which get
published alongside it as subprojects of the same build - to your local Maven repository:

[source,bash]
----
cd api-only-suite
./gradlew publishToMavenLocal
----

Once the plugin has a first Gradle Plugin Portal release, this example should switch to
`alias(libs.plugins.api.only.suite)`, matching the Shadow and Mirage examples, for consistency.

== Build And Run

[source,bash]
----
cd examples/api-only-suite/with-all-three-gaps
./gradlew detectAllApiGaps
----

This example does not enable `failOnShadow`/`failOnMirage`/`failOnDoppelganger`, so the build succeeds - the
point of this example is to show all three reports being generated by one aggregate task, not to demonstrate
a failing build (the individual plugins' own examples already cover that). `./gradlew build` also runs all
three detectors, since this example wires `detectAllApiGaps` into the `check` lifecycle task explicitly in
`build.gradle`.

== What To Expect

All three reports are written under `build/reports/`:

* `shadow-api-detector/shadow-apis.adoc` lists `GET /items/{id}`.
* `mirage-api-detector/mirage-apis.adoc` lists `POST /items` (`createItem`).
* `doppelganger-api-detector/doppelganger-apis.adoc` lists `GET /items` (`listItems`).

The console output from `./gradlew detectAllApiGaps` shows all three detectors ran:

[source]
----
> Task :detectShadowApis
Shadow API Detector: scanned 2 endpoint(s), found 1 shadow API(s). Report → .../shadow-apis.adoc

> Task :detectMirageApis
Mirage API Detector: scanned 2 described endpoint(s), found 1 mirage API(s). Report → .../mirage-apis.adoc

> Task :detectDoppelgangerApis
Doppelganger API Detector: scanned 1 declared-and-implemented endpoint(s), found 1 doppelganger API(s). Report → .../doppelganger-apis.adoc
----

== Suggested Fix

* Add `GET /items/{id}` to `openapi.yaml` (fixes the shadow API), or remove the handler if it was never meant to ship.
* Implement `createItem` in `ItemController`, or remove `POST /items` from `openapi.yaml` if it was never meant to ship (fixes the mirage API).
* Add verification evidence for `GET /items` using any of Doppelganger API Detector's three supported mechanisms (fixes the doppelganger API).
