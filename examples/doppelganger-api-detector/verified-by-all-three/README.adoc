= Doppelganger API Detector — Verified By All Three Sources Example
:toc: left

== Description

This example applies the Doppelganger API Detector plugin to an `ItemController` with four endpoints, each
declared in `openapi.yaml` and implemented, but verified in a different way:

[cols="1,3",options="header"]
|===
| Endpoint            | Verified by
| `GET /items`        | A real Spring RestDocs test (`ItemControllerRestDocsTest`).
| `GET /items/{id}`    | A real REST Assured test with live OpenAPI validation (`ItemControllerValidatorTest`).
| `PUT /items/{id}`    | A real Spring Cloud Contract file (`shouldUpdateItem.groovy`), whose concrete example URL is `/items/1`.
| `DELETE /items/{id}` | **Nothing.** No test, no contract file - deliberately left unverified.
|===

`failOnDoppelganger` is enabled; the build is expected to **fail**, on exactly the fourth endpoint.

== Intent

The three companion `verified-by-*` examples each show one mechanism working in isolation. This example shows
that all three compose in a single project - each endpoint gets checked against whichever mechanism actually
covers it, with no cross-talk between them - and, just as importantly, that mixing all three does not create a
false sense of complete coverage: `deleteItem` has none of the three, and detection still catches it precisely
because it is missing evidence, not because a mechanism was misconfigured.

`PUT /items/{id}` deliberately reuses the same path template as `GET /items/{id}` and `DELETE /items/{id}` -
distinguished only by verb - to show that Spring Cloud Contract's concrete example URL (`/items/1`) is matched
against the *templated* endpoint correctly (via `PathMatcher.matchesConcrete(...)` in `api-detector-core`; see
the `verified-by-spring-cloud-contract` example's README for the full explanation), not just against endpoints
that happen to have no path variable at all.

== Build And Run

[source,bash]
----
cd examples/doppelganger-api-detector/verified-by-all-three
./gradlew build
----

`detectDoppelgangerApis` runs before the test suite in this build's task graph and fails first, so
`./gradlew build` stops there without reaching `test`. To confirm the two real tests
(`ItemControllerRestDocsTest`, `ItemControllerValidatorTest`) genuinely pass on their own, run:

[source,bash]
----
./gradlew test
----

== What To Expect

`./gradlew build` fails on exactly one endpoint:

[source]
----
> Task :detectDoppelgangerApis FAILED
Doppelganger API Detector: scanned 4 declared-and-implemented endpoint(s), found 1 doppelganger API(s).
doppelgangerApiDetector: found 1 doppelganger API(s) declared and implemented but not verified by any configured contract verification source.
----

`build/reports/doppelganger-api-detector/doppelganger-apis.adoc` lists exactly `DELETE /items/{id}`
(`deleteItem`) - `listItems`, `getItem`, and `updateItem` do not appear, since all three have verification
evidence from their respective source.

`./gradlew test` succeeds independently, confirming the RestDocs and REST Assured tests are genuinely working
code, not just source shapes the scanner happens to recognise.

== Suggested Fix

Add verification evidence for `deleteItem` using any of the three mechanisms - a RestDocs test, a validated
REST Assured test, or a Spring Cloud Contract file - or remove the operation from `openapi.yaml` if it was
never meant to ship.
