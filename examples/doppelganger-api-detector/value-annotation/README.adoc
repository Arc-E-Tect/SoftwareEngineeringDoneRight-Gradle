= Doppelganger API Detector — @Value Annotation Example
:toc: left

== Description

This example applies the Doppelganger API Detector plugin to a `UserController` with two
endpoints:

[cols="1,3",options="header"]
|===
| Endpoint      | Verified by
| `GET /v1/users/{username}` (`getUserByUsername`) | A real, passing Spring RestDocs test (`UserControllerRestDocsTest`) that resolves its request path via a field annotated `@Value("${users.by-username}")`, injected by Spring from `application.properties`, not a string literal.
| `GET /v1/users` (`listUsers`) | **Nothing.** No test at all - deliberately left unverified.
|===

`failOnDoppelganger` is enabled; the build is expected to **fail**, on exactly `listUsers`.

== Intent

By default the scanners only resolve request paths that are string literals, local
variables/fields initialized with a literal, or class constants — a field populated by Spring's
dependency injection is invisible to them, since nothing in the source file itself shows what
value ends up there. Real-world contract tests commonly resolve endpoint paths (or base URLs)
this way instead, e.g. `@Value("${iff.base-url}")` in the accompanying book's User Account
microservice example code.

Without the plugin knowing where `${users.by-username}` resolves, `getUserByUsername`'s test
would be invisible to it, and the endpoint would be wrongly reported as a doppelganger API
despite being genuinely covered — a false positive. Configuring `propertyFiles` (the same
`application.properties` file Spring itself resolves the placeholder from) tells the plugin,
out of band, what value the annotated field ends up holding — without giving the scanner a
symbol solver, a Spring context, or classpath access.

This example proves two things at once: that the `@Value`-injected `usersByUsernamePath` field
is recognised as verification evidence for `getUserByUsername` (it does *not* appear in the
failure below), and that the detector genuinely still catches `listUsers`, which has no
evidence anywhere. A build that always succeeds proves nothing about whether detection
actually works - this example is designed to fail on exactly one endpoint, so the failure
itself is the demonstration.

== The Controller, Properties File, And Test

[source,java]
----
@RestController
@RequestMapping("/v1/users")
public class UserController {

    @GetMapping("/{username}")
    public String getUserByUsername(@PathVariable String username) { return "{}"; }

    @GetMapping
    public String listUsers() { return "[]"; }
}
----

[source,properties]
----
# src/test/resources/application.properties
users.by-username=/v1/users/{username}
----

[source,java]
----
@WebMvcTest(UserController.class)
@AutoConfigureRestDocs
class UserControllerRestDocsTest {

    @Autowired
    private MockMvc mockMvc;

    @Value("${users.by-username}")
    private String usersByUsernamePath;

    @Test
    void getUserByUsername() throws Exception {
        mockMvc.perform(get(usersByUsernamePath, "alice"))
                .andExpect(status().isOk())
                .andDo(document("get-user-by-username"));
    }
}
----

`openapi.yaml` declares both `GET /v1/users/{username}` and `GET /v1/users`, matching the
controller. Only `getUserByUsername` has a test.

[source,groovy]
----
doppelgangerApiDetector {
    rootDocument = file('src/main/resources/openapi/openapi.yaml')
    testDirs.from('src/test/java')

    propertyFiles.from('src/test/resources/application.properties')

    failOnDoppelganger = true
}
----

== Build And Run

[source,bash]
----
cd examples/doppelganger-api-detector/value-annotation
./gradlew build
----

`detectDoppelgangerApis` runs before the test suite in this build's task graph and fails first,
so `./gradlew build` stops there without reaching `test`. To confirm the real RestDocs test
genuinely passes on its own, run:

[source,bash]
----
./gradlew test
----

== What To Expect

`./gradlew build` fails on exactly `listUsers`:

[source]
----
> Task :detectDoppelgangerApis FAILED
Doppelganger API Detector: scanned 2 declared-and-implemented endpoint(s), found 1 doppelganger API(s).
doppelgangerApiDetector: found 1 doppelganger API(s) declared and implemented but not verified by any configured contract verification source.
----

`build/reports/doppelganger-api-detector/doppelganger-apis.adoc` lists exactly `GET /v1/users`
(`listUsers`) - `getUserByUsername` does not appear, since `propertyFiles` lets the scanner
resolve the `@Value`-injected field and recognise it as real verification evidence.

`./gradlew test` succeeds independently, confirming the RestDocs test is genuinely working
code.

== Suggested Fix

Add a RestDocs test for `listUsers`, or remove it from `openapi.yaml` if it was never meant to
be covered by this mechanism.
