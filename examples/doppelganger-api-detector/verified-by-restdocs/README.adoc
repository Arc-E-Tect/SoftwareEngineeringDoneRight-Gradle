= Doppelganger API Detector — Verified By RestDocs Example
:toc: left

== Description

This example applies the Doppelganger API Detector plugin to an `ItemController` with two endpoints:

[cols="1,3",options="header"]
|===
| Endpoint      | Verified by
| `GET /items/{id}` (`getItem`) | A real, passing Spring RestDocs test (`ItemControllerRestDocsTest`), using the real `spring-restdocs-mockmvc` library, not a structural stand-in.
| `GET /items` (`listItems`)    | **Nothing.** No test at all - deliberately left unverified.
|===

`failOnDoppelganger` is enabled; the build is expected to **fail**, on exactly `listItems`.

== Intent

This example proves two things at once: that a real `mockMvc.perform(get(...)).andDo(document(...))` call
chain is recognised as verification evidence for `getItem` (it does *not* appear in the failure below), and
that the detector genuinely still catches `listItems`, which has no evidence anywhere. A build that always
succeeds proves nothing about whether detection actually works - this example is designed to fail on exactly
one endpoint, so the failure itself is the demonstration.

Note that `getItem` is declared with a path variable (`/items/{id}`) - Spring's `MockMvcRequestBuilders`/
`RestDocumentationRequestBuilders` use the same `{id}`-style template syntax as the OpenAPI document itself, so
the scanner's string-literal path capture matches the OpenAPI path template exactly.

== The Controller, Document, And Test

[source,java]
----
@RestController
@RequestMapping("/items")
public class ItemController {

    @GetMapping("/{id}")
    public String getItem(@PathVariable Long id) { return "{}"; }

    @GetMapping
    public String listItems() { return "[]"; }
}
----

[source,java]
----
@WebMvcTest(ItemController.class)
@AutoConfigureRestDocs
class ItemControllerRestDocsTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void getItem() throws Exception {
        mockMvc.perform(get("/items/{id}", 1))
                .andExpect(status().isOk())
                .andDo(document("get-item"));
    }
}
----

`openapi.yaml` declares both `GET /items/{id}` and `GET /items`, matching the controller. Only `getItem` has a
test.

== Build And Run

[source,bash]
----
cd examples/doppelganger-api-detector/verified-by-restdocs
./gradlew build
----

`detectDoppelgangerApis` runs before the test suite in this build's task graph and fails first, so
`./gradlew build` stops there without reaching `test`. To confirm the real RestDocs test genuinely passes on
its own, run:

[source,bash]
----
./gradlew test
----

== What To Expect

`./gradlew build` fails on exactly `listItems`:

[source]
----
> Task :detectDoppelgangerApis FAILED
Doppelganger API Detector: scanned 2 declared-and-implemented endpoint(s), found 1 doppelganger API(s).
doppelgangerApiDetector: found 1 doppelganger API(s) declared and implemented but not verified by any configured contract verification source.
----

`build/reports/doppelganger-api-detector/doppelganger-apis.adoc` lists exactly `GET /items` (`listItems`) -
`getItem` does not appear, since it has real verification evidence.

`./gradlew test` succeeds independently, confirming the RestDocs test is genuinely working code.

== Suggested Fix

Add a RestDocs test for `listItems`, or remove it from `openapi.yaml` if it was never meant to be covered by
this mechanism.
