= Single-Module Vanilla Example
:toc: left

== Description

This example applies the Architecture Validator plugin to a plain Java project with no Spring dependencies.
The code contains a deliberate Hexagonal Architecture boundary violation.

== Intent

This example is intended to show how the default generated rules detect a direct dependency from an application service to an adapter implementation.
It also shows how to inspect the generated HTML and XML architecture reports.

== Build And Run

[source,bash]
----
cd examples/architecture-validator/single-module-vanilla
./gradlew clean testArchitecture
----

== What To Expect

`OrderApplicationService` depends directly on `DatabaseAdapter`.
The project is configured with `ignoreFailures = true`, so the task completes successfully while still reporting violations in the generated report output.

Open `build/reports/architecture-validator/html/index.html` after running the suite.
The XML report is written under `build/reports/architecture-validator/xml/`.

== Pinning The JUnit Line

[source,groovy]
----
architectureValidator {
    basePackage = 'com.arc_e_tect.example.vanilla'
    ignoreFailures = true
    setJunitVersion(libs.versions.architecture.validator.junit.iff.get())
}
----

`junitVersion` (set here via `setJunitVersion(...)` from the version catalog) controls the JUnit
Jupiter and JUnit Platform Suite versions used by the generated `testArchitecture` suite, so they
can be kept aligned with whichever JUnit line the rest of the build already depends on. This
example pins JUnit `5.10.2` (see `gradle/libs.versions.toml`); the `single-module-hybrid` example
pins `6.1.0` instead — the plugin supports either major line.

== Suggested Fix

Introduce an outbound port in `application.port.outbound`.
Depend on that interface from the application service.
Move the database-specific implementation behind the port in the adapter package.
