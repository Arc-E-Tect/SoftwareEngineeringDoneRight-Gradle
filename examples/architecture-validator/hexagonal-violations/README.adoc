= Hexagonal Violations Example
:toc: left

== Description

This example applies the Architecture Validator plugin to a single-module Hexagonal Architecture sample with multiple intentional violations.
The sample contains violations across adapter, application, and port placement boundaries.

== Intent

This example is intended to show what a failing architecture validation run looks like.
It also demonstrates that user-provided tests in `src/testArchitecture/java` run alongside generated architecture tests.

This is the plugin's canonical acceptance example, referenced from the main
link:../../../architecture-validator/README.adoc[architecture-validator README] — running it is
the quickest way to confirm a local build of the plugin still enforces its built-in rules.

== Build And Run

[source,bash]
----
cd examples/architecture-validator/hexagonal-violations
./gradlew clean testArchitecture
----

== What To Expect

The build is expected to fail with exactly six failing rules from the generated `HexagonalArchitectureTest`:

[source]
----
HexagonalArchitectureTest > domain_must_only_depend_on_domain_or_jdk_core FAILED
HexagonalArchitectureTest > domain_services_must_only_depend_on_domain_core_and_ports FAILED
HexagonalArchitectureTest > inbound_ports_reside_in_correct_package FAILED
HexagonalArchitectureTest > core_layer_must_not_depend_on_adapters FAILED
HexagonalArchitectureTest > adapters_must_not_depend_on_domain_services_directly FAILED
HexagonalArchitectureTest > only_configuration_may_depend_on_domain_service_implementations FAILED
----

The last four all flag the same two `OrderService`/`OrderController` violations, just through
different, complementary mechanisms - `domain_services_must_only_depend_on_domain_core_and_ports`
and `core_layer_must_not_depend_on_adapters` catch `OrderService` depending on `JpaOrderAdapter` (an
allow-list check and a blanket "nothing outside adapters may reach into adapters" check,
respectively), while `adapters_must_not_depend_on_domain_services_directly` and
`only_configuration_may_depend_on_domain_service_implementations` catch `OrderController` depending
on `OrderService` directly (an "adapters must go through ports" check and a "only configuration may
wire a service implementation" check). Seeing the same violation surfaced by more than one rule is
intentional defense-in-depth, not duplication of the same rule.

The project does not enable `ignoreFailures`, so these detected violations cause `testArchitecture`
— and therefore `./gradlew build` — to fail. Adapters are still allowed to implement outbound ports
whose signatures use domain objects; the built-in rule set distinguishes inbound adapters from
outbound adapters specifically so that legitimate case doesn't get flagged.

== Reports

Open `build/reports/architecture-validator/html/index.html` to inspect the full violation report.
The XML report is generated under `build/reports/architecture-validator/xml/`.

== Suggested Fix

Move adapter interactions behind explicit outbound ports.
Place `UseCase` interfaces under the configured inbound port package.
