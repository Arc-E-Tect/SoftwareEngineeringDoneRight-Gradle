= Library-Based Rules Example
:toc: left

== Description

This example applies the Architecture Validator plugin and adds an external rule pack published from the local `layer-validator` build.
The main module consumes that rule pack through `testArchitectureImplementation`.

== Intent

This example is intended to show how custom rule packs can be layered on top of the built-in generated rules.
It demonstrates how external and generated rules can report the same architectural problem from different perspectives.

== Build And Run

[source,bash]
----
cd examples/architecture-validator/library-based-rules
./gradlew clean testArchitecture
----

== What It Proves

The plugin discovers rule-pack test classes from a dependency build.
It generates `ExternalRulePackSuite` and runs the external rules together with the built-in vanilla rules.

The rule pack is an ordinary JUnit/ArchUnit test class — nothing here is Architecture Validator API,
just a class whose name ends in `Test` on the `testArchitectureImplementation` classpath:

[source,java]
----
public class LayeredRulesTest {

    private final JavaClasses classes = new ClassFileImporter()
            .withImportOption(ImportOption.Predefined.DO_NOT_INCLUDE_TESTS)
            .importPackages(System.getProperty("architectureValidator.basePackage", ""));

    @Test
    void applicationLayerShouldNotDependOnAdapters() {
        noClasses()
                .that().resideInAPackage("..application..")
                .should().dependOnClassesThat().resideInAPackage("..adapter..")
                .because("External rule packs should be able to enforce organization-wide layering rules")
                .check(classes);
    }
}
----

Reading `architectureValidator.basePackage` as a system property (rather than hard-coding a
package) is what lets the same rule-pack JAR be reused, unmodified, across projects with different
package roots — the plugin sets that system property automatically for every `testArchitecture`
run.

`layer-validator` is a separate, real Gradle project under this example (`layer-validator/`), built
and consumed as if it were published, but resolved locally via a composite build with dependency
substitution instead of an actual Maven repository — so the example needs no publishing step to
demonstrate a real external dependency:

[source,groovy]
----
// settings.gradle
includeBuild('layer-validator') {
    dependencySubstitution {
        substitute module('com.org.ea:layer-validator') using project(':')
    }
}
----

[source,groovy]
----
// build.gradle
dependencies {
    testArchitectureImplementation 'com.org.ea:layer-validator:1.0.0'
}
----

== What To Expect

`OrderApplicationService` depends directly on `DatabaseAdapter`.
That violates both the built-in vanilla rules and the external `LayeredRulesTest` rule pack.
The project is configured with `ignoreFailures = true`, so Gradle completes while the violation remains visible in the report output.

Open `build/reports/architecture-validator/html/index.html` to inspect details.

== Suggested Fix

Refactor the adapter behind an outbound port.
Then keep the external rule pack in place as a reusable architectural safety net.
