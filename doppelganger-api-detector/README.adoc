A Gradle plugin that finds endpoints which are both declared in your OpenAPI documentation *and* implemented by a `@RestController` method, but have no test verifying that the implementation still honors the contract - a "doppelganger API".

Doppelganger APIs look completely legitimate: they exist on paper and they exist in code. What nobody has confirmed is that the two still agree. This is the companion plugin to link:../shadow-api-detector/README.adoc[Shadow API Detector] (implemented but undocumented) and link:../mirage-api-detector/README.adoc[Mirage API Detector] (documented but unimplemented) - together the three cover the ways an endpoint's documentation, implementation, and verification can drift apart.

== OpenAPI compatibility

The plugin supports OpenAPI v3 documents that are compatible with the parser stack bundled by the plugin.
In practice, this means OpenAPI 3.0.x, 3.1.x, and 3.2.x are supported.
OpenAPI v2 (Swagger 2.0) is not supported.
OpenAPI 2 compatibility conversion is explicitly excluded from the runtime classpath.
The plugin uses `io.swagger.parser.v3:swagger-parser-v3` only.
OpenAPI versions newer than 3.2 are not supported at this time.
If `rootDocument` declares an unsupported version, the `detectDoppelgangerApis` task fails with a parse error.
The root document and every transitively referenced `$ref` document must also be parseable and resolvable as OpenAPI v3 content.

== How it works

1. Every Java source file under the configured controller directories is parsed and scanned for `@RestController` classes, exactly the way link:../shadow-api-detector/README.adoc[Shadow API Detector] does, to build the set of *implemented* endpoints.
2. The configured root OpenAPI document is parsed, following every `$ref` link, to build the set of *described* endpoints.
3. The intersection of the two - endpoints that are both implemented and described - is the candidate set checked for verification evidence.
4. Every enabled contract verification source scans its own directory for evidence that a candidate endpoint's contract has actually been exercised (see "Contract verification sources" below). An endpoint is verified as soon as *any one* source finds evidence for it - the three sources do not need to agree, so teams can adopt them incrementally, in any combination.
5. Every candidate endpoint with no verification evidence from any enabled source is a doppelganger API. An AsciiDoc report listing them, grouped by declaring controller class, is written to the configured report directory - the report is always written, whether or not the build is configured to fail.

[NOTE]
====
Like its siblings, this plugin operates entirely at the source level: it parses Java and configuration source with JavaParser, or a plain structural read for non-Java DSLs, and never compiles or executes anything. This is what gives it a short feedback cycle, including on code that does not currently build.
====

== Contract verification sources

[cols="1,3",options="header"]
|===
| Source                       | Evidence recognised
| Spring RestDocs               | A test method containing either `mockMvc.perform(get(...)/post(...)/put(...)/delete(...)/patch(...))` whose call chain also includes `.andDo(document(...))`, or `webTestClient.get()/post()/put()/delete()/patch().uri(...).exchange()...consumeWith(document(...))`. In the MockMvc case the HTTP verb comes from the static builder method name and the path from its first string-literal argument; in the WebTestClient case the verb comes from the request-builder method and the path from the `uri(...)` call.
| Atlassian OpenAPI request validator | A test method containing either `.filter(new OpenApiValidationFilter(...))` (REST Assured style) or a direct `.validateRequest(...)` / `.validateResponse(...)` call, paired with a REST-Assured-style request built via `given().when().get("/orders/{id}")`-style calls in the same method.
| Spring Cloud Contract         | Contract DSL files under `contractsDir` (a required property when this source is enabled - conventionally something like `src/testContract/resources/contracts/**/*.groovy` and `*.yml`), read structurally for `method '...'` and `url '...'` / `urlPath '...'` entries - no AST, no Groovy compilation.
|===

Each source matches by simple class/method name only, never resolving types - so none of the underlying testing libraries need to be on this plugin's own classpath. This matters in particular for the Atlassian OpenAPI request validator, whose Maven coordinates changed after v3.0.0 from `swagger-request-validator-*` to `openapi-request-validator-*` under `com.atlassian.oai`: matching by simple name recognises both old and new artifact versions identically.

=== Matching a concrete contract example against a templated endpoint

Unlike RestDocs and REST Assured - which build requests using the same `{id}`-style path template syntax Spring itself uses, so the literal string the scanner captures *is* the template - a Spring Cloud Contract file describes one concrete, resolved example request (e.g. `url '/items/1'`), not a template. `getItem` declared as `GET /items/{id}` is still correctly recognised as verified by a contract example for `/items/1`: matching is asymmetric here, treating the declared-and-implemented side as the template and the contract's own path as a concrete instance of it, rather than requiring the two to be structurally identical.

[NOTE]
====
This has one accepted, documented tradeoff: a concrete example path carries no information about which endpoint it was written to exemplify, so it can structurally satisfy a *different* template than the one it was actually meant to cover, if the two happen to share the same segment count and the same literal segments outside the templated position. In practice this is rare, and it is the same class of heuristic imprecision the detector family already accepts elsewhere (e.g. an unrestricted `@RequestMapping`'s `HttpVerb.ANY` matching any documented verb).
====

Spring RestDocs is enabled by default; the other two are opt-in. Enable the sources your team
actually uses:

[source,groovy]
----
doppelgangerApiDetector {
    useOpenApiRequestValidator = true
    useSpringCloudContract     = true
}
----

== Missing rootDocument, controllerDirs, testDirs, or contractsDir

A missing `rootDocument` file, a `controllerDirs` entry that doesn't exist yet, or - for a currently enabled verification source - a `testDirs`/`contractsDir` entry it depends on with none of the currently enabled sources able to gather any evidence at all, is **not** a build failure - `detectDoppelgangerApis` still runs, still writes its report, and never fails the build because of it, regardless of `failOnDoppelganger`. This matters for a build script bootstrapped ahead of the code it describes: a team scaffolding `doppelgangerApiDetector { rootDocument = file('src/main/resources/openapi/openapi.yaml') }` as part of a project template shouldn't see every build break until that file, the first `@RestController`, or the first verification test actually exists.

Instead, the generated report opens with a `[WARNING]` admonition explaining exactly what's missing, and doppelganger API detection is skipped for that run rather than computed from incomplete input - comparing a real OpenAPI document against zero implemented endpoints, or checking for verification evidence that could not possibly have been gathered, would otherwise report every candidate endpoint as a false-positive doppelganger API. `trackContractHistory` is similarly left untouched for that run: the report still displays whatever was last legitimately persisted, but nothing is advanced or saved from a partial view, which would otherwise misrepresent every endpoint this run couldn't see as newly removed.

If `controllerDirs` or `testDirs` has more than one entry and *some*, but not all, exist, detection still proceeds normally using whichever ones do - only the missing entries are called out as individual warnings, without skipping the run entirely. Either one left with **zero** entries configured at all (rather than one that doesn't exist) is treated as a deliberate, valid setup, not a gap, and never warns.

`testDirs` is shared by the Spring RestDocs and OpenAPI request validator sources, so a missing entry only counts as a gap - and only warns - when at least one of those two sources is actually enabled; both are still scanned, even when every `testDirs` entry is missing, since a directory containing no matching evidence looks identical to a scanner as one that doesn't exist yet. Detection is only suppressed when *every currently enabled* source has no usable directory to scan - a single enabled source with real evidence available is enough for the run to be considered complete, even if another enabled source's directory happens to be missing; that source simply contributes no evidence for this run, the same as if it had genuinely found none.

`contractsDir` behaves slightly differently once `useSpringCloudContract` is configured: it must be configured too (see "Configuration errors vs. bootstrapping gaps" below) - once it is, a `contractsDir` that doesn't exist on disk *yet* behaves exactly like a missing `testDirs` entry, warning rather than failing.

=== Configuration errors vs. bootstrapping gaps

Not every incomplete-looking configuration is a bootstrapping gap. Two DSL configurations are rejected eagerly, with a `GradleException`, before anything is scanned - regardless of `failOnDoppelganger` and regardless of what currently exists on disk:

* Every one of `useRestDocs`, `useOpenApiRequestValidator`, and `useSpringCloudContract` disabled at once. With no source enabled at all, no endpoint could ever be verified, so every declared-and-implemented endpoint would always be reported as a doppelganger API regardless of how much test coverage the project actually has - a report, and a potential build failure, with no real signal in it.
* `useSpringCloudContract = true` with `contractsDir` left unconfigured. Unlike `rootDocument`, `controllerDirs`, and `testDirs`, `contractsDir` has no default location: most projects have no `contracts` directory at all, so a missing *value* here means the property was never wired up, not that the directory it points to hasn't been created yet.

Both of these are permanent property-level contradictions, not gaps that a project naturally grows out of - unlike a `rootDocument` or `testDirs` entry that doesn't exist *yet*, no amount of writing tests or generating OpenAPI documentation resolves them; only editing the build script does. That is why they fail the build immediately instead of degrading to a `[WARNING]` admonition.

== Configuration

The plugin registers a `doppelgangerApiDetector` extension.

.Groovy DSL
[source,groovy]
----
doppelgangerApiDetector {
    // One or more directories to search recursively for @RestController classes.
    // Default: src/main/java
    controllerDirs.from('src/main/java')

    // One or more directories to search recursively for test classes, scanned by the Spring
    // RestDocs and OpenAPI request validator verification sources.
    // Default: src/testContract/java
    testDirs.from('src/testContract/java')

    // The root OpenAPI document. Required - every other document is expected to be
    // reachable from this one via $ref links relative to it.
    rootDocument = file('src/main/resources/openapi/openapi.yaml')

    // Directory where the OpenAPI documentation is stored, tracked so that a change to
    // any linked document invalidates the task's cached result.
    // Default: rootDocument's own parent directory
    openApiDir = file('src/main/resources/openapi')

    // Directory searched for Spring Cloud Contract DSL files. No default - required if
    // useSpringCloudContract is true; leaving it unconfigured in that case fails the build.
    // contractsDir = file('src/testContract/resources/contracts')

    // Whether each contract verification source is enabled.
    // Default: true for Spring RestDocs, false for the other two - opt in explicitly to the
    // sources your team actually uses.
    useRestDocs                = true
    useOpenApiRequestValidator = false
    useSpringCloudContract     = false

    // Whether the build should fail when doppelganger APIs are found. The report is written
    // either way.
    // Default: false
    failOnDoppelganger = false

    // Directory the AsciiDoc report is written to.
    // Default: layout.buildDirectory.dir('reports/doppelganger-api-detector')
    reportDir = layout.buildDirectory.dir('reports/doppelganger-api-detector')

    // Name of the generated AsciiDoc report file.
    // Default: 'doppelganger-apis.adoc'
    reportFileName = 'doppelganger-apis.adoc'

    // Version of the system under test whose @RestController classes are scanned, printed near
    // the top of the generated report (see "System Under Test Version" below).
    // Default: the project's own `version`
    // systemUnderTestVersion = 'v1.0.0'

    // Persists a per-endpoint history of when each endpoint first reached declared/implemented/
    // verified status (see "Tracking Contract History" below).
    // Default: false
    trackContractHistory = false

    // NDJSON file the history is read from/written to. Defaults into the project directory
    // (not build/), since it's meant to be committed.
    // Default: file('doppelganger-api-detector-contract-history.ndjson')
    // contractHistoryFile = file('doppelganger-api-detector-contract-history.ndjson')

    // When true, contractHistoryFile is written back to disk. Only consulted when
    // trackContractHistory is true; the file is always read either way.
    // Default: same as trackContractHistory
    // updateContractHistory = true
}
----

.Kotlin DSL
[source,kotlin]
----
doppelgangerApiDetector {
    controllerDirs.from("src/main/java")
    testDirs.from("src/testContract/java")
    rootDocument.set(file("src/main/resources/openapi/openapi.yaml"))
    failOnDoppelganger.set(false)
    reportDir.set(layout.buildDirectory.dir("reports/doppelganger-api-detector"))
    reportFileName.set("doppelganger-apis.adoc")
    // systemUnderTestVersion.set("v1.0.0")
    trackContractHistory.set(false)
    // contractHistoryFile.set(file("doppelganger-api-detector-contract-history.ndjson"))
    // updateContractHistory.set(true)
}
----

`rootDocument` is the only property that must always be set - in all but very rare cases (an OpenAPI description split across many top-level documents with no single entry point) the root document is all the plugin needs, since it is expected to link to every other document itself. `contractsDir` must additionally be set whenever `useSpringCloudContract` is enabled - see "Configuration errors vs. bootstrapping gaps" above.

== Task

[cols="2,1,3",options="header"]
|===
| Task name                | Group        | Description
| `detectDoppelgangerApis` | verification | Scans OpenAPI documentation, `@RestController` implementations, and test-level verification evidence, and reports endpoints that are declared and implemented but never verified against their contract.
|===

The task is **not** wired into `check` or `build` automatically. Teams generating their OpenAPI documentation from code, or migrating their tests onto one of the supported verification mechanisms gradually, would otherwise see every build fail immediately.

Running the report explicitly:

[source,shell]
----
./gradlew detectDoppelgangerApis
----

To make the task part of every build, wire it into `check` (or `build`) yourself once you're ready to enforce it:

.Groovy DSL
[source,groovy]
----
tasks.named('check') {
    dependsOn 'detectDoppelgangerApis'
}
----

.Kotlin DSL
[source,kotlin]
----
tasks.named("check") {
    dependsOn("detectDoppelgangerApis")
}
----

== Progress reporting

This task runs several phases in sequence - scanning `@RestController` classes, collecting OpenAPI endpoints, then scanning each enabled contract verification source - and each can take a while on a large codebase.
A one-line phase banner is logged at `LIFECYCLE` level before each phase starts, numbered out of the total phase count for that run, followed by periodic progress within the phase itself.

[source,shell]
----
> Task :detectDoppelgangerApis
Doppelganger API Detector: [1/3] Scanning @RestController classes...
Scanning @RestController classes: 150/438 (34%)
Scanning @RestController classes: done, 438 file(s)
Doppelganger API Detector: [2/3] Collecting OpenAPI endpoints...
Resolving OpenAPI documents: done, 14 item(s)
Doppelganger API Detector: [3/3] Scanning Spring RestDocs verification evidence...
Doppelganger API Detector: scanned 402 declared-and-implemented endpoint(s), found 5 doppelganger API(s). Report → build/reports/doppelganger-api-detector/doppelganger-apis.adoc
----

The total phase count reflects only the verification sources actually enabled and configured (`useRestDocs`, `useOpenApiRequestValidator`, `useSpringCloudContract`), so it varies from run to run.
This is plain log output, not an animated progress indicator.
The plugin deliberately avoids Gradle's internal, unsupported console/progress APIs, since their shape can change between Gradle versions and this plugin is published on the Gradle Plugin Portal for consumers on Gradle versions this project doesn't control.
Each line is printed once and never overwritten in place, so it plays back cleanly in CI logs as well as an interactive terminal.

== Tracking Contract History

NOTE: For a complete field-by-field reference to `contractHistoryFile` - its exact JSON schema, fingerprint algorithm, lifecycle semantics, and guidance for building tooling (including a visualization UI) around it - see link:docs/contract-history-file-format.adoc[Contract History File Format].

Setting `trackContractHistory = true` persists, across builds, a history of when each endpoint first reached each stage of its contract lifecycle - declared, implemented, stubbed, verified.
The history is keyed by a fingerprint of the endpoint's own HTTP verb and path, not by which plugin observed it, so Shadow, Mirage, and Doppelganger API Detector can all advance the *same* record when pointed at the same `contractHistoryFile` - useful if you run more than one of these plugins against the same API.
Doppelganger API Detector always has evidence for three of the four stages - `declared` from the OpenAPI documentation, `implemented` from the scanned `@RestController` classes, and `verified` from whichever contract verification sources are enabled (an empty list when every source is disabled, still distinct from offering no evidence at all) - but never `stubbed`, since it has no visibility into WireMock stubs.
The plugin itself has no dependency on git or any other version control system - branch-based control over when to advance the history (e.g. "only on `main`") is entirely a CI concern, expressed through `updateContractHistory`.

CAUTION: A `contractHistoryFile` written before `stubbedAt` existed (9 fields instead of the current 10) fails to load with a clear error rather than being silently reinterpreted. Apply the link:../mirage-api-detector/README.adoc[Mirage API Detector] plugin and run its `migrateContractHistory` task against the file to upgrade it in place, or point `contractHistoryFile` at a new location to start a fresh history - see link:../mirage-api-detector/docs/contract-history-file-format.adoc#legacy-format[the format reference's migration section] for details.

[cols="1,1,1,3",options="header"]
|===
| Property                | Type    | Default                                                    | Description
| `trackContractHistory`  | Boolean | `false`                                                    | When `true`, loads, advances, and reports from a persisted contract progress history file.
| `contractHistoryFile`   | File    | `doppelganger-api-detector-contract-history.ndjson` (project directory) | The NDJSON file the history is read from and, when `updateContractHistory` is `true`, written back to.
Deliberately defaults into the project directory, not `build/`, since it's meant to be committed. Only consulted when `trackContractHistory` is `true`.
| `updateContractHistory` | Boolean | same as `trackContractHistory`                             | When `true`, `contractHistoryFile` is written back to disk after being updated with the current run's endpoints.
The file is always *read* when `trackContractHistory` is `true`, regardless of this property - so the generated report always reflects the up-to-date history, whether or not this run persists it. Overridable for the whole build via the `-PdoppelgangerApiDetector.updateContractHistory` project property.
|===

`contractHistoryFile` is newline-delimited JSON (NDJSON) - one line per endpoint - sorted by fingerprint so that git diffs stay minimal and stable:

[source,json]
----
{"schemaVersion":1}
{"fingerprint":"a1f3c9d0e21b7f44","verb":"GET","path":"/orders/{id}","declaringClass":"com.example.OrderController","declaredAt":"2026-01-14T09:02:11Z","implementedAt":"2026-02-20T11:15:44Z","stubbedAt":null,"verifiedAt":"2026-03-01T10:00:00Z","lastSeenAt":"2026-08-12T07:00:00Z","removedAt":null}
----

The first line is a file-level `{"schemaVersion":N}` marker, always written, giving a future format change something to check against and branch reading logic on. It's purely additive: a file written before this existed simply has no such line, and is read exactly as it always was - the marker is optional on read, never required.

A missing `contractHistoryFile` is treated as an empty history, not an error.
A line that fails to parse (e.g. hand-edited into something invalid) is skipped with a `WARNING`-level `java.util.logging` message identifying its line number; it never fails the build.
A previously persisted record whose fingerprint is no longer present in the current scan is *never deleted* - it's kept exactly as it was, except its `removedAt` is stamped the first time it goes missing.

The generated report reflects the loaded (and possibly just-advanced) history as a `== Progress Over Time` section, once `trackContractHistory` finds at least one record: a human-friendly `Tracked since` timestamp, how many endpoints were declared/implemented/stubbed/verified in the last 7 and 30 days, and how many previously tracked endpoints are no longer seen in the current run.

Like any other Gradle task, `detectDoppelgangerApis` is skipped as `UP-TO-DATE` when none of its declared inputs have changed since the last run.
`contractHistoryFile`'s configured *path* (not its content, which the task itself manages) is one of those tracked inputs, so renaming or relocating it in the build script is, on its own, enough to make the task run again and write history to the newly configured location.
If a run is skipped for some other reason and you need to force it regardless (e.g. after manually editing `contractHistoryFile`), pass `--rerun`:

[source,shell]
----
./gradlew detectDoppelgangerApis --rerun
----

== System Under Test Version

Every generated report includes a line just below the title identifying the version of the system under test that was scanned:

[source,asciidoc]
----
System Under Test version: 1.0.0
----

By default, this is the project's own `version`, exactly as set in `build.gradle`/`build.gradle.kts` or a `gradle.properties` file. Set `systemUnderTestVersion` to override it - useful when the `@RestController` classes in `controllerDirs` belong to a different, independently versioned artifact than the one Gradle is building:

[source,groovy]
----
doppelgangerApiDetector {
    systemUnderTestVersion = 'v1.0.0'
}
----

== Report output

After the task runs, an AsciiDoc report is written to the configured `reportDir` (default: `build/reports/doppelganger-api-detector/doppelganger-apis.adoc`), listing every doppelganger API grouped by declaring controller class, with its HTTP verb, path, handler method, source file, and line number.

Every report opens with a preamble explaining what a doppelganger API is, how it differs from a shadow API and a mirage API, what the risks are, and a link to the https://owasp.org/API-Security/editions/2023/en/0x11-t10/[OWASP API Security Top 10] (specifically https://owasp.org/API-Security/editions/2023/en/0xa9-improper-inventory-management/[API9:2023 Improper Inventory Management]). The preamble text lives in its own bundled resource - `doppelganger-api-preamble.adoc` in the plugin's `src/main/resources` - so it can be revised independently of the report-writing code.

When `failOnDoppelganger` is `true` and at least one doppelganger API was found, the task fails the build after writing the report, so the report is always available for inspection regardless of build outcome.

== Full example

[source,groovy]
----
plugins {
    id 'java'
    id 'org.springframework.boot' version '<version>'
    id 'com.arc-e-tect.doppelganger-api-detector' version '<version>'
}

doppelgangerApiDetector {
    rootDocument = file('src/main/resources/openapi/openapi.yaml')
    failOnDoppelganger = true
}

tasks.named('check') {
    dependsOn 'detectDoppelgangerApis'
}
----

With this setup, running `./gradlew check` will fail the build - after writing the report - as soon as any endpoint declared in `openapi.yaml` and implemented by a `@RestController` class has no verification evidence from any enabled contract verification source.

== Relationship to the Shadow and Mirage API Detectors

This plugin and its two siblings scan the same sources of truth - your `@RestController` classes and your OpenAPI documentation - plus, for this plugin alone, your tests:

[cols="1,3",options="header"]
|===
| Plugin                       | Finds
| Shadow API Detector          | `@RestController` endpoints with no matching OpenAPI operation (implemented, undocumented)
| Mirage API Detector          | OpenAPI operations with no matching `@RestController` endpoint (documented, unimplemented)
| Doppelganger API Detector    | Endpoints both declared and implemented, but with no verification evidence (documented, implemented, unverified)
|===

Applying all three to the same project gives full-coverage drift detection across documentation, implementation, and verification. All three plugins share the same DSL shape and configuration property naming pattern (e.g. `failOnShadow` / `failOnMirage` / `failOnDoppelganger`), so switching between - or applying all of them alongside each other - requires no relearning.
