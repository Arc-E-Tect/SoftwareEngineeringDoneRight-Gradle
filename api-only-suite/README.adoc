This project calls its approach to API contracts "API-Only" rather than "API-First," deliberately: "First" implies a client is coming next, which in practice biases teams toward designing the API around that one client instead of treating it as a first-class, consumer-agnostic contract. Being API-Only means the contract, the implementation, and the verification that the two agree are all treated as first-class citizens together, for every endpoint, regardless of who calls it. The Arc-E-Tect API-Only Suite plugin exists to make that discipline easy to adopt in one step: it applies link:../shadow-api-detector/README.adoc[Shadow API Detector], link:../mirage-api-detector/README.adoc[Mirage API Detector], and link:../doppelganger-api-detector/README.adoc[Doppelganger API Detector] together, so declared, implemented, and verified are all checked - with no plugin left out by oversight.

This is a pure composition module. It contains no detection logic of its own, only wiring: applying it is indistinguishable, from each individual plugin's own point of view, from applying all three directly.

== OpenAPI compatibility

The suite composes Shadow, Mirage, and Doppelganger API Detector exactly as if each plugin was applied directly.
OpenAPI v2 (Swagger 2.0) is not supported.
OpenAPI 2 compatibility conversion is explicitly excluded from the runtime classpath of the composed detector plugins.
The composed parser runtime uses `io.swagger.parser.v3:swagger-parser-v3` only.
In practice, OpenAPI 3.0.x, 3.1.x, and 3.2.x are supported.
OpenAPI versions newer than 3.2 are not supported at this time.

== Applying the Plugin

=== Using the `plugins` block (recommended)

.Groovy DSL (`build.gradle`)
[source,groovy]
----
plugins {
    id 'com.arc-e-tect.api-only-suite' version '<version>'
}
----

.Kotlin DSL (`build.gradle.kts`)
[source,kotlin]
----
plugins {
    id("com.arc-e-tect.api-only-suite") version "<version>"
}
----

Applying this plugin applies all three detector plugins. Each one registers its own task and extension exactly as it does when applied on its own - `shadowApiDetector`, `mirageApiDetector`, and `doppelgangerApiDetector` are all available to configure directly, and `detectShadowApis`, `detectMirageApis`, and `detectDoppelgangerApis` are all registered as normal.

== Configuration

The plugin registers a thin `apiOnlySuite` extension exposing only the settings that are almost always identical across all three underlying plugins in practice: the shared OpenAPI document, the controller directories to scan, and whether the build should fail on a detected gap.

.Groovy DSL
[source,groovy]
----
apiOnlySuite {
    // The root OpenAPI document, forwarded to all three underlying plugins' own rootDocument.
    rootDocument = file('src/main/resources/openapi/openapi.yaml')

    // Controller directories, forwarded to all three underlying plugins' own controllerDirs.
    // Default (when left unset here, and unset on every individual plugin too): src/main/java
    controllerDirs.from('src/main/java')

    // Convenience switch forwarded to all three underlying plugins' own failOnShadow/failOnMirage/
    // failOnDoppelganger. Has no effect on detectAllApiGaps itself - see "Task" below.
    // Default: false
    failOnDetection = false
}
----

.Kotlin DSL
[source,kotlin]
----
apiOnlySuite {
    rootDocument.set(file("src/main/resources/openapi/openapi.yaml"))
    controllerDirs.from("src/main/java")
    failOnDetection.set(false)
}
----

**This extension is not a full proxy** for the three underlying plugins - it exists for the common case, not to duplicate every property from `shadowApiDetector`, `mirageApiDetector`, and `doppelgangerApiDetector`. Anything not exposed here - `reportDir`, `reportFileName`, Doppelganger's `testDirs`/`contractsDir`/`useRestDocs`/etc., `systemUnderTestVersion`, and each plugin's own `trackContractHistory`/`contractHistoryFile`/`updateContractHistory` (see each plugin's own "Tracking Contract History" section) - must be configured directly on the individual plugin's own extension block:

[source,groovy]
----
apiOnlySuite {
    // Sets failOnShadow, failOnMirage, and failOnDoppelganger to true in one line - see below.
    failOnDetection = true
}

shadowApiDetector {
    trackContractHistory = true
}

mirageApiDetector {
    trackContractHistory = true
}

doppelgangerApiDetector {
    useSpringCloudContract = false
    trackContractHistory = true
}
----

Since contract history is keyed by a fingerprint of an endpoint's HTTP verb and path rather than by which plugin observed it, pointing all three plugins' `contractHistoryFile` at the *same* file lets them share one unified history - each run fills in whichever stages that particular plugin has evidence for (Shadow/Mirage: declared and implemented; Doppelganger: all three, including verified):

[source,groovy]
----
def sharedHistory = file('contract-history.ndjson')

shadowApiDetector {
    trackContractHistory = true
    contractHistoryFile = sharedHistory
}

mirageApiDetector {
    trackContractHistory = true
    contractHistoryFile = sharedHistory
}

doppelgangerApiDetector {
    trackContractHistory = true
    contractHistoryFile = sharedHistory
}
----

=== Precedence

`rootDocument`, `controllerDirs`, and `failOnDetection` set on `apiOnlySuite` are forwarded to each of the three underlying extensions as a fallback - applied only where that individual extension does not already have a value.footnote:[For `controllerDirs`, "already has a value" is checked once, after the whole build script has evaluated - so a consumer can configure `shadowApiDetector.controllerDirs` anywhere in the script, in any order relative to `apiOnlySuite`, and it will still be recognised as explicitly set.]
**A value set directly on an individual plugin's own extension always wins over the value set on `apiOnlySuite`**, regardless of which block appears first in the build script:

[source,groovy]
----
apiOnlySuite {
    rootDocument = file('openapi/openapi.yaml')
}

shadowApiDetector {
    // This wins for Shadow API Detector specifically - Mirage and Doppelganger still get
    // apiOnlySuite's rootDocument above, since neither of them overrides it directly.
    rootDocument = file('openapi/legacy-openapi.yaml')
}
----

The same precedence rule applies to `failOnDetection`: it forwards as a fallback to each plugin's own `failOnShadow`/`failOnMirage`/`failOnDoppelganger`, and any of those three set directly wins over it.

[source,groovy]
----
apiOnlySuite {
    failOnDetection = true
}

mirageApiDetector {
    // This wins for Mirage API Detector specifically - Shadow and Doppelganger still fail on a
    // detected gap, since neither of them overrides its own fail-on-gap property directly.
    failOnMirage = false
}
----

Note that `failOnDetection` - like `failOnShadow`/`failOnMirage`/`failOnDoppelganger` themselves - has no effect on `detectAllApiGaps`; see "Task" below.

== Task

[cols="2,1,3",options="header"]
|===
| Task name           | Group        | Description
| `detectAllApiGaps`  | verification | Runs all three Arc-E-Tect API-Only detectors: Shadow, Mirage, and Doppelganger.
|===

`detectAllApiGaps` is a plain aggregate task with no detection logic of its own - it lets a consumer who wants everything run one task instead of three. Running any of the three individual tasks directly (`./gradlew detectShadowApis`, etc.) continues to work exactly as it does without this plugin.

[IMPORTANT]
====
**`detectAllApiGaps` never fails the build on a detected gap**, regardless of `failOnShadow`/`failOnMirage`/`failOnDoppelganger` - or `apiOnlySuite.failOnDetection`, which simply forwards to those three.
It depends on three dedicated task instances - not `detectShadowApis`/`detectMirageApis`/`detectDoppelgangerApis` themselves - wired identically except with their own fail-on-gap property forced to `false`.
This is deliberate: without it, whichever detector happened to run first and find a gap would abort the whole task graph before the other two ever ran, silently hiding whatever they would have found - exactly the failure mode this task exists to avoid for a "run everything and see the full picture" workflow.
Each of the three reports is still written normally either way.

Run the individual `detectShadowApis`/`detectMirageApis`/`detectDoppelgangerApis` tasks directly - or wire them into `check` one at a time - when you actually want the build to fail on a detected gap.
====

The task is **not** wired into `check` or `build` automatically, for the same reason none of the three individual plugins are: teams generating their OpenAPI documentation from code, or migrating their tests onto one of Doppelganger's verification mechanisms gradually, would otherwise see every build fail immediately.

Running all three detectors explicitly:

[source,shell]
----
./gradlew detectAllApiGaps
----

To make the aggregate task part of every build, wire it into `check` (or `build`) yourself once you're ready to enforce it:

.Groovy DSL
[source,groovy]
----
tasks.named('check') {
    dependsOn 'detectAllApiGaps'
}
----

.Kotlin DSL
[source,kotlin]
----
tasks.named("check") {
    dependsOn("detectAllApiGaps")
}
----

Since `detectAllApiGaps` never fails on a detected gap (see above), wiring it into `check` this way makes `check` regenerate all three reports as part of every build, but does *not* make `check` fail when a gap is found - wire the individual tasks into `check` instead if that's what you want.

| Shadow API Detector       | `build/reports/shadow-api-detector/shadow-apis.adoc` - see link:../shadow-api-detector/README.adoc#_report_output[its own "Report output" section]
| Mirage API Detector       | `build/reports/mirage-api-detector/mirage-apis.adoc` - see link:../mirage-api-detector/README.adoc#_report_output[its own "Report output" section]

|===

== The Shadow / Mirage / Doppelganger / Compliant relationship

Every endpoint the three composed plugins look at falls into exactly one of four states:

[cols="1,3",options="header"]
|===
| State | Meaning

| Shadow
| Implemented, *not* declared - link:../shadow-api-detector/README.adoc[Shadow API Detector]'s finding: exists in code but not in the OpenAPI description.

| Mirage
| Declared, *not* implemented - link:../mirage-api-detector/README.adoc[Mirage API Detector]'s finding: exists in the OpenAPI description but not in code.

| Doppelganger
| Declared *and* implemented, but *not* verified - link:../doppelganger-api-detector/README.adoc[Doppelganger API Detector]'s finding: no test confirms the two still agree.

| Compliant
| Declared, implemented, *and* verified - what none of the three plugins flags.
|===

These four states are a strict partition, not four independently-chosen numbers: fixing how many
endpoints are declared, how many are implemented, how many are verified, and the total endpoint
count pins all four state sizes at once. Concretely, given `declaredCount` (endpoints with an
OpenAPI description), `implementedCount` (endpoints with a matching `@RestController` method),
`verifiedCount` (endpoints with a passing contract test), and `totalCount` (the union of all
endpoints seen by any of the three):

[source]
----
overlap        = declaredCount + implementedCount - totalCount   // declared AND implemented
Shadow         = totalCount - declaredCount
Mirage         = totalCount - implementedCount
Compliant      = verifiedCount
Doppelganger   = overlap - Compliant
             = declaredCount + implementedCount - totalCount - verifiedCount
----

`overlap` (declared-and-implemented, regardless of verified) splits entirely between Doppelganger
and Compliant, so `Doppelganger <= overlap` is the only extra constraint - the other three states
are already fully determined once `declaredCount`, `implementedCount`, `verifiedCount`, and
`totalCount` are fixed.

This is the same relationship the
link:../tracker-lens/DASHBOARD-THEMING.adoc#shadow-mirage-doppelganger-compliant-math[tracker-lens
plugin documents], for anyone building a dashboard or report that visualizes all four states
together rather than reading each detector's own report in isolation - see
link:../tracker-lens/README.adoc#_the_lens_system[tracker-lens] and its
`examples/tracker-lens/dashboard-extra-charts` example for a worked visualization built on exactly
this math.

== Full example

[source,groovy]
----
plugins {
    id 'java'
    id 'org.springframework.boot' version '<version>'
    id 'com.arc-e-tect.api-only-suite' version '<version>'
}

apiOnlySuite {
    rootDocument = file('src/main/resources/openapi/openapi.yaml')
}

shadowApiDetector {
    failOnShadow = true
}

mirageApiDetector {
    failOnMirage = true
}

doppelgangerApiDetector {
    failOnDoppelganger = true
}

tasks.named('check') {
    dependsOn 'detectAllApiGaps'
}
----

With this setup, running `./gradlew check` runs all three detectors against the single configured `rootDocument`, and fails the build - after every report has been written - as soon as any of the three finds a gap.
